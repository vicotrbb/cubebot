# Operator and API reference

Configuration and HTTP behavior of what currently runs. Intended design lives in [ARCHITECTURE](../ARCHITECTURE.md).

## Runtime and lifecycle

Each agent pod runs one container in the installation's declared sandbox runtime ([In-house VMM as the agent sandbox](adr/sandbox.md#in-house-vmm-as-the-agent-sandbox)): in `kvm`, `cubebot-sandbox run` from `apps/sandbox`, which boots `cubebot-agent` in a KVM guest from the guest kernel and root image the sandbox image always carries (see the [sandbox](../apps/sandbox/README.md)); in `container`, the agent image itself as `cubebot-agent container`, optionally under a RuntimeClass or Docker runtime ([Standard containers with optional sandbox runtimes](adr/sandbox.md#standard-containers-with-optional-sandbox-runtimes)). Both run the same agent, desktop and workspace layout; only `kvm` contains a kernel exploit from software the agent installed. The console's Platform health view shows the runtime, and calls only `kvm` a virtual machine. The agent runs its tools itself, as the configured tool user, when the terminal flag is set.

The backend remains a modular monolith. PostgreSQL uses SQLx with embedded versioned migrations. The agent module also has a namespaced kube-rs API adapter, durable resource reservations and a fixed pod/PVC specification compiler. Controlled HTTP, PostgreSQL and manifest tests cover these boundaries; explicit reconciliation provisions and observes installation anchors, workspace claims and pods, and explicit installation configuration now activates serial lifecycle reconciliation at startup. The compiler requires digest-pinned images, a dedicated runtime service account, HTTPS orchestrator origin and CSI support for ReadWriteOncePod.

Kubernetes clients are constructed from explicit configuration with transport retries disabled; reconciliation owns safe recovery rather than replaying effectful requests. Explicit reconciliation now drains, requests guarded pod shutdown, retains terminal evidence, releases only its own execution finalizer and permits a later pod epoch. The same recovery path handles a proven terminal pod without advancing the agent's desired generation; partial runtime failure, NodeLost and deletion latch that physical attempt into drain. Authenticated quiescence reports alone never authorize replacement; a missing pod without retained terminal proof remains uncertain.

Runtime bootstrap TokenReview is enabled with explicit controller configuration. `POST /api/runtime/bootstrap` issues one agent credential per sandbox incarnation. It has no clock expiry; it stops working when its pod attempt is no longer bound to that pod, or when an operator runs `cubebot-admin revoke-runtime <agent-id>` (with `CUBEBOT_DATABASE_URL`). Revocation covers every incarnation the agent has had so far: their channels close, they receive no more work or provider material, their ledger writes are refused and they cannot bootstrap again. A later incarnation, such as the replacement after the revoked agent exits, gets a new credential, so stop the agent to keep it stopped. The same process may bootstrap again to rotate an unrevoked credential. The native runtime requires `CUBEBOT_ORCHESTRATOR_ORIGIN`, `CUBEBOT_BOOTSTRAP_TOKEN_FILE` and a private existing `CUBEBOT_JOURNAL_DIRECTORY`; its tool journal occupies the `tools` subdirectory. HTTPS is required except for literal loopback HTTP used in local tests. Redirects, automatic retries and environment proxy discovery are disabled.

## Local database

The liveness-only process still runs without a database. To run the identity API with PostgreSQL:

```sh
cp .env.example .env
# Choose your local POSTGRES_PASSWORD in .env.
just db-up
just db-down
```

This is the `cubebot-dev` Compose project, separate from an installation's. It publishes PostgreSQL on loopback (`POSTGRES_PORT`), which a release does not, and retains its named volume when stopped. The example credentials are for local development. The orchestrator applies embedded migrations when `CUBEBOT_DATABASE_URL` is exported. Invalid configured databases stop startup.

### Identity development workflow

Export `CUBEBOT_DATABASE_URL` with your local PostgreSQL connection string. Create the initial administrator through the local operator binary, using exported `CUBEBOT_BOOTSTRAP_LOGIN` and `CUBEBOT_BOOTSTRAP_PASSWORD`, then remove those bootstrap variables from your shell:

```sh
cargo run --locked -p cubebot-orchestrator --bin cubebot-admin -- bootstrap
cargo run --locked -p cubebot-orchestrator
```

Bootstrap is one-time and serialized in PostgreSQL. Passwords must contain 12–1024 bytes and logins use 3–64 lowercase ASCII letters, digits, dots, underscores or hyphens, starting with a letter or digit. Passwords use Argon2id. Sessions last one day and persist only SHA-256 token digests. Send the returned opaque token as `Authorization: Bearer <token>` over HTTPS outside loopback development. `GET /api/identity/setup` returns `{"open": bool}`, true until the installation has its administrator. While open, the unauthenticated `POST /api/identity/setup` takes `login` and `password`, runs the same bootstrap and answers like login, with the token and the session cookie; once bootstrapped, by either path, it returns 409. It shares login's password-hashing capacity and returns 429 when that is saturated. With `CUBEBOT_BOOTSTRAP_LOGIN` and `CUBEBOT_BOOTSTRAP_PASSWORD_FILE` (a file, such as a mounted Secret; one trailing newline is ignored), the orchestrator itself runs the same bootstrap at start while setup is open, does nothing once it is closed, and refuses to start with an invalid login or password; the Helm chart's `admin` values set both. There is no other public registration endpoint ([Invitations and optional OpenID Connect admission](adr/identity.md#invitations-and-optional-openid-connect-admission)).

The current identity API has `GET` and `POST /api/identity/setup`, `POST /api/identity/login`, `GET /api/identity/me` (the account's `id`, `login`, `administrator` and a `name` that is `null` until accounts carry a display name), `POST /api/identity/logout`, administrator-only `POST /api/identity/accounts`, and administrator-only `POST /api/identity/suspend`. Login and account creation accept `login` and `password`; creation also requires a unique `request_id` and accepts `administrator`, default false. Suspension requires account `id`, `expected_revision` and `request_id`. `GET /api/identity/accounts` returns up to 100 administrator-visible account summaries with activity and revisions; pass the last ID as `?after=<id>` for the next page. Logout removes the session, and suspension blocks subsequent authentication and removes the account's sessions.

Administrators create a seven-day invitation with `POST /api/identity/invitations`, a `login` and a unique `request_id`. The first response contains its ID, revision and a one-time bearer token; only its digest is stored. Retrying that request returns the same ID/revision with `token: null`. Deliver the token through a trusted channel. `POST /api/identity/invitations/accept` requires that token, a new password and a unique `request_id`, creating only the bound member login. Repeating the original request with its original password returns the recorded account ID while the invitation remains valid and the account active; changing the password conflicts, and a different request cannot redeem the used invitation. `POST /api/identity/invitations/revoke` requires the invitation ID, `expected_revision` and `request_id`. Expired/revoked/used invitations cannot create another account, and inviting an existing suspended login cannot reactivate it. `GET /api/identity/invitations` lists up to 100 administrator-visible invitation statuses/revisions, with `?after=<id>` pagination. If the issuing response is lost, inspect and revoke the recorded invitation, then issue a new request to obtain a new token. Raw tokens are not recoverable.

### Optional OpenID Connect and browser sessions

Administrators set single sign-on up in the console under Platform › Sign-in, which needs `CUBEBOT_PUBLIC_ORIGIN`: `GET /api/identity/oidc/settings` returns `{managed, enabled, issuer, client_id, has_client_secret, admit_subjects, admit_email_domains, redirect_uri, can_store_secret}`; `PUT` with `{issuer, client_id, client_secret?, admit_subjects, admit_email_domains}` fetches the issuer's discovery document first (503 `oidc_unavailable` when it fails, and nothing changes), then stores the settings and applies them at once; `DELETE` turns single sign-on off. The callback is always `<public origin>/api/identity/oidc/callback`. An absent `client_secret` keeps the stored one and an empty one removes it; it is encrypted with the credential key (`CUBEBOT_CREDENTIAL_KEY_FILE`), never returned, and without that key only a public client can be saved. Saving changed settings or turning it off ends the sessions single sign-on started; built-in sign-in keeps working. Each change is audited as `oidc.configure` or `oidc.disable`. `GET /api/identity/oidc` answers `{enabled}` without a session, for the sign-in page, which then offers "Continue with single sign-on".

`CUBEBOT_OIDC_CONFIG`, the path to a local JSON configuration file, still sets it from the deployment instead and then wins: the console shows those settings read-only and `PUT` and `DELETE` answer 409. Configure the provider to allow this exact callback URI:

```json
{
  "issuer": "https://identity.example.com",
  "client_id": "cubebot",
  "redirect_uri": "https://cubebot.example.com/api/identity/oidc/callback",
  "admit_subjects": ["explicit-provider-subject"],
  "admit_email_domains": []
}
```

If the provider requires a confidential client, export `CUBEBOT_OIDC_CLIENT_SECRET` separately. HTTPS is required except for loopback development. `CUBEBOT_PUBLIC_ORIGIN` optionally specifies the exact browser origin and must agree with the callback origin; OIDC otherwise derives it from the callback. Set this origin even without OIDC to enable built-in browser session cookies. The service does not load these values from `.env` itself.

`POST /api/identity/oidc/start` returns an authorization URL and sets a ten-minute HttpOnly browser flow cookie. Follow the URL, then return through the callback. Cubebot validates state, browser binding, PKCE, nonce, signature, issuer, audience, expiry and any access-token hash before issuing its one-day platform session cookie and redirecting to `/`. While single sign-on is off its start, link and callback endpoints answer 404. HTTPS session and flow cookies use `__Host-` names, `Secure`, `Path=/` and `SameSite=Lax`; loopback HTTP uses development cookie names. Unsafe cookie-authenticated requests require an exact matching `Origin`; bearer API clients keep their existing authentication path.

New membership requires either an exact admitted subject or an explicitly allowed domain on a verified email claim. Both lists default empty. Userinfo may supply a missing email, with its subject checked against the ID token. Admission creates an ordinary member; provider role/group claims confer no administrator status or local team membership. Existing active bindings can sign in without repeating first-login admission. Accounts are bound by trusted issuer and subject, never merged by matching email.

`POST /api/identity/oidc/link` starts explicit linking from a platform session created within ten minutes. That session must still be valid at callback. Each account has at most one active subject per issuer. Administrators inspect bindings with `GET /api/identity/oidc/bindings` (100 records, `?after=<id>` cursor), and revoke with `POST /api/identity/oidc/revoke`, supplying `id`, `expected_revision` and `request_id`. Revocation retains the binding as a tombstone and removes the account's OIDC-derived sessions, while built-in sessions remain independent. Suspension also prevents automatic re-admission.

Changing the non-secret OIDC configuration or removing it advances a persisted policy revision, invalidating pending flows and OIDC sessions. Rotating the client secret alone does not invalidate platform sessions. Built-in credentials remain available for installation recovery. Discovery/JWKS are refreshed during callback; provider requests have deadlines, reject redirects and limit response bodies to one MiB. Four concurrent OIDC operations and 1,000 pending unexpired flows bound basic resource use.

### Durable agent definitions

`POST /api/agents` accepts `request_id`, `name` and `instructions`. Creation currently requires an installation administrator and records a durable definition, command receipt and event in one PostgreSQL transaction. Names must contain 1–255 UTF-8 bytes without control characters; instructions accept at most 65,536 bytes and exclude null bytes. Repeating the same request returns the original ID/revision; changing its content conflicts. Current administrator authority is checked before returning a cached creation receipt.

`GET /api/agents` lists up to 100 agents the caller holds any capability on: administrators see every agent, others those with a user or team grant on the agent or on its conversation. Pass the last returned ID as `?after=<id>` for the next page; authorization filtering occurs before the page limit. `GET /api/agents/<id>` returns the same summary for one agent. It carries `capabilities`, the caller's own grants on that agent and its conversation as names such as `conversation_send` (administrators get every agent capability), `avatar` (`paint`, `eyes` and `accessory` of the cube, `orange`/`round`/`none` by default), `desktop_active` (a running turn called `computer`, a `browser_*` tool, `vault_fill`, `request_login` or `screenshot` in the last 120 seconds), `pending_login`, `last_sequence` (the newest turn in its conversation, 0 without turns) and `read_sequence` (the caller's read cursor, 0 until set). `instructions` is `null` without `agent_manage`. Creation and `POST /api/agents/<id>/definition` accept an optional `avatar`; like the wallpaper it is not part of the revision history. Unknown and inaccessible IDs both return 404. Revoking a grant or removing team membership takes effect on subsequent reads without a new login. Definition updates, revisions, status and lifecycle still need `agent_manage`, and these management permissions confer no memory, workspace or conversation access. `GET /api/agents/<id>/wallpaper` serves the image to anyone who may see the agent, 404 while it uses the default.

Definitions belong to the installation; `created_by` is provenance rather than ownership. They begin with revision 1 and `desired_state: "running"`: agents are always on ([Agent idle lifecycle](adr/agents.md#agent-idle-lifecycle)). `activity` is `working`, `dreaming`, `sleeping` (running, idle past `idle_delay_seconds` with nothing queued, waiting or delegated) or `idle` for a running agent, and `stopped` or `retired` otherwise. Desired state is persisted intent, not an observation of a pod. Explicitly configured lifecycle reconciliation can provision the fixed workload layout. No create response claims successful provisioning.

Managers edit with `POST /api/agents/<id>/definition`, supplying `request_id`, `expected_revision`, `name`, `instructions` and `idle_policy` of `sleep` or `keep_running`, which is kept and has no effect. Edits increment the agent revision, retain immutable snapshots and increment `instructions_revision` only when instruction text changes. `GET /api/agents/<id>/revisions?after=<revision>` returns up to 100 authorized configuration snapshots in ascending order. Their revision numbers can skip lifecycle-only changes. Existing definitions are snapshotted when this migration is applied; unavailable historical text is not reconstructed.

`GET /api/agents/<id>/status` requires current agent-management access and reports desired state separately from the latest physical attempt, resource phase, validated Kubernetes phase/readiness/reason, observation time/age, blocked reason, drain report and retained terminal-evidence indicator. It includes workspace reservation status and current runtime identity eligibility without credentials, manifests or raw proof. Missing Running observations hold Active identity while recovery reporting remains bounded by its credential expiry.

`POST /api/agents/<id>/lifecycle` accepts `request_id`, `expected_revision` and `action` of `start`, `stop`, `restart` or `retire`. HTTP 202 acknowledges persisted intent only. Start from stopped and explicit restart advance `restart_generation`; start while already running does not, and a message to a stopped agent starts it. Replay returns its original receipt without repeating the transition. A retired definition remains inspectable but cannot be edited or started. Previously accepted receipts can still be replayed by their original actor while that actor retains current management access. With explicit controller configuration, startup acquires installation process ownership and reconciles these commands automatically. Without it, database-only development mode persists intent and serves no runtime routes.

The Kubernetes boundary currently supports namespaced pod/PVC creation, recorded-pod observation and guarded pod stop/finalizer requests. It checks the recorded namespace/name/UID, installation/agent/attempt labels and installation ConfigMap controller anchor before changing an existing pod. Stop requests require Cubebot's execution finalizer and send UID plus resource-version preconditions with a nonzero grace period. Finalizer release requires deletion already requested, non-restarting runtime/tool containers with known identified exit reports, and terminal init containers; it preserves other controllers' finalizers. Missing objects, changed UIDs, unknown container status, NodeLost and ephemeral execution remain uncertain. The installation anchor/UID registry, resource specifications, runtime control protocol and configured controller activation are implemented. The running service contacts Kubernetes only when explicitly configured. Its single-active guard retains ownership across database-session loss and requires exact prior-container termination evidence for crash takeover.

### Runtime channel

`GET /api/runtime/channel` upgrades to a WebSocket after checking the agent credential; human credentials are rejected. Messages are JSON text tagged by `type`.

- Agent to orchestrator: `pull` (ready for the next turn), `event` with `turn`, `sequence` and `event`, and `drained` with `request_id`.
- Orchestrator to agent: `turn`, `ack` with `turn` and `sequence` once an event is durable, `cancel` with `turn`, `steer` with `turn`, `id` and `message`, `drain` with `request_id`, `backup` with `backup` (send the workspace; see [Backups](#backups)), and `revoked`.
- A `turn` carries the message, the agent's instructions, the current model and provider key, up to twelve completed earlier exchanges, tool events from earlier runs of the same turn and the first event sequence to use. The agent assembles its own context from these records.
- Event kinds are `text_delta`, `tool_call`, `tool_result`, `usage`, `summary`, `steered`, `done` (which may carry staged `memories`; see [Memory](#memory)) and `error`. The orchestrator appends each to `turn_events`, keyed by turn and sequence; a resent event keeps its first recorded form. Only `done` or `error` from the attempt running the turn settles it. Later events are retained as evidence.

Turns run in lanes ([Agent execution lanes](adr/agents.md#agent-execution-lanes)): one main-lane turn per agent, for direct chat, room work and messages, which a partial unique index enforces, beside up to the agent's `task_lanes` delegated tasks (one to four, default two, set with the agent definition). A task's turn carries `task: true`, no conversation history, and no computer tool. A waiting turn holds its lane until it is retried or cancelled. Cancelling a turn marks it `cancelled` and the channel delivers `cancel`. When the credential stops authorizing the sandbox, the channel delivers `revoked` and closes; stopping the sandbox is the hard stop. While a drain request exists the channel delivers `drain`. The agent finishes its active turn and replies `drained`, then the orchestrator records the acknowledgement and answers `revoked`. A turn left running by an attempt whose session is no longer valid becomes `waiting` with `execution_interrupted`.

The agent keeps unacknowledged events in memory and resends them after reconnecting. It journals each tool call before running it and each result before reporting it. After a crash it reports a journaled result, or an `uncertain` result for a call that never finished, and never runs the command again. A tool call with no definite result after its run ended is shown as uncertain and blocks retry of that turn.

Each channel polls PostgreSQL once a second for new turns, cancellation, drain and revocation.

Browsers follow a conversation through `GET /api/conversations/{id}/events`, a server-sent event stream. It replays `turn_events` after a cursor (`after` or `Last-Event-ID`; without one, from the running turn's first event), then polls twice a second. `turn_event` frames carry each event with its conversation-wide id; `turn` frames carry a turn snapshot whenever its state may have changed. Recording an event locks its conversation, so ids become visible in order and a cursor never skips one.

### Plan sign-in

[Personal subscription connections](adr/identity.md#personal-subscription-connections). An administrator can power agents with their own ChatGPT Plus/Pro or SuperGrok/X Premium plan from Platform → AI providers, on the OpenAI and xAI Grok cards. The plan is personal: it serves only agents its owner created, and room routing and task orchestration of messages and tasks they started. It is never offered to other people's agents, and only its owner can make it the provider in use (`provider: "chatgpt"` or `"supergrok"` on `POST /api/provider`, without `api_key` or `access`).

- ChatGPT uses OpenAI's Sign in with ChatGPT program. `POST /api/provider/subscriptions/chatgpt` returns an authorization URL; the first sign-in registers the installation (`client_id=dynamic_agent_client`) and keeps the issued `oaiapp_…` id with one `ext_agent_host_id` per installation. The browser then lands on `http://127.0.0.1:1456/auth/callback?…`, which does not load; the person pastes that address to `POST /api/provider/subscriptions/chatgpt/{sign_in}`. Inference goes to `api.openai.com/v1/responses` with `store:false`, `stream:true`, the system prompt as `instructions` and no `max_output_tokens`; models come from the account's `/v1/models`.
- Grok uses device-code sign-in at `auth.x.ai` with the Grok CLI's client id, and inference at `cli-chat-proxy.grok.com/v1` sends `x-grok-client-version` because the proxy refuses other clients. The console asks for explicit consent first. `POST /api/provider/subscriptions/supergrok` returns the code and xAI's page; `POST …/supergrok/{sign_in}` answers 202 until the person approves.
- `GET /api/provider/subscriptions` lists signed-in plans without tokens: the account, owner, expiry, `problem` (`sign_in_again` after a refused renewal, `refresh_failing` while a renewal retries) and `waiting`, the turns held by the plan's usage limit. `DELETE /api/provider/subscriptions/{provider}` forgets the tokens, stops agents using the plan and asks the vendor to revoke it; `revoked:false` means the vendor did not confirm.
- Tokens are one encrypted record per plan, bound to its token revision. The orchestrator renews them every half minute once due (ChatGPT only allows it in the last minutes of its one-hour token), one renewal at a time under the row lock, and saves the rotated refresh token with the new access token. A turn carries only the access token and `api_key_expires_at`; within five minutes of that time the agent asks `GET /api/runtime/provider` for the current one. A token with under two minutes left is never handed out.
- A MiniMax M Plan has no sign-in: its owner pastes the plan's key on the MiniMax card (`POST /api/provider/subscriptions/minimax` with `provider: "minimax_plan"`, or `"minimax_plan_cn"` for the mainland China platform). It is stored and served exactly like a signed-in plan, but never expires or renews, and `DELETE /api/provider/subscriptions/minimax/{provider}` always answers `revoked:false` because MiniMax has no revocation endpoint. MiniMax sells the plan for "individual, interactive developer use"; a pay-as-you-go key (`minimax`, `minimax_cn`) is the installation-managed choice for shared or production agents. Both reach MiniMax's Anthropic-compatible API (`api.minimax.io/anthropic`, or `api.minimax.cn/anthropic`), so thinking blocks replay unchanged; there is no computer toolset, cache breakpoint or `tool_choice: none`, and the window and output limit are fixed at the documented 1M and 128K. Plan turns carry no price; mainland pay-as-you-go turns stay unpriced because MiniMax bills them in yuan.
- A plan's usage limit stops the turn with `provider_usage_limit` and it waits; vendors give no reset time, so a person retries it, or switches agents to another provider first.

These sign-ins are for self-hosted installations; do not offer them in a hosted, multi-tenant Cubebot.

### Rooms, delegation and steering

Rooms ([Direct mentions and a tool-free room coordinator](adr/rooms.md#direct-mentions-and-a-tool-free-room-coordinator), [Independent assignments for multiple room mentions](adr/rooms.md#independent-assignments-for-multiple-room-mentions), [Explicit agent messaging and delegation](adr/rooms.md#explicit-agent-messaging-and-delegation), [Queued messages with explicit steering](adr/rooms.md#queued-messages-with-explicit-steering), [Cancel selected work and its descendants](adr/rooms.md#cancel-selected-work-and-its-descendants) and [Contain delegated failures and let the parent adapt](adr/rooms.md#contain-delegated-failures-and-let-the-parent-adapt)) reuse the `room` grant scope: `conversation.read` reads a room, `conversation.send` posts to it, and administrators create rooms with `POST /api/rooms` (`request_id`, `name`, `agents`). `PUT /api/rooms/{room}/members` with `agents` replaces the member set, for administrators and `room.manage` holders; removed members keep the work already delivered to them. A room's `manage` says whether the viewer may change its members.

- `POST /api/rooms/{room}/messages` with `request_id` and `message`. Each member named as `@name` (case-insensitive, not inside a word or address) gets one turn in its own conversation, prefixed with the room and sender; the same request posted again returns the same message and creates no turn. When the turn is claimed, the room's last ten earlier messages and the agents' replies to them go ahead of its request; they are context, not stored with the turn. A message without a member mention is `routing`: the orchestrator's coordinator, running beside the controller every two seconds with the installation's provider connection and no tools, sends the room, members, up to five open tasks of the room and the last ten messages, and expects `assign` with a member id or `continue` with an open task id; every message, chatter included, gets an owner. `continue` adds the message as steering to that task and settles the message as `continued`, naming the task's agent in `note`. The answer is validated against current membership before a turn exists. After three failed or invalid answers, or without a provider connection, the room's first member by name takes the message; only a room without members settles it as `failed`. It is never broadcast. Messages settled before 2026-11-03 may still read `clarify` or `no_action`.
- Agents reach agents that share a room with them through `delegate` and `send_message`, which call `POST /api/runtime/turns/{turn}/messages` with the tool call's id; a resent call returns the same child. A child is a turn in the recipient's conversation with `parent_turn_id` set, and at most four ancestors. A delegated child runs in a task lane. A delegating parent that ends its run with children still open becomes `delegated` and holds no lane; each time one of its children settles it is queued again, and its next run gets every delegated child: settled ones with their outcome, failed or cancelled ones with their last eight tool events as evidence, open ones with their status. An agent-originated turn that errors becomes `failed` instead of `waiting`. `send_message` children are not waited for; with `expects_reply` a completed one is relayed once to its sender as a new turn, `Reply from agent …`, unless it already answered with `send_message`, and the relay expects no reply.
- `POST /api/conversations/{id}/messages/{turn}/steer` queues a correction for a queued, running or delegated turn. The channel sends `steer` while the turn is active; the agent adds it to the context before its next model request and reports `steered`, which marks it incorporated. A turn that ends first leaves it unincorporated, and steering never reopens it. Steering a turn also copies it to its open delegated descendants (`propagated`), not to messages it sent.
- Cancelling a turn cancels every unsettled descendant through `parent_turn_id`, including `send_message` children; completed results stay. Delegation and cancellation lock the ancestry's root, so a child committed before a cancel is cancelled with it and none can be created after.

`GET /api/rooms/{room}/events` streams the room as server-sent `message` frames: a `RoomMessage` snapshot whenever a message is new or its routing or deliveries change, polled once a second, resuming after `after` or `Last-Event-ID`. Room summaries from `GET /api/rooms` carry `last_sequence`, the newest message, and `read_sequence`, the viewer's cursor. `just docker-rooms` runs all of this on real agents through Docker, with the console in Chromium when `CUBEBOT_PLAYWRIGHT_MODULE` is set.

### Preferences and read cursors

`GET /api/identity/me/preferences` returns the caller's console preferences, `{favorites: [{kind: "agent"|"room", id}], theme: "system"|"light"|"dark", collapsed: [string]}`, with defaults before the first write; `PUT` with the same shape replaces the whole document, and the last write wins. It is one JSON document per account, at most 200 favorites and 100 collapsed sections. `PUT /api/conversations/{id}/read` and `PUT /api/rooms/{id}/read` with `{sequence}` record how far the caller has read: one cursor per account and scope that only moves forward, so a lower value is ignored and the response carries the cursor as stored. Both need `conversation.read` on that scope; a negative sequence is invalid.

### Installation stream

`GET /api/installation` returns `{name, terminal_enabled, computer_use_enabled, controller}` for any signed-in session: `controller` is `kubernetes`, `docker` or `database_only`, the flags come from the active controller or Docker configuration, and `name` is the administrator's name for it, else `CUBEBOT_INSTALLATION_NAME`, else "Cubebot". Administrators read and change it under Platform › General: `GET /api/installation/settings` returns `{name, storage_quota_bytes, upload_limit_bytes, revision, default_name, storage}`, where `storage` (absent without shared files) holds `{capacity_bytes, quota_bytes, default_quota_bytes, upload_limit_bytes, default_upload_limit_bytes, used_bytes}` with the values in force; `PUT` with `{name, storage_quota_bytes, upload_limit_bytes, revision}` applies at once, where `null` returns a value to the deployment's, a name is 1 to 64 characters, a quota at least 64 MiB and an upload limit at least 1 MiB (400 otherwise), and a stale `revision` answers 409. Changes are audited as `installation.settings`. `GET /api/events` is one server-sent stream per browser session, polled once a second with two queries, one for agents and one for rooms. `agent` frames carry the same summary as `GET /api/agents` for every agent the caller may see, each once when the stream opens and again whenever its `activity`, `desktop_active`, `pending_login` or `last_sequence` changes; `room` frames carry `{id, last_sequence}` for every visible room when the stream opens and whenever a room's newest message changes. Keep-alives are sent between polls, every poll reauthenticates, and the first poll runs before the response so a refusal is an HTTP status.

### Activity

`GET /api/activity` lists, newest first and at most 100, what needs the caller: `{kind, agent, room, turn, at, text}` with `at` in RFC 3339. Kinds are `login_pending` for pending login handoffs on agents the caller may see, `turn_waiting` and `turn_failed` for turns in conversations they hold `conversation.read` on (`room` names the room a delivery came from), `invitation_pending` for administrators, and `dream_published_skill` for skill revisions a dream run published on agents they hold `memory.read` or `agent.manage` on. Everything is derived from the tables that already record it; nothing is stored or acknowledged.

### Memory

Each agent has one memory pool in `memories`, with every revision in `memory_revisions`. A revision is authored either by a person (`human_id`) or by the agent through the turn that wrote it (`turn_id`); removal is a revision too and only hides the memory from search. Search is PostgreSQL full-text (`english` configuration): any query word matches, results are ranked by `ts_rank`, and there are no vectors.

- The agent has three tools: `search_memory`, `remember` (to revise, pass a memory id and revision) and `forget`. Nothing is searched unless the agent calls `search_memory`, which uses `GET /api/runtime/memories?query=` with its agent credential and returns at most ten of that agent's own memories. An unavailable search is reported as unavailable, not as empty.
- `remember` and `forget` stage changes in the turn. When the model's reply ends the turn, the agent makes one more request, without tools, asking for up to five durable facts the turn did not save, and stages any it returns. A turn that stages a removal skips this request: with a real model, extraction there re-saved the removed fact as a note. The staged changes travel on the `done` event as `memories` and commit in the same transaction that completes the turn. A failed or cancelled turn commits none of them. A revision or removal against a revision that is no longer current, such as one a person has since edited, is dropped. An exact duplicate of a live memory is not saved twice, and the agent cannot write back the exact text of a revision a person replaced or removed.
- People with `memory.read` on the agent (or administrators) list and search through `GET /api/agents/{agent}/memories?query=`. With `memory.edit` they `POST` a new memory, `PUT /api/agents/{agent}/memories/{memory}` with `content` and `expected_revision`, and `DELETE` it with `?expected_revision=`; a stale revision returns 409. The console's Memories view, next to Edit agent, uses these.

### Dreaming

[Idle-only dreaming with visible status and results](adr/memory.md#idle-only-dreaming-with-visible-status-and-results)'s idle dreaming, with the agent deciding when to dream ([Agent-centric execution in a sandbox boundary](adr/sandbox.md#agent-centric-execution-in-a-sandbox-boundary)). An agent definition carries `idle_delay_seconds` (60 to 86400, default 600) and an optional `dreaming_model`, a model name on the agent's provider connection; without one the run uses the connection's model ([Default agent model with optional purpose overrides](adr/agents.md#default-agent-model-with-optional-purpose-overrides)). Both are set through `POST /api/agents/{id}/definition` and the console's Edit agent form. `GET /api/agents` and `GET /api/agents/{id}` report `activity`: `working` while a turn runs, `dreaming` while a run's sandbox still holds its credential, `idle`, or the desired state (`sleeping`, `retired`).

- When a pulling agent has no claimable turn, the channel sends `idle` with `dream_after_seconds`. If the agent then has no turn, no unacknowledged event and no drain for that long, it calls `POST /api/runtime/dreams/{run}` with a fresh run id. The orchestrator admits the run, under the agent row lock a turn claim also takes, only when no turn is queued, running or waiting and some memory revision not made by a dream is newer than the last completed or no-op run; otherwise 409. Admission closes an unfinished earlier run as failed and returns the provider, model, key and the 50 most recently changed memories.
- The agent asks the model, without tools, for a JSON plan of `revise` and `forget` changes and a short report (a malformed change is skipped alone; with no usable plan the run fails and its report says why), and sends each change to `POST /api/runtime/dreams/{run}/changes` as a memory change with `expected_revision`. Commits use the turn rules: a stale revision, an exact duplicate or text a person replaced is dropped, so rerunning a dream over changes already made adds nothing. Removal only hides a memory; every revision stays. Each revision a run commits carries its `dream_run_id`.
- Any message on the channel stops the run before its next commit, and an in-flight model request is abandoned. `PUT /api/runtime/dreams/{run}` with `outcome` (`completed`, `yielded`, `failed`) and a report of at most 8 KiB ends it; a completed run with no committed revision is recorded as `no_op`. A run whose sandbox loses its credential is closed as failed by the controller's recovery pass.
- `just docker-dreams` runs three real agents through the Docker backend (same needs as `just docker-sandbox`): a consolidating run with tagged revisions and kept history, admission only after an outside memory change, a yield to a chat message mid-run, the `dreaming_model` override, and a failed run on an unknown model.
- `dream_runs` holds each run's status (`running`, `finished`), start, end, outcome, model and report. People with `memory.read` read the latest 50 runs, each with its committed revisions and the content they replaced, through `GET /api/agents/{agent}/dreams`; the console's Dreams view uses it.

### Skills

[Reusable skills created by humans, agents, and dreaming](adr/memory.md#reusable-skills-created-by-humans-agents-and-dreaming), [Shared installation skill library by default](adr/memory.md#shared-installation-skill-library-by-default) and [Shared skill revisions by any agent or user](adr/memory.md#shared-skill-revisions-by-any-agent-or-user), without imports. `skills` holds the installation's library with each skill's current revision, `skill_revisions` every immutable revision with its author (a person or a dream run), and `skill_installations` the revision each agent uses.

- A package is a JSON object of relative path to text: `SKILL.md` at the root, starting with `---` front matter whose single-line `name` (lowercase words joined by hyphens, at most 64 characters) and `description` (at most 1024 characters, single-line or a YAML `|`/`>` block, read as one line) are required, and other files under `scripts/`, `references/` or `assets/`. Paths are plain segments, none starting with a dot, at most four deep; at most 64 files and 64 KiB in all, no NUL bytes. Storing a package never runs it.
- Any active person lists the library with `GET /api/skills`, reads any revision with `GET /api/skills/{skill}/revisions/{revision}`, publishes with `POST /api/skills` (`files`; 409 when the name is taken) and adds a revision with `PUT /api/skills/{skill}` (`files`, `expected_revision`; 409 when stale, 400 when the name changes). Editing an older or dream-written revision means publishing its content as the next revision.
- With `memory.read` on the agent, `GET /api/agents/{agent}/skills` lists its installations with the library's current revision. With `agent.manage`, `PUT /api/agents/{agent}/skills/{skill}` with `revision` installs or moves an installation, and `DELETE` removes it. A new revision never moves an installation. The console's Skills view, next to Dreams, uses these.
- Each turn's system prompt appends the installed skills' names and descriptions. The agent's `load_skill` tool fetches its installed revision from `GET /api/runtime/skills/{name}`, writes every file as the tool user under `.cubebot-skills/{name}/{revision}/` in the workspace and returns `SKILL.md`, so scripts run through `bash` under the ordinary tool limits. With tools disabled it returns only `SKILL.md`.
- The agent's `skill_list`, `skill_create`, `skill_update` and `skill_install` tools post to `POST /api/runtime/turns/{turn}/skills` while the turn runs. A revision they write names the turn as its author and moves that agent's installation; other agents stay pinned. A turn publishes at most three revisions, a package identical to the current one writes nothing, and a taken name is refused with the existing skill's description.
- `apps/orchestrator/skills/{coding,design}/SKILL.md` ship in the binary. Startup adds each once with `installs_by_default`, and installs it on every existing agent then; new agents get it when created.
- Dream admission also returns the latest 20 completed exchanges, each side cut to 2000 characters, and the first 20 installed packages. The model may propose up to three skills: a new package (`expected_revision` null) or a whole revised package against its installed revision. Each goes to `POST /api/runtime/dreams/{run}/skills`; it is published as a revision tagged with the run and installed for the dreaming agent. A stale revision, an unknown skill or a taken name is dropped, and an invalid package returns 400 without failing the run. `just docker-skills` runs three real agents through the Docker backend (same needs as `just docker-dreams`): a member and an administrator share the library under per-agent grants, one agent loads and runs a skill's script as the tool user and stays pinned until updated, an uninstalled agent and a bystander cannot run it, and a taught procedure is dreamed into a skill installed only for the dreaming agent, which keeps its revision while a member edits it. `GET /api/agents/{agent}/dreams` lists each run's skill revisions with their `SKILL.md` and the one they replaced, and a run that published a skill is not `no_op`.

### Shared files

[Orchestrator-managed file storage on a persistent volume](adr/memory.md#orchestrator-managed-file-storage-on-a-persistent-volume) and [Native Cubebot storage API](adr/memory.md#native-cubebot-storage-api). `CUBEBOT_STORAGE_DIRECTORY`, an absolute path on a volume only this orchestrator mounts (the compose `shared-files` volume; on Kubernetes a `ReadWriteOncePod` PVC), enables them; `CUBEBOT_STORAGE_QUOTA_BYTES` caps stored and in-flight bytes for the installation, 10 GiB by default, and `CUBEBOT_UPLOAD_LIMIT_BYTES` caps one file, unlimited by default (the Helm chart sets 25 MiB); an administrator's values under Platform › General replace both. The quota in force never exceeds 90% of the volume's size, read at start, so the disk cannot fill before uploads are refused. Without the directory every files endpoint answers 503.

- Bytes live under `staging/` while an upload streams in, then are synchronized, hard linked into `blobs/{id}` and the directory synchronized before `blobs` and `files` rows commit. Startup deletes every staged file and every blob without a row, which a crash between the link and the commit leaves, and logs recorded blobs with no bytes; downloads of those answer 500 `integrity_fault`, never empty content.
- `files` is a folder tree owned by one person or one agent, with names unique per folder; `file_shares` grants `read` or `write` on a file and everything under it to a person (by login), a team or an agent (by name). The owner, and people with `workspace.write` on an owning agent, manage shares; `workspace.read` reads an agent's files; administrators read every file. Deletion is explicit and takes a folder's contents with it.
- People: `GET /api/files` (`parent`), `POST /api/files?name=&request_id=&parent=` with the raw bytes as the body (201, or 200 with the earlier file for a reused `request_id`; 409 name taken; 413 `file_too_large` over the upload limit; 507 quota used up), `POST /api/files/folders`, `GET /api/files/shared`, `PATCH /api/files/{file}` (`parent`, `name`; moves stay within the owner's folders), `DELETE /api/files/{file}`, `GET /api/files/{file}/content` (one `Range` gives 206; always an attachment with `nosniff` and a sandbox CSP), and `GET`/`PUT /api/files/{file}/shares` (the whole list). At most 16 transfers run at once; more answer 429.
- Agents: `GET /api/runtime/files` (`parent`, `shared`), `POST /api/runtime/files`, `GET /api/runtime/files/{file}/content` and `POST /api/runtime/files/{file}/shares` (one share), behind the tools `files_list`, `files_put` (a workspace file read as the tool user, the call id as `request_id`), `files_get` (written as the tool user, replacing the file only once complete) and `files_share`.
- The console's Files page lists your files and what is shared with you, uploads by picking or dropping files, downloads, renames, moves by dragging onto a folder or breadcrumb, deletes, and edits shares.

### Backups

[Backups without pauses](adr/packaging.md#backups-without-pauses) and [Cubebot-coordinated backup and restore workflows](adr/packaging.md#cubebot-coordinated-backup-and-restore-workflows); operators start from [deploy/README.md](../deploy/README.md#backup-and-restore).

- **Settings.** `CUBEBOT_BACKUP_ENDPOINT`, `_REGION` (us-east-1), `_BUCKET`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY_FILE` (a file holding the secret), `_SCHEDULE` (`daily` or `off`), `_KEEP_DAILY` (7), `_KEEP_WEEKLY` (4), `_BANDWIDTH_BYTES` (20 MiB a second) and `_CONCURRENCY` (2). An empty variable is unset. A value the deployment sets wins over `backup_settings`, which the console saves; the bucket secret saved there is encrypted with the credential key. A custom endpoint uses path-style addressing, AWS virtual-hosted.
- **Worker.** One task in the active orchestrator checks every minute and runs a backup when the schedule is daily and nothing started in the last day (a failed one, the last hour), or when Back up now asked. A backup a restart interrupted is marked failed at the next start.
- **Bucket.** `blobs/{id}` holds each shared-file blob once. `backups/{id}/` holds `database.dump` (`pg_dump --format=custom` on a snapshot the orchestrator exported, the same one it lists `blobs` in), `workspaces/{agent}.tar` and, written last, `manifest.json`. The id is the UTC start, such as `20261107T030000Z`. A manifest in the bucket means the backup passed verification; one that fails has its manifest deleted, and retention removes its parts. Objects of more than 16 MiB go up as multipart uploads. Every transfer shares one byte rate, and at most the concurrency limit run at once.
- **Workspaces.** The worker inserts a `backup_workspaces` row per agent that is neither stopped nor retired. Each channel delivers `backup` once, and the agent runs `nice -n 19 ionice -c 3 tar --create` in its workspace as the tool user, streaming to `PUT /api/runtime/backups/{backup}/workspace`, which the orchestrator pipes to the bucket (409 when that backup did not ask or already has it). tar's status 1, files changed while read, is accepted. A row still `requested` after ten minutes becomes missing.
- **Retention.** After each verified backup, the newest backup of each of the newest `keep_daily` UTC days and `keep_weekly` Monday-start weeks is kept with the one just made; every other prefix is deleted, manifest first, then each blob no kept manifest names. Their rows become `deleted`.
- **Console.** Administrators: `GET`/`PUT /api/installation/backup` (settings with their sources, history, restored workspaces, key state; 409 on a stale `revision`), `POST /api/installation/backup/run` (202; 409 while one runs; 400 without a bucket) and `POST /api/installation/backup/key`, the credential key in base64 once per installation (409 after; audited as `backup.key_downloaded`).
- **Restore.** `CUBEBOT_RESTORE_BUCKET` with `_ENDPOINT`, `_REGION`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY_FILE` and `_BACKUP` (an id; the newest manifest when empty or `newest`). Before migrations, the orchestrator restores only when `_sqlx_migrations` does not exist yet or `restore.json` is on the shared-file volume. It reads the manifest; refuses a newer schema or migration than its own; opens the manifest's key check with `CUBEBOT_CREDENTIAL_KEY_FILE`; writes `restore.json`; downloads and checks the dump; runs `pg_restore --single-transaction`; fetches each blob it lacks (checked against its SHA-256); marks the restored backup's row with its manifest status; records `workspace_restores`; retires the backed-up installation's process ownership, its Kubernetes anchor and its agent pod and workspace-claim records (pods become `stopped` with proof `restored`; Docker records recover by themselves), since absence there never proves they stopped; then deletes the marker and starts normally. Meanwhile it serves `GET /api/restore` (`state` `restoring` or `failed`, `step`, `done` of `total` files, `error`, `missing`), liveness and readiness, and 503 for anything else; the normal router answers `GET /api/restore` with `state: none`. Each agent calls `GET /api/runtime/workspace/restore` before opening its channel (204 when nothing waits; a tar stream without a length, which ends in an error when its checksum differs), extracts it as the tool user and reports `POST /api/runtime/workspace/restore` with `error`; until that succeeds it retries every five seconds and takes no work.

### Knowledge base

[One knowledge base for the installation, in Markdown](adr/memory.md#one-knowledge-base-for-the-installation-in-markdown).

- People: `GET|POST /api/kb/pages` (the outline without bodies; `request_id`, `parent`, `kind` of `page` or `folder`, `title`, `body`, `icon`), `GET|PATCH|DELETE /api/kb/pages/{id}`, `POST .../place` (`parent`, `after`), `.../restore`, `.../purge`, `GET .../versions`, `.../versions/{revision}`, `POST .../attachments?name=&request_id=` with the raw bytes, `GET /api/kb/search?q=`, `GET /api/kb/trash`, `GET|DELETE /api/kb/attachments/{id}`.
- `PATCH` takes `title`, `icon` (empty removes it), and either `body` with `expected_revision`, or `replace` with `old_text` and `new_text`, the first of which must occur exactly once. A stale `expected_revision` is 409 with the current `revision`.
- Agents: the same under `/api/runtime/kb`, refused with 403 while `agents.knowledge_base` is off, and without `purge`. Tools: `kb_search`, `kb_outline`, `kb_read`, `kb_create`, `kb_edit`, `kb_write`, `kb_move`, `kb_delete`, and with a workspace `kb_attach` and `kb_fetch`.
- The capability is `knowledge_base` on `POST /api/agents/{id}/definition`, and the switch under an agent's About, Capabilities.

### Voice calls

`GET /api/agents/{id}/call` upgrades to the call WebSocket and needs `conversation.send`; a cookie is accepted only from the console's origin. The page sends 16 kHz mono PCM16 as binary frames. The server's binary frames are a 4-byte little-endian sample rate followed by PCM16, and its text frames are JSON with a `kind`: `preparing`, `ready`, `interrupt`, `partial`, `user`, `agent`, `tool`, `queued`, `answered`, `unanswered` and `notice`. A close frame's reason says why a call could not go on.

`GET /api/speech` reads the installation's settings, without any key, and `PUT /api/speech` changes them for administrators. `PUT /api/agents/{id}/speech` sets an agent's overrides and needs `agent.manage`. A call's turns are `chat_turns` rows with `call_id`; `GET /api/conversations/{id}/messages` returns them inside one message whose `call` field is set. Embedded models download into `speech-models` under `CUBEBOT_STORAGE_DIRECTORY`; a call without that directory can only fail on the Silero model, which every provider needs. `just speech-check` runs the embedded models on real audio, and `just call-check` runs a whole call in a browser. See [the decision](adr/console.md#voice-calls-over-the-chat-pipeline).

### Routines

[Routines](adr/agents.md#routines). `routines` holds each agent's routines; every run is a `chat_turns` row with `routine_id`, `origin` (`person`, `agent`, `schedule`, `webhook`) and the routine's `command` copied in, and `routine_hooks` keeps a day of webhook deliveries for replay and the rate window.

- People: with `conversation.read` on the agent, `GET /api/agents/{agent}/routines` and `GET .../routines/{routine}/runs` (the latest 50 runs); with `conversation.send`, `POST /api/agents/{agent}/routines` (`request_id`, `webhook`, `routine`; the response's `secret` is the only time it is shown), `PUT .../routines/{routine}` (`expected_revision`, `routine`; 409 when stale; makes the routine the person's), `DELETE` (cancels its queued and waiting turns), `POST .../secret` (a new secret) and `POST .../runs` (`request_id`; `turn` is null when it coalesced).
- Webhook: `POST /api/hooks/{routine}` with `Authorization: Bearer <secret>`, an optional `Idempotency-Key` of at most 255 bytes and a UTF-8 body of at most 8 KiB: 202 `{"turn":...}`, 200 with the first answer for a repeated key, 401 for a wrong secret, 409 for a disabled routine or retired agent, 413 for a larger body and 429 past 60 a minute.
- Agents: `POST /api/runtime/turns/{turn}/routines` (`call`, `tool`, `input`) behind `routine_create`, `routine_list`, `routine_update`, `routine_delete` and `routine_run`; a refusal is 409 with the reason the model reads. The turn delivery's `command` runs as a journaled `bash` call before the model; with `command_only` its result is the answer.

### Explicit lifecycle controller configuration

Set `CUBEBOT_CONTROLLER_CONFIG` to a local JSON file and configure `CUBEBOT_DATABASE_URL`. Supply `CUBEBOT_POD_NAMESPACE`, `CUBEBOT_POD_NAME` and `CUBEBOT_POD_UID` from the orchestrator Pod's Downward API metadata. The observed Pod must have one regular container named `orchestrator`, RestartAlways, a dedicated service account and no ephemeral containers. The ownership proof covers that container; init containers must not run independent orchestrator instances.

```json
{
  "connection": { "kind": "in_cluster" },
  "sandbox_image": "registry.example/cubebot-sandbox@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "runtime_service_account": "cubebot-runtime",
  "orchestrator_origin": "https://cubebot.example",
  "network": { "dns": ["10.96.0.10"] },
  "runtime": { "kind": "kvm" }
}
```

`runtime` is required and installation-wide: `{"kind":"kvm"}` or `{"kind":"container","class":"<RuntimeClass>"}`, where `class` is optional and must name a RuntimeClass the cluster administrator installed; the class's overhead is the only pod change its admission may add. `sandbox_image` names the sandbox image for `kvm` and the agent image for `container`. A sandbox refuses a workspace volume the other runtime laid out (`workspace.ext4` under `container`, a `runtime/` directory under `kvm`) and exits with status 78, which the agent's status reports as `RuntimeLayoutMismatch`; there is no conversion.

`network` is required; supply one to three resolver IPs. Pods use `dnsPolicy: None` with exactly those resolvers, so use fully qualified hostnames for cluster services. Egress control is pod-level NetworkPolicy, which governs exactly one agent. In `kvm`, sandbox pods carry `devices.kubevirt.io/kvm` and `devices.kubevirt.io/tun` resource limits, so each gets `/dev/kvm` and `/dev/net/tun` from KubeVirt's (or a compatible) device plugin, and run the sandbox as root with only `NET_ADMIN`, which needs a privileged Pod Security namespace. Configurations that still set the removed `backend` or `qualified` fields are refused. The guest's root image and kernel come from the sandbox image, its workspace disk is a file on the workspace PVC, and the projected token reaches the guest only over vsock. In `container`, pods run `cubebot-agent container` with no device resources, as root with only `SETUID`, `SETGID` and `CHOWN`, which baseline Pod Security admits, and a writable root filesystem; the workspace PVC is mounted at `/var/lib/cubebot`, so the workspace, journal and browser profile have the guest's paths, and the projected token is read from its mounted file. The desktop's host channel is `cubebot-agent desktop` instead of `cubebot-sandbox desktop`.

Replace the example image digest with the built sandbox image. For an explicitly selected kubeconfig, replace `connection` with `{"kind":"kubeconfig","path":"/trusted/kubeconfig","context":"cubebot"}`. The service never discovers the default context. Kubernetes transport requires certificate-verified HTTPS, with literal loopback HTTP allowed for local controlled workflows. The orchestrator origin supplied to agents requires HTTPS.

Optional `computer_use_enabled` (with `terminal_enabled`) sets `CUBEBOT_COMPUTER_ENABLED` in every sandbox ([Desktop as a VMM device](adr/sandbox.md#desktop-as-a-vmm-device)): the sandbox's init starts the desktop, and the agent offers the provider's own computer-use tool, served by the sandbox's screen arbiter. It is installation-wide, and the provider rejects that tool for models without computer use, so set it only with a model that has it, such as OpenAI `gpt-5.5` or a current Claude model.

For an orchestrator endpoint signed by a private CA, set optional `control_ca_secret` to a Secret in the installation namespace with a `ca.crt` PEM bundle. The compiler mounts only that key, read-only, in the sandbox container and sets `CUBEBOT_CONTROL_CA_FILE`, so the same Secret may hold the listener's `tls.key`. Public roots remain trusted; certificate and hostname checks remain enabled. A missing key blocks Pod startup; an unreadable, empty, malformed or oversized bundle blocks runtime startup. The maximum bundle size is 64 KiB. Trust is loaded at runtime process startup, so replace Pods to apply CA changes.

The orchestrator serves agents on a second, TLS-only listener when `CUBEBOT_CONTROL_BIND_ADDR`, `CUBEBOT_CONTROL_TLS_CERT_FILE` and `CUBEBOT_CONTROL_TLS_KEY_FILE` are set together; it serves the same routes as `CUBEBOT_BIND_ADDR`, which keeps serving `/api/runtime` for agents started before. The Helm chart points `orchestrator_origin` at it, `https://orchestrator-control.<namespace>.svc.<cluster domain>:8443`, so agents never pass through the public ingress.

Optional `sandbox_resources`, `{"requests": {...}, "limits": {...}}` over `cpu`, `memory` and `ephemeral-storage`, replaces those defaults for every sandbox container (requests 100m, 256Mi, 64Mi; limits 2, 3Gi, 1Gi; a `kvm` sandbox requests 2304Mi, its guest's 2 GiB plus the VMM, so Kubernetes never places more guests on a node than its memory holds); other keys, malformed quantities and a request above its limit are refused at start. A changed value drains and replaces running agents, as any pod change does.

The controller scans durable agent intent in keyset batches of 32 and waits five seconds after each full scan. It checks process ownership before each reconciliation and bounds each attempt to sixty seconds. HTTP handling proceeds concurrently. Shutdown stops admission, settles handlers and the current reconciliation, then releases ownership. Ownership-check failure stops both loops and retains the claim. Agent drain and physical termination rules still control whether a replacement Pod is allowed.

Without controller configuration, database-only development mode holds the same exclusion lock and a durable development claim. A clean stop permits later controller activation. An unclean development exit retains the claim because there is no Kubernetes container proof for that local process; automatic takeover is deliberately unavailable. Once Kubernetes ownership has been established, omitting controller configuration is refused. Liveness-only mode without a database remains available.

### Authentication resource limits

The orchestrator permits at most four concurrent Argon2 computations across password hashing and verification. Additional work receives HTTP 429 with `Retry-After: 1`; it does not enter an unbounded hashing queue. The permit stays with the blocking computation if its HTTP caller disconnects.

Each active account has a persisted budget of ten password-verification attempts per 60-second window. Login reserves against that account; password-bearing command replay reserves against the command's actor. Successful and failed attempts both count, including a reservation followed by a busy hash worker. Invitation replay and login share the member's budget, so replay is not an alternate unlimited password-checking path. Exhaustion returns the generic unauthorized response until the window resets. Restart does not clear the budget, and existing sessions remain usable.

### Teams and human permissions

Administrators manage local access teams through `GET/POST /api/identity/teams`, `POST /api/identity/teams/membership` and `POST /api/identity/teams/delete`. Team creation accepts `request_id` and `name`; membership changes accept `request_id`, `team`, `account_id`, `expected_revision` and `present`. Deletion accepts `request_id`, `team` and `expected_revision`. Listing returns at most 100 records; use the last team's ID as `?after=<id>` for the next page. Deleting a team disables its access while preserving its records. Suspended accounts can be removed from teams, but cannot be added.

`POST /api/identity/access/grants` accepts `request_id`, a `recipient` object with `kind` of `user` or `team` and its `id`, a `scope` object with `kind` of `agent`, `room` or `conversation` and its `id`, and a named `capability`. Supported capabilities are `agent_manage`, `conversation_read`, `conversation_send`, `memory_read`, `memory_edit`, `workspace_read`, `workspace_write`, `browser_view`, `browser_control` and `room_manage`. Conversation capabilities accept room/conversation scope; room management accepts room scope; the remaining capabilities accept agent scope. These are exact grants with no implied read/edit/control hierarchy. `POST /api/identity/access/revoke` accepts `request_id`, grant `id` and `expected_revision`.

`POST /api/identity/access/explain` accepts `scope` and `capability` and explains the authenticated user's current access, including direct and team grant sources. Administrators receive these defined permissions through their installation role. Ordinary membership grants no private-resource access, and an agent manager gains no unrelated content or grant-administration authority. Team/grant management is administrator-only initially. Agent and text-conversation handlers check resource existence and content access.

Team/grant, suspension and revocation mutation responses include an ID and revision. Their `request_id` is scoped to the authenticated actor and command kind: retries return the recorded receipt, while changed request content returns a conflict. `GET /api/identity/commands/<kind>/<request_id>` reads the caller's receipt, with current administrator authorization. Administrator command kinds are `account.create`, `account.suspend`, `invitation.create`, `invitation.revoke`, `team.create`, `team.membership`, `team.delete`, `access.grant`, `access.revoke` and `oidc.revoke`. These receipts survive restart. Password-bearing commands keep a separate Argon2 verifier to reject changed-password retries without storing a fast password digest. Password verification runs outside database transactions. Administrator receipt retrieval never returns that verifier.

`GET /api/identity/access/events?after=<sequence>` returns up to 100 administrator-visible mutation records, including the actor, affected resource, revision and non-secret request. Publication is serialized through transaction commit so a cursor cannot skip a lower event that commits late. Account/invitation events include only non-secret metadata; passwords, invitation tokens and password verifiers are excluded from their audit payloads.

`GET /api/health/ready` checks the configured database and exists only in database-enabled mode. It does not attest to agent, Kubernetes or provider readiness.

```sh
just integration
```

This builds the orchestrator/operator binaries, starts an isolated disposable PostgreSQL 18 container with a generated password and temporary host-backed data directory, runs real database/HTTP tests, signed local OIDC issuer workflows and process restarts, then removes that container and its test data. It never uses `just db-up`'s server or an installation's. Migrations run once into a `cubebot_template_<hash>` database; each test copies it with `CREATE DATABASE ... TEMPLATE`. Tests run in parallel, one process per test, because password hashing limits concurrent work per process. Ordinary `cargo test` explicitly reports the database cases as ignored; `just integration` runs them and fails if Docker or PostgreSQL is unavailable.

### Docker sandboxes without a cluster

Set `CUBEBOT_DOCKER_CONFIG` to a JSON file instead of `CUBEBOT_CONTROLLER_CONFIG`:

```json
{
  "image": "cubebot-sandbox:dev",
  "orchestrator_origin": "https://cubebot.example",
  "runtime": { "kind": "kvm" }
}
```

`runtime` works as in the controller configuration, with `class` naming a Docker runtime (`docker run --runtime`); `image` is the agent image for `container`. Optional `terminal_enabled` works as in the controller configuration. Optional `network` names an existing Docker network for the containers, instead of the default bridge. Optional `control_ca_file` is an absolute host path to a PEM bundle the guest trusts for `orchestrator_origin`; it is bind-mounted read-only into each container, which sets `CUBEBOT_CONTROL_CA_FILE`. The containers run as root without `CAP_DAC_OVERRIDE`, so the file must be world-readable. In `kvm` the Docker host must be x86_64 Linux with `/dev/kvm` and `/dev/net/tun`; each container gets both devices and runs as root in group 10001 with only `NET_ADMIN`. In `container` any Docker host serves, Docker Desktop on a Mac included; each container runs `cubebot-agent container` as root with only `SETUID`, `SETGID` and `CHOWN`, a `/tmp` tmpfs, 1 GiB of shared memory, 3 GiB of memory and 1024 processes. A container that refused its volume stays the agent's attempt, with its reason, until a restart. The controller runs under development ownership and serves the runtime API. Each running agent gets one retained volume (`cubebot-workspace-<agent>`) and one container per epoch (`cubebot-agent-<agent>-<epoch>`) through the local `docker` CLI. Containers are recorded as pod attempts in namespace `docker`, so sessions, drains, epochs and restart generations behave as on Kubernetes: a crashed or stale container is stopped and its final state retained before a new epoch starts, and a running agent is drained before it is stopped.

`deploy/cubebot` creates one network for an installation's sandboxes, `cubebot-sandboxes` by default, with inter-container traffic off and `cubebot uninstall` removing it, so sandboxes cannot reach each other or Cubebot's other containers directly and reach the orchestrator only at its control address. OrbStack does not enforce the inter-container rule, so there they can still reach each other. **Private addresses stay reachable from Docker sandboxes:** this machine's LAN, its other published ports and cloud metadata at `169.254.169.254`. Docker has no portable way to block them, as Docker Desktop has no host firewall to add a rule to; on Linux a `DOCKER-USER` rule of your own can. The Helm chart's NetworkPolicy does block them. A KVM guest cannot use Docker's embedded resolver on this network: it gets the sandbox's non-loopback resolvers, which there are none of, so `1.1.1.1` and `8.8.8.8`, and names only your own DNS server knows do not resolve in it.

Each container gets a fresh bootstrap token in `CUBEBOT_BOOTSTRAP_TOKEN`, passed through the `docker` CLI's environment rather than its arguments; Docker keeps it in the container's configuration until the container is removed. The orchestrator stores only its SHA-256 digest. The token logs in only while that container's attempt is bound and observed running. `orchestrator_origin` must be HTTPS and not loopback: the sandbox sits on the container's own network, where the host's loopback is unreachable, and host networking would hand the host's interface to the guest. On Docker Desktop, `host.docker.internal` reaches the host's loopback.

The orchestrator serves HTTPS on `CUBEBOT_BIND_ADDR` when both `CUBEBOT_TLS_CERT_FILE` and `CUBEBOT_TLS_KEY_FILE` name PEM files; setting only one is a startup error. On an x86_64 Linux server with `/dev/kvm`, Docker, OpenSSL and the sandbox image built as above, three commands run an agent:

```sh
just db-up
just docker-orchestrator
CUBEBOT_BOOTSTRAP_LOGIN=admin CUBEBOT_BOOTSTRAP_PASSWORD=... OPENAI_API_KEY_FILE=... just docker-agent "My agent"
```

`just docker-orchestrator` first runs `just dev-ca`, which makes a self-signed control CA and a certificate for the `docker0` address in `.cubebot/dev-ca`, and makes either again when it has under 30 days left or the address changes; a new certificate keeps a CA that is still good. It then serves HTTPS on `docker0:8443` with a generated credential key and `.cubebot/docker.json`, which sets `terminal_enabled` so agents can run tools. Containers reach it over the default bridge; a host firewall must accept TCP 8443 from `docker0`. `just docker-agent` bootstraps the administrator and the OpenAI provider the first time, then creates and wakes an agent and prints its ID. The web development server proxies to `http://127.0.0.1:8080` and does not reach this orchestrator. `just docker-sandbox` checks the same path end to end on a disposable database: one agent boots through Docker and runs one bash tool call.

Every `docker-*` suite takes `CUBEBOT_SANDBOX_RUNTIME=kvm|container` (default: `kvm` where `/dev/kvm` exists, else `container`); `kvm` skips off x86_64 Linux, and every suite needs `OPENAI_API_KEY_FILE`. The nightly workflow runs them in `container` on GitHub's runners when the provider secret exists. `just container-check`, which runs on every push, needs only Docker: one agent boots in `container` against a scripted provider listening in the sandbox's own network at the loopback origin the agent's `CUBEBOT_TEST_PROVIDER_ORIGIN` seam accepts (the Docker launcher forwards the orchestrator's value), runs one bash call, and through the host channel the wallpaper shows and a person's key is refused until they take control, then reaches the tool user's display. On a Mac the orchestrator listens on loopback and sandboxes reach it as `host.docker.internal`; `just dev-ca DIRECTORY NAMES` takes the certificate's subject alternative names.
