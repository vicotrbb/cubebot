# Status

Updated 2026-11-04. This page lists what runs and what has not been qualified. [ARCHITECTURE](../ARCHITECTURE.md) describes the intended system; [the reference](development/reference.md) documents current configuration and APIs.

## What runs

- Built-in sign-in/out, accounts, invitations, teams, scoped grants and optional OpenID Connect.
- Authorized agent creation, editing and lifecycle intent, with Kubernetes reconciliation when a controller is configured. Agents are always on ([Agent idle lifecycle](adr/agents.md#agent-idle-lifecycle) as amended 2026-11-03): a new agent's sandbox starts at creation, an agent idle past its delay with nothing queued, waiting or delegated reads as `sleeping` while it keeps running, and only a person's `stop` stops the sandbox. `idle_policy` is accepted and has no effect.
- Encrypted OpenAI, Anthropic or OpenRouter API-key/model configuration and one permanent text conversation per agent, served by the native Rust runtime through the website. Agents use one provider at a time; Platform › AI providers shows each one's state and keeps the keys of those not in use. The OpenRouter adapter (`modules/providers/src/openrouter.rs`, Chat Completions) is tested against a scripted server following its documentation, including one turn by a real agent in `just container-check`. It has not yet run against OpenRouter with a real key.
- Built-in tools (`bash`, file, `glob`, `grep`) and an MCP client for stdio and Streamable HTTP servers, disabled by default, run by the agent inside its sandbox as a configured tool user, with parallel calls. See [tool execution](development/bounded-terminal.md). MCP servers are installation configuration managed in the console (Platform › MCP servers, `/api/mcp-servers`), shared with every agent by default or granted per agent on its Connections tab; environment variables and headers are stored encrypted and reach the agent with each turn. MCP tools have no per-tool grants yet.
- Two declared sandbox runtimes ([In-house VMM as the agent sandbox](adr/sandbox.md#in-house-vmm-as-the-agent-sandbox) as amended 2026-11-02), set per installation by the required `runtime` field of the controller and Docker configurations and shown on the console's Platform health view: `kvm`, where `cubebot-sandbox run` boots each agent in a KVM guest, and `container`, where the agent image runs directly as `cubebot-agent container`, optionally under a RuntimeClass or Docker runtime. Both are launched as one container per agent by the Kubernetes controller or, without a cluster, through Docker. On an x86_64 Linux host with `/dev/kvm` the `kvm` sandbox also runs directly, inside a network namespace of its own. A sandbox refuses a workspace volume the other runtime laid out, which the agent's status reports as `RuntimeLayoutMismatch`.
- Per-agent memory in PostgreSQL with full-text search: the agent's `search_memory`, `remember` and `forget` tools, turn-end extraction staged with the turn, revision history with source turns, and console search and editing guarded by `expected_revision`. See [memory](development/reference.md#memory).
- Idle dreaming: after the agent's idle delay with no turn and every event acknowledged, the agent asks its dreaming model (or the connection's model) to consolidate its 50 most recently changed memories, and commits the changes one at a time against their revisions. Any channel message makes the run yield before its next commit. Runs, their outcome, report and committed revisions are listed in the console's Dreams view; the agent's activity shows working, dreaming, idle or sleeping. See [dreaming](development/reference.md#dreaming).
- Skills ([Reusable skills created by humans, agents, and dreaming](adr/memory.md#reusable-skills-created-by-humans-agents-and-dreaming), [Shared installation skill library by default](adr/memory.md#shared-installation-skill-library-by-default) and [Shared skill revisions by any agent or user](adr/memory.md#shared-skill-revisions-by-any-agent-or-user)): an installation-wide library in PostgreSQL of text packages (`SKILL.md` plus `scripts/`, `references/` and `assets/` files) with immutable revisions, published and revised by any active person against `expected_revision`, and per-agent installations pinned to a revision. The turn's system prompt lists installed skills; the agent's `load_skill` tool writes the installed revision into the workspace as the tool user and returns its instructions. A dream may publish a new or revised skill from its latest 20 turns, installed for that agent and shown in its report. See [skills](development/reference.md#skills).
- Rooms and agent-to-agent work ([Agent execution lanes](adr/agents.md#agent-execution-lanes), [Direct mentions and a tool-free room coordinator](adr/rooms.md#direct-mentions-and-a-tool-free-room-coordinator), [Independent assignments for multiple room mentions](adr/rooms.md#independent-assignments-for-multiple-room-mentions), [Explicit agent messaging and delegation](adr/rooms.md#explicit-agent-messaging-and-delegation), [Queued messages with explicit steering](adr/rooms.md#queued-messages-with-explicit-steering), [Cancel selected work and its descendants](adr/rooms.md#cancel-selected-work-and-its-descendants) and [Contain delegated failures and let the parent adapt](adr/rooms.md#contain-delegated-failures-and-let-the-parent-adapt)): administrators create rooms of agents, and administrators or `room.manage` holders change their members. A message's `@name` mentions deliver one turn per mentioned member, carrying the room's recent messages and replies as context; unmentioned messages go to a tool-free coordinator call that picks one owner, continues an open task of the room as steering, asks a question or does nothing. Agents learn their own name and the agents they share a room with, and use `delegate` and `send_message`. A delegating parent yields and resumes each time a child settles, with every outcome so far, failed and cancelled ones with evidence; it cannot send the same task to the same agent twice, or more than 16 tasks. A `send_message` that expects a reply has the answer relayed back once. Delegated tasks run in task lanes beside the main lane, two by default, with their own context and no desktop control. Steering targets one turn, enters its context before the next model request and is copied to its open delegated descendants. Cancel stops the turn's whole subtree. The console shows rooms live over server-sent events, each turn's origin, delegated work, steering state and each tool's name, and edits room members and an agent's task lanes. See [rooms and delegation](development/reference.md#rooms-delegation-and-steering). `just integration` covers these with the real agent binary and a scripted model. ## Code behind the accepted design

[Agent-centric execution in a sandbox boundary](adr/sandbox.md#agent-centric-execution-in-a-sandbox-boundary) replaces per-turn grants and invocation leases with coarse agent authority, and [In-house VMM as the agent sandbox](adr/sandbox.md#in-house-vmm-as-the-agent-sandbox) makes Cubebot's own KVM VMM the strong sandbox runtime beside a declared `container` runtime (amended 2026-11-02). The tool container, network initializer and kernel egress baseline are gone; the agent runs its tools itself. Runtime control is one authenticated WebSocket per sandbox, with an agent credential that lasts for the sandbox incarnation; per-turn grants, terminal leases and journal custody are gone. The sandbox boots a guest from a read-only root disk with a workspace disk, virtio-net on a tap redirected to the pod interface, and a vsock control channel that carries the agent's configuration in and liveness out (see the [sandbox](../apps/sandbox/README.md)). `just guest-boot` checks in CI, against a stand-in orchestrator in a network namespace, that the guest agent reaches it from the pod address, reports liveness and keeps its journal across a restart. The orchestrator launches sandboxes as root with only `NET_ADMIN`, `/dev/kvm` and `/dev/net/tun`, which needs a privileged Pod Security namespace, and the sandbox image always carries the guest; CI builds that image only in its guest job. `just cluster-sandbox` covers [Agent-centric execution in a sandbox boundary](adr/sandbox.md#agent-centric-execution-in-a-sandbox-boundary)'s sandbox scenarios in kind, with a generic device plugin and a fixture NetworkPolicy. On 2026-10-29 it passed on an x86_64 AMD host with `/dev/kvm`, kind running inside a privileged pod: an agent ran turns against OpenAI `gpt-4.1-mini` inside KVM guests, and all six scenarios passed. Those are: the agent runs in the guest, not its pod; the guest reaches its gateway but not another sandbox, PostgreSQL or the Kubernetes API, the API probe included, under kindnet; a running command survives an orchestrator SIGKILL and commits once; stopping the agent ends its VM; a revoked credential loses work delivery and ledger writes; and a sandbox lost mid-task resumes from its journal without repeating its committed effect ([evidence](development/evidence/2026-10-29-cluster-sandbox.json); its `source` fingerprint `d2ea1ee5…` is the committed tree before this page and the evidence file were added, and its `base_commit` names the runner's own snapshot commit). That run's `just guest-boot` skipped only the bare-host refusal check, which cannot trip inside a pod. This is one kind run, not a qualified isolation boundary on a production CNI. The nightly workflow now runs `cluster-admission`, `cluster-startup`, `cluster-chat` and `cluster-sandbox` on a GitHub-hosted x86_64 runner with `/dev/kvm`, every one with guest-built images; it has not run there yet.

## Not yet qualified

Agent system

- Computer use: the console desktop view is measured on one host, not across a network or under load; a long `type` holds the arbiter, and every viewer's frames, for about 10 ms a character, and a busy guest can still drop a burst of input; person input is logged only by the arbiter, not in `desktop_sessions`; a drag shows no motion until release; no mobile touch input; no pointer in screenshots, US keyboard layout only, and no per-agent setting. OpenAI safety checks on computer calls are neither acknowledged nor surfaced. Anthropic computer use is tested only against a stand-in provider. In the passing run the model retyped the URL several times before answering; why the first attempts did not take is unmeasured. Login handoffs: one pending per agent; the turn ends only because the tool tells the model to; a request made while a person already holds control refuses nothing until they take control again; the banner polls every 3 s; nothing times out an unanswered request; and the person sees only the reason, not which turn asked.
- Integrations, event sources other than routine webhooks, notifications, PWA/push and token streaming are not implemented. Responses commit as complete messages.
- Rooms and delegation: a delegated child that is interrupted waits for a person like any turn, and a child's provider outage fails it rather than waiting; each settled child costs its parent another model run; a small model with a long conversation history can claim to have delegated without calling the tool (the real-agent check uses a fresh agent for each delegation it needs); nothing stops a parent from delegating a differently worded copy of open work, beyond the 16-task cap; task lanes share the workspace and `main` browser session without coordination; installation-wide capacity and provider concurrency limits ([Agent execution lanes](adr/agents.md#agent-execution-lanes)) are not enforced; the room stream polls the ledger once a second per open room. Loop prevention is the four-ancestor and 16-task limits and relays that expect no reply.
- Memory is lexical only: no embeddings or hybrid retrieval ([Hybrid memory retrieval](adr/memory.md#hybrid-memory-retrieval)), dreaming exercised on real agents only by `just docker-dreams` on the Docker backend (not on a cluster, and quality, cost and yield latency unmeasured), no dream usage accounting, no wake of a sleeping agent to dream, and a dream sees only its 50 most recently changed memories; suppression of content a person replaced or removed only for exact text, so a paraphrase can bring it back ([Direct memory editing and conversational correction](adr/memory.md#direct-memory-editing-and-conversational-correction)), and no console view of revision history. Extraction runs one extra model request after every completed turn; its quality, cost and duplicate rate are unmeasured.
- Skills: no imports ([File and Git imports with Agent Skills compatibility](adr/memory.md#file-and-git-imports-with-agent-skills-compatibility)), no agent-created skills during ordinary turns, no binary files, single-line front matter only, no library paging, search or removal, and no idempotent retry of a publish whose response was lost. `just docker-skills` exercised skills on three real agents through the Docker backend with gpt-4.1-mini on 2026-10-30 (not on a cluster): load and script run as the tool user, pinning, update, uninstall, a bystander denied, and a dream that wrote a skill (on the second lesson in one run). Whether dream-written skills help later work is unmeasured.
- Shared files: one passing `docker-files` run, not repeated; no load, full-disk, database-outage or orchestrator-replacement test; the fsync and hard-link sequence is unqualified on any CSI driver; the chart's `ReadWriteOncePod` volume ran only under kind's test CSI driver; no paging, versions, resumable uploads or revocation of a download already streaming; over HTTP/1 a refused upload is read out only up to 64 MiB or 30 seconds, so a larger one's client sees a reset instead of 507; blobs are not part of a backup procedure yet ([Cubebot-coordinated backup and restore workflows](adr/packaging.md#cubebot-coordinated-backup-and-restore-workflows)).
- Console: no token streaming or per-turn usage display; no console view of memory revision history, grant listing per agent (the Access tab works from the audit events) or search over messages; the Playwright harnesses, the floating desktop preview and the dark theme are unverified on a KVM host with real agents; SSR renders only the sign-in page, the app shell renders in the browser; the service worker caches hashed assets only.
- Room content workflows and event streaming are not implemented.
- Tool-journal crash-window behavior on CSI is unqualified. Each channel polls PostgreSQL once a second, and each open browser conversation stream (`GET /api/conversations/{id}/events`) twice a second; delivery latency and database load at scale are unmeasured.

Kubernetes and isolation

- Real-cluster qualification of lifecycle, fencing and active-work drain is pending. Kubernetes boundary tests are local API-contract tests, not proof of physical fencing.
- Mount, credential, network and fencing qualification remain installation prerequisites. CNI/CSI, DNS, grants, browsers and arbitrary-tool isolation (G1–G3) are pending.
- NetworkPolicy enforcement on guest traffic has passed only under kind's kindnet in one `just cluster-sandbox` run; it is not qualified on a production CNI.
- Connected-cluster operation with a private control CA is unqualified; only local TLS tests exist.
- Database-only development mode is not production recovery qualification.
- The Docker backend with a `just dev-ca` control CA in `kvm` is checked only by the local `just docker-sandbox`. It passed once on 2026-10-30 on an x86_64 AMD host with `/dev/kvm`, with Docker running inside a privileged pod: one agent booted in a KVM guest, authenticated over HTTPS to the `docker0` address, and ran one bash tool call against OpenAI `gpt-4.1-mini`.
- The `container` runtime is checked on every push by `just container-check`, against a scripted provider, not a model: one agent boots, runs one bash call, and through the host channel the wallpaper shows and a person's key is refused until they take control, then reaches the tool user's display. - `just cluster-admission` creates no running agent or workspace; CSI, CNI and full lifecycle qualification are pending.

Identity and security

- Re-admitting a revoked OIDC subject is unavailable. Invitation token delivery is manual. There is no remote authentication-management UI.
