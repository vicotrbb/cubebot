# Status

Updated 2026-10-30. This page lists what runs and what has not been qualified. [ARCHITECTURE](../ARCHITECTURE.md) describes the intended system; [the reference](development/reference.md) documents current configuration and APIs.

## What runs

- Built-in sign-in/out, accounts, invitations, teams, scoped grants and optional OpenID Connect.
- Authorized agent creation, editing and lifecycle intent, with Kubernetes reconciliation when a controller is configured.
- Encrypted OpenAI API-key/model configuration and one permanent text conversation per agent, served by the native Rust runtime through the website.
- Built-in tools (`bash`, file, `glob`, `grep`) and an MCP client for stdio and Streamable HTTP servers, disabled by default, run by the agent inside its sandbox as a configured tool user, with parallel calls. See [tool execution](development/bounded-terminal.md). MCP tools have no per-tool grants yet.
- `cubebot-sandbox run`, which boots each agent in a KVM guest, launched as one container per agent by the Kubernetes controller or, without a cluster, through Docker. On an x86_64 Linux host with `/dev/kvm` it also runs directly, inside a network namespace of its own. The development `process` backend was removed on 2026-10-29: there is no way to run an agent outside a guest, and the sandbox image does not build without the guest.
- Per-agent memory in PostgreSQL with full-text search: the agent's `search_memory`, `remember` and `forget` tools, turn-end extraction staged with the turn, revision history with source turns, and console search and editing guarded by `expected_revision`. See [memory](development/reference.md#memory).
- Idle dreaming: after the agent's idle delay with no turn and every event acknowledged, the agent asks its dreaming model (or the connection's model) to consolidate its 50 most recently changed memories, and commits the changes one at a time against their revisions. Any channel message makes the run yield before its next commit. Runs, their outcome, report and committed revisions are listed in the console's Dreams view; the agent's activity shows working, dreaming, idle or sleeping. See [dreaming](development/reference.md#dreaming).
- Skills (ADRs 0055 to 0057): an installation-wide library in PostgreSQL of text packages (`SKILL.md` plus `scripts/`, `references/` and `assets/` files) with immutable revisions, published and revised by any active person against `expected_revision`, and per-agent installations pinned to a revision. The turn's system prompt lists installed skills; the agent's `load_skill` tool writes the installed revision into the workspace as the tool user and returns its instructions. A dream may publish a new or revised skill from its latest 20 turns, installed for that agent and shown in its report. See [skills](development/reference.md#skills).
- Rooms and agent-to-agent work (ADRs 0005, 0014 to 0016, 0071 to 0073): administrators create rooms of agents, and administrators or `room.manage` holders change their members. A message's `@name` mentions deliver one turn per mentioned member, carrying the room's recent messages and replies as context; unmentioned messages go to a tool-free coordinator call that picks one owner, continues an open task of the room as steering, asks a question or does nothing. Agents learn their own name and the agents they share a room with, and use `delegate` and `send_message`. A delegating parent yields and resumes each time a child settles, with every outcome so far, failed and cancelled ones with evidence; it cannot send the same task to the same agent twice, or more than 16 tasks. A `send_message` that expects a reply has the answer relayed back once. Delegated tasks run in task lanes beside the main lane, two by default, with their own context and no desktop control. Steering targets one turn, enters its context before the next model request and is copied to its open delegated descendants. Cancel stops the turn's whole subtree. The console shows rooms live over server-sent events, each turn's origin, delegated work, steering state and each tool's name, and edits room members and an agent's task lanes. See [rooms and delegation](development/reference.md#rooms-delegation-and-steering). `just integration` covers these with the real agent binary and a scripted model. On 2026-10-31 `just docker-rooms` ran them on three real `gpt-4.1-mini` agents through Docker on the homelab x86_64 KVM host, with the console checked in Chromium: mentions and a deduplicated retry, the coordinator choosing the shell-running agent and doing nothing for chatter, room context reaching a delivery, the room stream, a delegation run in a task lane and resumed, steering followed after a tool call, steering copied to a running task, a relayed reply with no echo, two of three tasks running at once with the third queued, a cancelled child and a cancelled root stopping their commands, the coordinator continuing an open task, and membership changes scoped to `room.manage`. The runs found and fixed: agents did not know their own names, so a mention read as a message about someone else; a resumed parent re-delegated its whole request each time a child settled (29 tasks for 3), now refused and capped; a cancel delivered before the turn ended made the channel announce idleness early, so the agent would never dream; and every tool showed as "Terminal"
- Operator revocation of an agent's runtime credential with `cubebot-admin revoke-runtime`.
- Computer use (ADR 0085), off unless the controller configuration sets `computer_use_enabled`: guest init starts Xorg, openbox, xterm and Chromium as the tool user on the virtio-gpu display, and the agent offers the provider's own computer tool (Anthropic `computer_toolset_20260801`, OpenAI `computer`). The sandbox's screen arbiter serves screenshots as PNG and turns the agent's requests on vsock port 1025, and the orchestrator's on the host channel (`cubebot-sandbox desktop` through exec), into keyboard and tablet input, with modes `agent`, `watch` and `human` and each event logged with its source and, for the agent, its tool call id. Screenshots are `screenshot` tool outcomes in the ledger; console views and replays to the agent leave the image out. `just guest-boot` checks the host channel's screenshot against the pattern the guest drew, a person's input refused until that person takes control, and agent input refused with "a person has control". On 2026-10-30 `just cluster-sandbox`'s computer-use scenario passed alone in a fresh kind cluster on the homelab x86_64 host with OpenAI `gpt-5.5`: the model navigated Chromium to example.com in 8 calls with 8 screenshots and 2 clicks and answered "Example Domain", and every call's id appeared in the arbiter's log. The full `just cluster-sandbox` run that day passed its first two scenarios and then hit the known "command started" stall in the orchestrator-restart scenario before reaching it. A person watches it from the agent's Desktop tab in the console: the orchestrator's `GET /api/agents/{id}/desktop` WebSocket, which needs `browser.view` and, to take control, `browser.control`, proxies the host channel, where the arbiter sends each connection the 64x64 PNG tiles that changed since its last frame, at most every 50 ms, with the pointer and who last moved it. Only the person holding control changes the mode, a host channel that closes hands back the control taken through it, and after a hand-back the arbiter refuses agent input until the agent takes a screenshot. `desktop_sessions` records the viewer, start, end and each take and hand-back; the transcript marks the agent's first screenshot after a hand-back. The page shows the input round trip and screen update rate. On 2026-10-30 `just docker-desktop` passed on the homelab x86_64 KVM host with OpenAI `gpt-5.5` and the built console behind Caddy: an administrator, a viewer with `browser.view`, a controller with `browser.view` and `browser.control`, and an outsider; no credential 401, no grant 403, another agent's desktop 403, a stopped agent 409, and a cookie only with the console's origin. The first frame matched a screenshot; the viewer could neither take control nor send input; the controller's typed URL and click, and the console's in Chromium, reached the guest's Chromium; the agent's input was refused while the controller held control, and the model was told; after the hand-back the agent looked again before its click went through, and the transcript marked that screenshot; a dropped connection, a sign-out and a revoked grant each ended control or the session within the 30 s recheck; and `desktop_sessions` held every session and control change, while neither it nor the orchestrator's log held a frame. Measured there on one host: input round trip through the orchestrator to the arbiter 0.4 ms median (0.5 ms p95) from a direct client and 22 ms median as the console page reports it through Caddy; a keystroke to the frame showing it 50 ms median (51 ms p95), bounded by the 50 ms frame interval; 20 frames a second; a first frame of 87 KiB in 63 ms. Getting there found and fixed two faults: a typed string over about a dozen characters was lost, because the arbiter sent all its key events at once and the guest's evdev buffer of 64 dropped them (it now sends 8 events per 10 ms); the agent's OpenAI requests carried only a refused call's screenshot, so the model answered with empty text and the turn stalled the conversation (the refusal now follows as a note). Runs with the old host channel relay, which used `io::copy` between its socket and stdout, never delivered the orchestrator's first frame, but a direct probe of it did, so the cause is unproven; the relay now forwards each read as it arrives and every later run got frames. At boot X's keyboard focus is not on Chromium, so typing takes a click first. With computer use on, the agent also has [browser tools](development/bounded-terminal.md#browser-tools) over Chromium's DevTools protocol: navigate, read the accessibility tree, click, type and page screenshots, in a `main` session in the workspace profile or named task sessions in browser contexts of their own. On 2026-10-30 `just docker-browser` passed on the homelab x86_64 KVM host with OpenAI `gpt-5.5` and two agents, every check read from a server the guest's Chromium called, the ledger, the arbiter's log or the host's frame: a form filled and submitted through navigate, read, type and click in `main`, each input call preceded by an arbiter mode query and no read; the host's frame and a `browser.view` viewer's frame through the orchestrator showing the page; an unreachable URL and an unknown element failing with the browser's reason; a page screenshot's PNG in the ledger and not in the conversation view; a task session keeping its own cookie, never sending `main`'s and leaving `main`'s page in place; a closed task session refused until navigated again, then without its cookies; two task sessions navigated in parallel in one turn; navigation refused with "a person has control" and never reaching the site while a person held the desktop, reads still working, and going through after the hand-back; and a `main` cookie surviving a sandbox restart, waited 40 s after being set since Chromium writes cookies on a 30 s timer. The first run found that a read after `browser_close` silently opened a new page; only `browser_navigate` opens a session now. After the restart the model twice answered a navigation request from earlier results without calling the tool; the test asks once more when a turn makes no call. Browser input after a hand-back does not yet require a new observation, as the computer tool's does.

Evidence: [text chat](development/text-chat-mvp.md), [cluster admission](development/cluster-admission.md), [cluster startup](development/cluster-startup.md), [layout verification](development/layout-verification.md).

## Code behind the accepted design

[ADR 0083](adr/0083-agent-centric-execution-in-a-sandbox-boundary.md) replaces per-turn grants and invocation leases with coarse agent authority, and [ADR 0084](adr/0084-in-house-vmm-as-the-agent-sandbox.md) makes Cubebot's own KVM VMM the sandbox. The tool container, network initializer and kernel egress baseline are gone; the agent runs its tools itself. Runtime control is one authenticated WebSocket per sandbox, with an agent credential that lasts for the sandbox incarnation; per-turn grants, terminal leases and journal custody are gone. The sandbox boots a guest from a read-only root disk with a workspace disk, virtio-net on a tap redirected to the pod interface, and a vsock control channel that carries the agent's configuration in and liveness out (see the [sandbox](../apps/sandbox/README.md)). `just guest-boot` checks in CI, against a stand-in orchestrator in a network namespace, that the guest agent reaches it from the pod address, reports liveness and keeps its journal across a restart. The orchestrator launches sandboxes as root with only `NET_ADMIN`, `/dev/kvm` and `/dev/net/tun`, which needs a privileged Pod Security namespace, and the sandbox image always carries the guest; CI builds that image only in its guest job. `just cluster-sandbox` covers ADR 0083's sandbox scenarios in kind, with a generic device plugin and a fixture NetworkPolicy. On 2026-10-29 it passed on an x86_64 AMD host with `/dev/kvm`, kind running inside a privileged pod: an agent ran turns against OpenAI `gpt-4.1-mini` inside KVM guests, and all six scenarios passed. Those are: the agent runs in the guest, not its pod; the guest reaches its gateway but not another sandbox, PostgreSQL or the Kubernetes API, the API probe included, under kindnet; a running command survives an orchestrator SIGKILL and commits once; stopping the agent ends its VM; a revoked credential loses work delivery and ledger writes; and a sandbox lost mid-task resumes from its journal without repeating its committed effect ([evidence](development/evidence/2026-10-29-cluster-sandbox.json); its `source` fingerprint `d2ea1ee5…` is the committed tree before this page and the evidence file were added, and its `base_commit` names the runner's own snapshot commit). That run's `just guest-boot` skipped only the bare-host refusal check, which cannot trip inside a pod. This is one kind run, not a qualified isolation boundary on a production CNI. The nightly workflow now runs `cluster-admission`, `cluster-startup`, `cluster-chat` and `cluster-sandbox` on a GitHub-hosted x86_64 runner with `/dev/kvm`, every one with guest-built images; it has not run there yet.

## Not yet qualified

Agent system

- Computer use: the console desktop view is measured on one host, not across a network or under load, and the console lists only agents a person manages (`agent.manage`), so someone with only `browser.view` or `browser.control` cannot reach the Desktop tab; a long `type` holds the arbiter, and every viewer's frames, for about 10 ms a character, and a busy guest can still drop a burst of input; person input is logged only by the arbiter, not in `desktop_sessions`; a drag shows no motion until release; no mobile touch input; no pointer in screenshots, US keyboard layout only, and no per-agent setting. OpenAI safety checks on computer calls are neither acknowledged nor surfaced. Anthropic computer use is tested only against a stand-in provider. In the passing run the model retyped the URL several times before answering; why the first attempts did not take is unmeasured.
- Integrations, triggers, notifications, PWA/push and token streaming are not implemented. Responses commit as complete messages.
- Rooms and delegation: a delegated child that is interrupted waits for a person like any turn, and a child's provider outage fails it rather than waiting; each settled child costs its parent another model run; a small model with a long conversation history can claim to have delegated without calling the tool (the real-agent check uses a fresh agent for each delegation it needs); nothing stops a parent from delegating a differently worded copy of open work, beyond the 16-task cap; task lanes share the workspace and `main` browser session without coordination; installation-wide capacity and provider concurrency limits (ADR 0005) are not enforced; the room stream polls the ledger once a second per open room. Loop prevention is the four-ancestor and 16-task limits and relays that expect no reply.
- Memory is lexical only: no embeddings or hybrid retrieval (ADR 0022), dreaming exercised on real agents only by `just docker-dreams` on the Docker backend (not on a cluster, and quality, cost and yield latency unmeasured), no dream usage accounting, no wake of a sleeping agent to dream, and a dream sees only its 50 most recently changed memories; suppression of content a person replaced or removed only for exact text, so a paraphrase can bring it back (ADR 0026), and no console view of revision history. Extraction runs one extra model request after every completed turn; its quality, cost and duplicate rate are unmeasured.
- Skills: no imports (ADR 0058), no agent-created skills during ordinary turns, no binary files, single-line front matter only, no library paging, search or removal, and no idempotent retry of a publish whose response was lost. `just docker-skills` exercised skills on three real agents through the Docker backend with gpt-4.1-mini on 2026-10-30 (not on a cluster): load and script run as the tool user, pinning, update, uninstall, a bystander denied, and a dream that wrote a skill (on the second lesson in one run). Whether dream-written skills help later work is unmeasured.
- Room content workflows and event streaming are not implemented.
- Tool-journal crash-window behavior on CSI is unqualified. Each channel polls PostgreSQL once a second, and each open browser conversation stream (`GET /api/conversations/{id}/events`) twice a second; delivery latency and database load at scale are unmeasured.

Kubernetes and isolation

- Real-cluster qualification of lifecycle, fencing and active-work drain is pending. Kubernetes boundary tests are local API-contract tests, not proof of physical fencing.
- Mount, credential, network and fencing qualification remain installation prerequisites. CNI/CSI, DNS, grants, browsers and arbitrary-tool isolation (G1–G3) are pending.
- NetworkPolicy enforcement on guest traffic has passed only under kind's kindnet in one `just cluster-sandbox` run; it is not qualified on a production CNI.
- Connected-cluster operation with a private control CA is unqualified; only local TLS tests exist.
- Database-only development mode is not production recovery qualification.
- The Docker backend with a `just dev-ca` control CA is checked only by the local `just docker-sandbox`. It passed once on 2026-10-30 on an x86_64 AMD host with `/dev/kvm`, with Docker running inside a privileged pod: one agent booted in a KVM guest, authenticated over HTTPS to the `docker0` address, and ran one bash tool call against OpenAI `gpt-4.1-mini`. It is not in CI.
- `just cluster-admission` creates no running agent or workspace; CSI, CNI and full lifecycle qualification are pending.

Identity and security

- OIDC is tested only with a controlled signed issuer. No external identity-provider compatibility or production security qualification is claimed.
- Authentication rate and concurrency limits need broader load and security qualification.
- Re-admitting a revoked OIDC subject is unavailable. Invitation token delivery is manual. There is no remote authentication-management UI.

Packaging and operations

- Helm packaging does not exist yet.
- Production PostgreSQL image digests and pgvector are unqualified; the development image follows PostgreSQL 18.
- The frontend's Nitro Bun adapter is a prerelease dependency. Bun SSR and static assets are smoke-tested; production hosting is unqualified.
- Container image builds are unqualified. The 2026-10-25 retry was blocked by Docker running out of disk space.
- Security, fencing and scale (ADR 0061: 100 registered, 25 working agents) require the [qualification plan](design/qualification.md).
