### Account and invitation command reconciliation

Added actor/kind/request receipts to account creation, suspension, invitation issuance and revocation. Suspension/revocation require expected revisions, and replay returns the recorded revision without repeating the mutation. Password-bearing requests retain a separate Argon2 verifier and store only non-secret metadata in command digests/audit payloads. Changed passwords conflict even when the public request metadata is identical. Argon2 work occurs outside database transactions; replay rechecks activity and administrator authority as appropriate.

Invitation redemption now records its request identity and account outcome. Only the original request with its original password proof may replay, and current expiry/revocation/account activity still apply. A competing request cannot create another account. The post-lock fresh-clock expiry check remains in the flow. Administrator account/invitation listings expose current status and revisions with bounded ID cursors, excluding credential material.

Ruling: invitation tokens remain non-recoverable authentication secrets. Issuance retries return the same invitation ID/revision and no token, rather than persisting recoverable token plaintext. If an issuing response is lost, the administrator inspects/revokes that record and issues a fresh command. This preserves one-time disclosure and a reviewable recovery path without introducing credential encryption for a secret that need not be recoverable.

Updated all existing callers to require mutation request IDs/revisions; no legacy mutation API without those fields remains. Login and logout retain their authentication/session semantics. Red checks observed missing request-aware signatures and account listing; real PostgreSQL tests subsequently passed concurrency/reconnect replay, changed-secret conflicts, original redemption identity, suspended-account rejection and absence of secrets/verifiers from audit JSON. ### Authentication resource controls

Added a shared four-slot semaphore for all Argon2 hashing/verification. Admission is immediate; saturation returns Busy/HTTP 429 with Retry-After 1 and no-store. The permit moves into the blocking CPU closure and remains held even if the awaiting request is cancelled. No new hashing worker service, dependency or queue was introduced.

Added an atomic PostgreSQL reservation of ten password-verification attempts per active account per 60-second window. Login and secret-bearing command replay use the same reservation. Successful and unsuccessful proofs count; a reservation also counts if subsequent Argon2 admission is busy. Exhaustion returns the same unauthorized shape as other credential denial. Account activity is checked at reservation and after verification; existing sessions remain independent of a temporary verification budget. Session expiry/issuance use fresh wall-clock evaluation.

Ruling: apply the verification budget to command replay as well as sign-in. Otherwise a known used invitation and its request identity would form an alternate password-checking oracle outside the login budget. The account is the login subject for login, the administrator for account-creation replay, and the admitted member for invitation-redemption replay. Normal bearer-authenticated resource operations do not consume this password budget.

Tests observed missing Busy/capacity APIs before implementation. Real PostgreSQL checks cover concurrent reservations, reconnect persistence and window reset. A replay-bypass regression was tested with the production guard temporarily removed: it failed because the original password still passed after ten incorrect replay proofs. The guard was restored and the full integration workflow passed, including actual HTTP quota exhaustion and restart. Independent source review found no actionable correctness/security issues; it did not independently rerun the tests. Final quality/smoke metrics follow below.

Milestone 1 remains open for optional OIDC and full acceptance, and subsequent agent/content APIs must still enforce their domain resource checks. No general denial-of-service, cluster, provider, recovery or scale qualification is inferred from these controls.

### Optional OIDC and browser identity

Added the Rust OpenID Connect authorization-code/PKCE adapter, trusted local installation configuration, signed issuer/subject bindings, exact-subject or verified-email-domain admission with member baseline, and explicit linking from a recent still-valid platform session. State is one-time and browser-bound; only hashes of state and the cookie-held PKCE verifier enter PostgreSQL. Flow expiry is checked after the row lock. Provider role claims and matching email never merge or elevate accounts. No provider calls occur at startup.

Browser cookies use the same identity/authorization boundary as bearer clients, with exact-origin CSRF checks for unsafe cookie requests. HTTPS session and flow cookies use host prefixes, Secure and Path=/. Provider calls have deadlines, redirect rejection, body limits and a shared concurrency bound. Configuration revisions invalidate pending flows and OIDC sessions when changed or disabled. Built-in sessions stay independent. Administrator binding inspection/revocation uses bounded pagination, optimistic revisions and durable request receipts; revocation tombstones bindings and deletes OIDC-derived sessions.

The controlled issuer uses real RSA signatures, rotating JWKS, PKCE verification and confidential-client authentication. Initial end-to-end run passed browser binding, token rejection, replay, key rotation, admission, explicit linking, logout, CSRF, persistence across process restart and disabled-policy invalidation. Expanded revocation and verified-domain/userinfo cases and final gates are in progress; results follow after execution. A temporary test ordering error reused a session after intentionally revoking it; the workflow now keeps that verification independent.

Independent review identified sibling-domain flow-cookie injection; host-prefixed HTTPS flow cookies fixed it. Review confirmed that fix and found no further blocking security issues. Its lock-order concern was also addressed: linking locks the account before locking/revalidating the session, matching suspension/revocation order. No external issuer, real frontend login, agent, Kubernetes, recovery or scale qualification is claimed. Milestone 1 remains open pending its final acceptance audit; all later milestones remain pending.

Final OIDC slice verification: `just integration` passed 28 Rust cases and both actual-process identity/OIDC workflows.
