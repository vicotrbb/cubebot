### Authentication resource controls

Added a shared four-slot semaphore for all Argon2 hashing/verification. Admission is immediate; saturation returns Busy/HTTP 429 with Retry-After 1 and no-store. The permit moves into the blocking CPU closure and remains held even if the awaiting request is cancelled. No new hashing worker service, dependency or queue was introduced.

Added an atomic PostgreSQL reservation of ten password-verification attempts per active account per 60-second window. Login and secret-bearing command replay use the same reservation. Successful and unsuccessful proofs count; a reservation also counts if subsequent Argon2 admission is busy. Exhaustion returns the same unauthorized shape as other credential denial. Account activity is checked at reservation and after verification; existing sessions remain independent of a temporary verification budget. Session expiry/issuance use fresh wall-clock evaluation.

Ruling: apply the verification budget to command replay as well as sign-in. Otherwise a known used invitation and its request identity would form an alternate password-checking oracle outside the login budget. The account is the login subject for login, the administrator for account-creation replay, and the admitted member for invitation-redemption replay. Normal bearer-authenticated resource operations do not consume this password budget.

Tests observed missing Busy/capacity APIs before implementation. Real PostgreSQL checks cover concurrent reservations, reconnect persistence and window reset. A replay-bypass regression was tested with the production guard temporarily removed: it failed because the original password still passed after ten incorrect replay proofs. The guard was restored and the full integration workflow passed, including actual HTTP quota exhaustion and restart. Independent source review found no actionable correctness/security issues; it did not independently rerun the tests. Final quality/smoke metrics follow below.

### Private runtime recovery journal

Added an agent-owned binary journal under a dedicated private directory, outside tool mounts. Immutable record files and one checksummed atomic checkpoint retain opaque execution evidence without a second mutable platform database. The runtime loop, record schemas, central reconciliation endpoint and authenticated drain are still pending; this module grants no execution authority and is not activated by the placeholder runtime entry point.

Append writes and synchronizes a private temporary record, renames and synchronizes the directory, then publishes and synchronizes the committed high-water checkpoint before returning. Acknowledgement publishes the central acknowledgement high-water mark before removing records. Sequence numbers remain monotonic after all records are acknowledged. Recovery validates every unacknowledged committed record before cleanup; missing, truncated, altered or incorrectly attributed evidence fails closed. Only uncommitted files beyond the durable checkpoint, recognized temporary files and centrally acknowledged records can be removed. Unknown files are rejected. A missing checkpoint with an existing stable lock file cannot silently initialize a fresh journal; interrupted first initialization requires repair rather than guessing whether sequence history existed.

Failed mutating I/O poisons the instance, requiring recovery before another append or acknowledgement. Callers must stop starting actions when durable journaling fails.

### Native runtime identity and drain control loop

The client validates non-nil identities, positive epoch/version, a correctly shaped runtime credential and a lifetime from 1 through 120 seconds. Renewal requires the same agent/attempt/epoch and an increasing session version. Authenticated control responses must exactly match the issued actor and valid disposition/request combinations. Existing locked dependency versions were reused; no provider SDK, custom networking layer or new service was introduced.
