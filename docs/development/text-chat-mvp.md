# Minimal text chat

This implementation is limited to built-in browser sign-in/out, authorized agent creation/editing/listing, one installation OpenAI API-key/model connection, and durable text conversations. The existing identity, grants, lifecycle ownership and Kubernetes reconciliation remain the foundations. Tools, rooms, delegation, knowledge systems, integrations, triggers, PWA/push and scale qualification are outside this implementation.

## Local setup

Run the existing PostgreSQL/bootstrap workflow in README. Export `CUBEBOT_DATABASE_URL`, `CUBEBOT_PUBLIC_ORIGIN` matching the exact website origin, and `CUBEBOT_CREDENTIAL_KEY_FILE` pointing to a separately protected file containing exactly 32 random raw bytes. The file must have no group/other permissions. Missing or incorrect keys do not trigger plaintext storage or automatic replacement. A projected Kubernetes Secret can supply the file with mode 0400. Retain this key separately from database backups. Automated key rotation is outside this MVP; retain version 1 for these records.

The orchestrator reads this configuration at startup. It never serves the key to a human or runtime. API keys entered into the administrator website are encrypted with AES-256-GCM and a fresh nonce before persistence. Ciphertext is bound to installation, connection, format/key version and configuration revision. Normal read endpoints return only model, revision and access policy. A wrong installation key prevents overwriting an existing encrypted connection.

Start `just dev-api` and `just dev-web`. The development frontend forwards `/api` through Nitro's native route rules. Production requires the existing same-origin ingress routing to the orchestrator; the frontend build does not embed a local development proxy or provider key.

A configured lifecycle controller is needed to provision real agent pods. Text-chat pods reuse the fixed runtime image, identity, private persistent journal mount and guarded lifecycle. They omit tool processes, tool mounts, browser storage and the privileged tool-network initializer. Existing retained two-container attempts remain recognized for terminal recovery. No external cluster is configured or deployed by this implementation.

Use an available OpenAI Responses API model ID. The adapter sends explicit text context with `store: false`, no tools and a 2,048 output-token bound. It requests a complete response, then commits it atomically; token streaming is not part of this MVP. Provider errors and incomplete/invalid responses become visible waiting states. Configuration is installation-managed and defaults to all eligible agents. API clients may instead submit `access: {"mode":"explicit_grants","agents":[...]}` to restrict the connection. Omitted access during edits preserves the existing policy. No model or account fallback occurs.

## Durable API behavior

- Every agent has one permanent conversation with the same identity. It exists as soon as the agent exists. `GET /api/agents/{id}/conversation` returns its metadata after checking content access. There is no conversation-creation or conversation-list API. Agent management does not implicitly authorize its shared transcript.
- `GET /api/conversations/{id}/messages?after=<sequence>` pages the one retained history in order. Missing and inaccessible conversations return the same 404 response. Different explicitly authorized participants read and send into that same history.
- `POST /api/conversations/{id}/messages` takes `request_id` and `message`. Human authority is rechecked, the message and agent wake intent commit together, and only then does HTTP 202 acknowledge acceptance. Matching retries return the accepted turn; changed input conflicts. Accepted messages are never removed by provider failures.
- `POST /api/conversations/{id}/messages/{turn}/retry` takes a new `request_id`. It requeues the same accepted waiting turn, records the retry durably and never creates another human message. Replaying a retry returns the same turn and cannot restart a later run. A committed response cannot be retried or replaced.
- `GET/POST /api/provider` requires a current administrator. Updates take `request_id`, `expected_revision`, `provider` (`openai` by default, or `anthropic`), `model`, `context_window` (tokens; required for OpenAI, reported by Anthropic's Models API when omitted), `api_key` and optional `access`. Receipts contain no recoverable secret. The installation key is supplied through operator configuration, not this API.

Text input is limited to 16 KiB, replies to 32 KiB, and each history page to 100 turns. Context is managed within that one conversation. The agent assembles it from instructions, the current message, and at most twelve complete earlier exchanges within a 128 KiB history budget. Older history remains persisted and readable even when it is outside inference context. There is no summarization or long-term memory.

## Runtime control and recovery

The agent receives turns and reports their events over the [runtime channel](reference.md#runtime-channel). One turn runs per agent. Waiting failures hold later queued turns until the failed turn is retried or cancelled. Queued, running, waiting, cancelled and committed states are visible in history. Selecting an agent opens its only chat directly. The browser preserves a pending send's request ID and draft in account-scoped session storage until acknowledgement, so a refresh or failed response does not silently create a fresh send.

The native adapters for OpenAI Responses and Anthropic Messages stream over SSE with a 120-second stall deadline, no total deadline or output cap, a 16 MiB bound per stream event, no redirects, no proxy discovery and no automatic network retries. The ledger bounds one encoded turn event at 8 MiB. The agent retries an explicit HTTP 429 or 5xx response, or a provider-reported overload before any text has streamed, up to four attempts in total on the same model. It waits for `retry-after` when the provider sends one and otherwise backs off 1, 2 and 4 seconds, with jitter; a requested wait over 60 seconds goes straight to waiting. Each turn carries the latest compaction summary and every completed exchange after it. Once provider-reported tokens reach 80% of the model window, the agent summarizes with the same model at the next safe point, records the summary as a `summary` turn event and continues from the summary and the current request. Ambiguous network failures, authentication rejection and invalid responses go to waiting without an automatic second request. An external provider may have processed an interrupted request even when no response was received. An explicit retry can spend again, while Cubebot still commits at most one response for the accepted turn. No claim of exactly-once provider billing, full cluster fencing qualification, security certification or scale qualification is made.

Final gates passed: `just check`, `just integration` and `just smoke`. The complexity gate passed with maximum 15; no first-party exclusions or threshold changes were added. `just check` includes the two Bun frontend boundary/pagination tests. ## Single-conversation correction

ADR 0082 replaces the initial prototype's multiple-conversation model. The picker and new-conversation action were removed. Existing messages/results are migrated to the agent's permanent conversation in sequence order. Former IDs retain migration provenance and resolve old message references to the permanent conversation after current authorization checks. Separate legacy audiences are not combined into a broader grant: their old grants are revoked for administrator review. A prior initiator keeps access only if that person already saw every source history. The new permanent conversation never resets on refresh, agent edits, sleep or restart.

Correction validation passed: `just check`, `just integration`, `just smoke`, and four focused PostgreSQL chat tests. The focused tests cover singleton identity before opening, concurrent openings, reconnect, authorized shared access, management without content access, interleaved legacy-history migration with source provenance, denied legacy audiences, and idempotent retries through former conversation IDs. Complexity remains at maximum 15. The existing local preview was migrated in place after a private backup; browser inspection confirmed the original exchange remains visible without a conversation picker. No additional credential-backed provider call was made for this correction; the earlier live-provider evidence above remains separate from controlled-provider recovery tests.
