# Sandbox and isolation

These decisions cover where an agent's work runs and what bounds it: one sandbox per agent as the trust boundary, Cubebot's own KVM virtual machine monitor and the declared `kvm` and `container` runtimes, and the desktop inside the sandbox. They also cover what the agent may do inside that boundary: install software, reach the network, and use a browser with separate sessions, reused logins, live viewing and human takeover.

## Agent-centric execution in a sandbox boundary

Accepted 2026-10-27. Amended 2026-10-28: the sandbox is a guest of Cubebot's own VMM rather than a VM-class Kubernetes RuntimeClass. Amended 2026-11-02: the sandbox is the installation's declared runtime, a `kvm` guest or the agent image as a `container`.

**Decision.** The agent owns its execution and runs inside one sandbox per agent. The user selected this model on 2026-10-27.

- **The agent owns** its loop, context assembly and compaction, memory behavior, tools and recovery journal. It decides when to call a model, which tool to run, what to remember and what to retrieve.
- **The orchestrator is ledger and switchboard only.** As ledger it durably records what humans and recovery need: agent definitions, conversations, messages, results, memory records, usage and audit. As switchboard it authenticates agents and people, routes messages and work to agents, enforces content permissions, owns provider credential refresh and starts and stops sandboxes. It does not run turns, schedule lanes, authorize individual tool calls or decide memory policy.
- **One sandbox per agent.** Each running agent gets one sandbox in the installation's declared runtime (see [In-house VMM as the agent sandbox](#in-house-vmm-as-the-agent-sandbox)): a `cubebot-sandbox` KVM guest, or the agent image run directly as a container under [Standard containers with optional sandbox runtimes](#standard-containers-with-optional-sandbox-runtimes), optionally on a RuntimeClass. The runtime, terminal, browser, local MCP servers and agent-installed software run together inside it. The sandbox edge is the trust boundary; isolation between the runtime and its own tools is not. Only the KVM guest is a VM-class boundary; a container runtime is reported as a container and never as a VM. Standard container runtimes remain usable for the orchestrator.
- **Coarse, long-lived authority.** A sandbox receives one agent-scoped credential for its lifetime, plus the provider credentials that agent is eligible for. There are no per-turn inference grants, invocation leases or renewal windows. Revocation means revoking that credential or stopping the sandbox.

Usage: a person sends a message. The orchestrator records it, checks the sender's content access and wakes or notifies the agent. The agent pulls the message, works through its own loop for as long as it needs, calls the provider directly and runs commands or a browser inside its sandbox. It writes results, memory changes and usage back to the ledger through idempotent operations. Stopping the agent stops the sandbox.

What remains from earlier decisions: agents still never connect to PostgreSQL ([Agent state access through the orchestrator](agents.md#agent-state-access-through-the-orchestrator)). Provider inference stays direct ([Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication)), and the orchestrator still owns refresh ([Orchestrator-owned provider authentication refresh](identity.md#orchestrator-owned-provider-authentication-refresh)). Content permissions, [one permanent conversation](agents.md#one-permanent-conversation-per-agent), [installation-managed connections](identity.md#installation-wide-connection-access-by-default) and [explicit deletion](memory.md#retain-durable-data-until-explicitly-deleted) are unchanged. [Lanes](agents.md#agent-execution-lanes) become a scheduling rule inside the agent loop rather than an orchestrator admission rule.

This decision replaced parts of other decisions:

- [Agent state access through the orchestrator](agents.md#agent-state-access-through-the-orchestrator): orchestrator modules owning agent memory policy and execution leases for reporting. The interface remains the only path to platform state.
- [Bounded continuation during disconnection](agents.md#bounded-continuation-during-disconnection): finite per-turn authorization windows and the ban on starting queued work while disconnected. Disconnection now limits only what needs the switchboard.
- [Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication): per-turn, versioned inference grants. Provider material is propagated per sandbox lifetime.
- The separate runtime and tool containers in one pod, and credential separation between them (see What changed).

Still in force from the container layout this replaced: restarts must reconcile active tool invocations and runtime records before replaying work. A runtime restart does not prove a command stopped, and a tool failure does not prove an external action failed. Persistent files survive according to the workspace contract; process and browser state are not promised to survive sandbox replacement. The workspace remains shared across the agent's lanes, with no per-task sandbox, workspace isolation or additional agent identity, and workspace content is untrusted input. Do not load executable runtime code from the writable agent workspace.

Consequences: the tool runner, network initializer, kernel egress filter, root supervisor and per-turn grant and lease protocol are removal candidates once the sandbox path is qualified (the VMM decision removes the tool container, network initializer, in-pod egress baseline and two-container recovery checks). A `kvm` installation must provide nodes that expose `/dev/kvm` to the sandbox pod, which rules out some managed clusters without nested virtualization; those run the `container` runtime with the weaker boundary declared. Agents hold their provider keys for longer, so rotation and revocation must actually work. A compromised sandbox can spend that agent's provider budget and act as that agent until its credential is revoked. Budget limits ([Shared goal budgets with optional cost limits](agents.md#shared-goal-budgets-with-optional-cost-limits)) are checked from ledger usage reports, not enforced per call.

**Rationale.** The first implementation split one agent's work across the orchestrator and two containers. The orchestrator granted each turn, leased each tool invocation and renewed short authority windows. The runtime and tool runner shared a pod network, so credential separation needed UID-aware kernel filtering, a privileged network initializer and a root supervisor. Every new agent capability had to cross that machinery, and most engineering effort went into the control plane instead of the agent. Any credential inside the sandbox is reachable by code the agent runs there, so splitting authority per turn inside it bought little real security for a lot of protocol. Giving each agent only its own authority bounds the damage of a compromised sandbox to that agent. A VM boundary contains hostile code better than containers sharing a kernel and pod network, and pod-level NetworkPolicy now applies to exactly one agent.

Alternatives considered: keep per-turn grants inside a VM sandbox, which keeps the protocol cost without a matching security gain. Run without a sandbox and rely on containers, which leaves hostile tool code sharing a kernel with the platform (since 2026-11-02 this is offered only as the declared, weaker `container` runtime). Proxy all inference through the orchestrator, which [Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication) already rejected.

**What changed.** This decision superseded the earlier layout (accepted 2026-10-23) that separated the trusted Rust runtime and tool execution into two containers within each agent pod. There, the runtime container owned the model/tool loop, orchestrator communication, provider calls, provider credentials and recovery state; a tool container ran terminal commands, browser workloads, agent-directed programs and local third-party MCP subprocesses, reached the workspace, and executed authorized requests from the runtime through an authenticated tool-execution interface. Provider credentials, the runtime's platform identity and recovery journals were to be kept out of the tool container's mounts, environments, logs and results, and shared process namespaces avoided. Because the containers shared a pod network, the interface could not trust localhost and enforcement within the pod network stayed open. Its alternatives were a single container with internal process isolation, or separate runtime and tool pods with independent networking. Its platform references were [Kubernetes pod networking](https://kubernetes.io/docs/concepts/workloads/pods/#pod-networking) and [restricting a Secret to one container](https://kubernetes.io/docs/concepts/configuration/secret/#use-case-secret-visible-to-one-container-in-a-pod). All of that is replaced: the runtime and its tools run together in one sandbox, the trust boundary is the sandbox edge, and credential separation between runtime and tools is no longer a goal. Its open details (tool-execution transport and authentication, security contexts, network enforcement in the shared pod network) are dropped with it; workspace mounts, images, resource allocation, browser sessions, background processes and restart reconciliation carry into this decision's open details. Its validation scenarios that a command runs only in the tool container, that runtime secrets and journals are inaccessible from that command, that a tool cannot impersonate the runtime to the orchestrator and that unauthorized local requests are rejected are replaced by the sandbox-edge scenarios below; its scenarios for workspace persistence across replacement, lane limits and restart during a tool invocation carry over.

The sandbox mechanism changed twice. As accepted, each agent got a VM-class Kubernetes RuntimeClass such as Kata Containers. On 2026-10-28 [In-house VMM as the agent sandbox](#in-house-vmm-as-the-agent-sandbox) replaced that with a `cubebot-sandbox` VM. On 2026-11-02 its amendment made the runtime a declared installation setting, `kvm` or `container`.

**Open details.** Credential lifetime and rotation; the revocation path when the orchestrator is unavailable; the ledger write contract and idempotency keys; which sandbox configurations are qualified; sandbox image and persistent workspace layout; resource allocation; background process management; how the agent loop schedules concurrent lanes; local development without a cluster.

**Validation scenarios.** A sandbox runs its agent in a `cubebot-sandbox` VM under the `kvm` runtime, and as the agent image under the `container` runtime, reported as a container; a command in the sandbox cannot reach another agent's sandbox, the orchestrator database or the Kubernetes API; revoking the agent credential stops ledger writes and provider refresh; stopping the agent terminates the sandbox; a long task continues through an orchestrator restart and reconciles results without duplicates; a sandbox lost mid-task resumes from its journal and the ledger without repeating committed effects; workspace changes persist across replacement; concurrent lanes obey existing limits; restart during a tool invocation does not blindly repeat its effects.

## In-house VMM as the agent sandbox

Accepted 2026-10-28. Amended 2026-10-29: the development `process` backend is removed. Amended 2026-10-30: guest sizing is 2 vCPUs and 2 GiB by default. Amended 2026-11-02: one agent image with declared runtimes, `kvm` or `container`.

**Decision.** Cubebot ships its own thin KVM virtual machine monitor as a fourth application, `apps/sandbox`, built as the `cubebot-sandbox` binary. It is Rust, drives KVM through ioctls using the `libc` and `nix` crates already in the dependency graph, and uses no VMM crates (no rust-vmm, Firecracker or Cloud Hypervisor components). The user selected this on 2026-10-28. Since 2026-11-02 it is one of two declared runtimes: one agent image, declared runtimes, no undeclared or misreported one.

- **Declared runtimes.** An installation sets one runtime at install, `kvm` or `container`, as a required `runtime` setting. `kvm` is this VMM, still the strong runtime wherever `/dev/kvm` exists. `container` runs the same agent image directly as a container (`cubebot-agent container`), optionally under an administrator's RuntimeClass or Docker runtime as [Standard containers with optional sandbox runtimes](#standard-containers-with-optional-sandbox-runtimes) describes; it has the same desktop, workspace layout, tools and recovery, but does not contain a kernel exploit from software the agent installed. No runtime is inferred, defaulted or reported stronger than it is: the installation API reports the runtime and the console shows it, never calling a container a virtual machine. A sandbox refuses a workspace volume the other runtime laid out, and the agent's status says so; there is no conversion. That choice was made on 2026-11-01.
- **KVM only, every boot.** `cubebot-sandbox run` boots the guest on x86_64 Linux with `/dev/kvm` and refuses to run anywhere else. Every `kvm` sandbox boots a KVM guest, and the sandbox image always carries the guest kernel and root image.
- **One container per agent.** On Kubernetes the `kvm` agent pod runs one container, `cubebot-sandbox`, with access to `/dev/kvm`. The agent runs inside the guest VM, not in the container.
- **Guest devices.** The guest gets virtio-blk disks for a read-only root image and the agent's workspace, virtio-net backed by a tap device inside the pod's network namespace, virtio-vsock for control between the sandbox process and the guest, and a serial console whose output becomes the container log. The desktop runs inside the guest and adds no VMM devices ([Desktop as a VMM device](#desktop-as-a-vmm-device)).
- **Sizing.** The sandbox runs one thread per vCPU and boots with 2 vCPUs and 2 GiB by default, each configurable up to the VMM's limits.
- **Network policy still applies.** Guest traffic leaves through the tap device in the pod network namespace, so pod-level NetworkPolicy governs exactly one agent, as [Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary) requires.
- **The orchestrator sees one interface.** A `Sandbox` interface with create, start, stop, exec channel, workspace and status operations hides where sandboxes run. Kubernetes (one pod and one workspace PVC per agent) and Docker (cluster-less) implement it; both launch `cubebot-sandbox run` in `kvm` and the agent image in `container`.
- **Docker sandboxes are attempts too.** Each Docker container is recorded as a pod attempt with its own epoch, so sessions, drains and recovery rules match Kubernetes. Without a Kubernetes service-account token, each container receives a random bootstrap token minted by the orchestrator, which stores only its digest; the token logs in only while that container is the agent's current running attempt.

Usage: an administrator configures the sandbox image (the `kvm` image is `cubebot-sandbox`; the `container` image is the agent image). The orchestrator creates the agent's workspace and starts its sandbox. On a KVM node `cubebot-sandbox` boots the guest, attaches the workspace disk and tap device, and relays the guest serial console to the container log. Stopping the agent stops the container, which ends the VM.

This amends only the sandbox mechanism of [Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary); its ownership, authority and ledger rules are unchanged. [Standard containers with optional sandbox runtimes](#standard-containers-with-optional-sandbox-runtimes) holds as written for the `container` runtime. A cluster may still schedule a `kvm` sandbox pod on any runtime that exposes `/dev/kvm`. Durable attempt records and the rule that an uncertain effect is never blindly replayed remain in force.

Consequences: the separate tool container, privileged network initializer, in-pod kernel egress baseline and two-container recovery checks are removed; the agent runs its tools in its own sandbox. Cubebot owns VMM code, so the guest-facing device emulation is the attack surface to review and fuzz. The sandbox needs `unsafe` for ioctls and guest memory; it is confined to `apps/sandbox` and every other crate keeps `unsafe_code = "forbid"`. Nodes need `/dev/kvm`, normally through a device plugin rather than a privileged pod, so managed clusters without nested virtualization cannot run the `kvm` runtime; they run the `container` runtime, with the weaker boundary declared. A guest kernel and root image are release artifacts, and every `kvm` sandbox image build, test cluster and Docker host needs them and `/dev/kvm`.

**Rationale.** [Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary) needs a VM boundary; a RuntimeClass such as Kata Containers was only one way to obtain it, and it tied every qualified installation to a cluster-level runtime handler Cubebot does not control, ruled out clusters where the administrator cannot install one, and left no VM path at all for cluster-less development. Owning a small VMM keeps the boundary inside Cubebot's release and qualification, works wherever `/dev/kvm` is reachable, and avoids depending on a cluster-scoped runtime handler. The device set is deliberately minimal: block, network, vsock and serial cover the agent, its terminal, its browser and its journal. Avoiding VMM crates keeps the device model small enough to review in full. The declared `container` runtime exists so installations without `/dev/kvm` can still run agents, with the weaker boundary stated rather than hidden.

Alternatives considered: keep a RuntimeClass such as Kata, which leaves the boundary outside Cubebot and unavailable without cluster-level installation. Embed rust-vmm, Firecracker or Cloud Hypervisor crates, which brings a far larger device model and dependency surface than four devices need. Use gVisor or plain containers, which do not give a hardware virtualization boundary (plain containers return only as the declared `container` runtime).

**What changed.** As accepted on 2026-10-28, a development `process` backend existed; the 2026-10-29 amendment removed it. Until 2026-11-02 the rule was "one backend, no unisolated mode": the KVM guest was the only agent sandbox. The 2026-11-02 amendment replaced it with "one agent image, declared runtimes, no undeclared or misreported one", which restored [Standard containers with optional sandbox runtimes](#standard-containers-with-optional-sandbox-runtimes) for the `container` runtime. The open guest memory and vCPU sizing was settled on 2026-10-30 by [Desktop as a VMM device](#desktop-as-a-vmm-device): a desktop needs more than the original single vCPU and 256 MiB. That decision added virtio-gpu and virtio-input devices on 2026-10-30; its 2026-11-01 amendment removed them, so the VMM is back to the four devices above.

**Open details.** Guest kernel and root image build and signing; vsock control protocol; how `/dev/kvm` reaches the pod on each qualified cluster; tap and address setup inside the pod network namespace; the sandbox qualification matrix.

**Validation scenarios.** A sandbox on a KVM node boots the guest, mounts the workspace disk and logs through the serial console; a command in the guest cannot reach another agent, the database or the Kubernetes API, and NetworkPolicy changes take effect on guest traffic; stopping the agent ends the VM; a sandbox image built without the guest fails to build; a sandbox lost mid-command recovers from its journal and the orchestrator's attempt records without re-running the command; `cubebot-sandbox run` refuses to start without `/dev/kvm`; the installation API and console report a `container` runtime as a container; a sandbox refuses a workspace volume laid out by the other runtime and the agent's status says why.

## Standard containers with optional sandbox runtimes

Accepted 2026-10-24. Set aside for agents 2026-10-28, when the in-house VMM became the only agent sandbox. Restored 2026-11-02: applies as written to the `container` runtime.

**Decision.** Under the `container` runtime ([In-house VMM as the agent sandbox](#in-house-vmm-as-the-agent-sandbox)), run agent pods on the cluster's standard container runtime by default. Support administrator-approved alternative sandbox runtimes through Kubernetes RuntimeClass selection, named in the controller's `runtime.class` (or a Docker runtime under the Docker backend). Installation policy may require a sandbox for agent execution. If a required or explicitly selected runtime is unavailable, block execution rather than silently falling back. The user selected this policy on 2026-10-24 and its restoration on 2026-11-01. The `kvm` runtime remains the hardware boundary where `/dev/kvm` exists.

Usage: an individual installs Cubebot on a compatible cluster with the `container` runtime and starts agents on its standard runtime. An organization with an approved sandbox runtime configures Cubebot to use it and can require that selection. If compatible nodes or the runtime are unavailable, accepted work remains durable and the console reports why its agent cannot start.

Ownership: the cluster administrator installs and configures node runtime handlers and RuntimeClass resources. Cubebot installation administration controls the approved runtime choices and requirements. The lifecycle module resolves the effective policy and applies it to agent pod specifications. Ordinary agent creation, software installation, and task execution do not authorize installing node runtimes, altering RuntimeClass resources, or weakening installation policy.

RuntimeClass selects the runtime for the agent pod's container, which runs the agent image with its runtime and tools together. Alternative runtimes must be qualified against the required browser, terminal, local MCP, storage, and networking behavior. No particular sandbox implementation is selected or certified by this decision.

The standard mode retains requirements for scoped permissions, resource limits, and enforced network controls. Optional sandboxing adds an isolation mechanism; it does not replace those requirements or prove that they work.

Record the requested runtime policy and observed pod configuration, including a clear provisioning or compatibility failure. Check policy on creation and replacement. Runtime unavailability, pod failure, or a retry must not clear an explicit selection or downgrade a required sandbox. An installation policy change must not be displayed as applied to existing agents until the affected pods actually comply.

Keep agent identity, memory, history, and persistent workspace across a runtime class change. Reconcile active execution and external effects before replacement. File persistence does not promise that installed software, live browser sessions, or running processes remain compatible with another runtime. Compatibility failures require visible recovery rather than silent workspace deletion. Switching between the `kvm` and `container` runtimes is not such a change: a sandbox refuses the other runtime's workspace layout and there is no conversion.

RuntimeClass resources are cluster-scoped infrastructure. Referencing an administrator-provided class is consistent with [One namespace for the entire installation](packaging.md#one-namespace-for-the-entire-installation) and does not authorize Cubebot to manage the cluster's runtime configuration.

**Rationale.** Requiring a sandbox runtime for all installations would exclude clusters without one; supporting only standard containers would give organizations no stronger option. The user selected standard operation with optional, enforceable sandbox policy to preserve installation flexibility. Since the VMM decision, the stronger default is the `kvm` runtime where `/dev/kvm` exists, and this decision governs installations that declare `container`.

Platform reference: [Kubernetes RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/), reviewed on 2026-10-24, documents per-pod runtime selection, administrator-managed runtime configuration, scheduling constraints, and overhead accounting.

**What changed.** As accepted, the agent pod held a trusted runtime container and a tool container ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary) records that layout), and standard mode required separated credentials and mounts between them; the shared pod network left trusted runtime traffic and tool traffic indistinguishable. That layout is gone: the agent image is one container, and the sandbox edge is the boundary. On 2026-10-28 the in-house VMM made its KVM guest the only agent sandbox and set this decision aside for agents; on 2026-11-02 the declared-runtime amendment restored it for the `container` runtime. "By default" now means within the `container` runtime only: the installation must declare `kvm` or `container` explicitly, and no runtime is inferred or defaulted (a genuine conflict between the two texts, resolved in favour of the later declared-runtime rule).

**Open details.** Supported runtime implementations and versions; installation-wide defaults and any per-agent selection interface; policy activation and the safe activation and replacement procedure; node scheduling constraints; overhead accounting; compatibility diagnostics; and the qualification matrix. Support must be claimed per tested configuration rather than for every RuntimeClass implementation.

**Validation scenarios.** Start on a compatible default runtime; use an approved alternative; reject unapproved selection; block when a required runtime is unavailable; preserve the selected policy during retries and replacement; prevent agent-driven downgrades; show pending policy application honestly; and qualify browser, terminal, local MCP, volumes, network enforcement, and recovery under each supported mode. Implementation and runtime qualification remain pending.

## Desktop as a VMM device

Accepted 2026-10-30. Amended 2026-10-30: the agent's own screenshots are kept in the turn ledger. Amended 2026-10-31: a login handoff refuses agent screenshots. Amended 2026-11-01: the screen and input move into the sandbox as two X servers under a root arbiter, replacing the virtio-gpu and virtio-input devices.

**Decision.** The agent's desktop is owned by an arbiter that agent-run code cannot bypass. The user selected the host-owned desktop on 2026-10-30 and moved it inside the sandbox on 2026-11-01.

- **The desktop runs inside the sandbox.** Guest init (or container init), as root, starts Xvfb on `:0` with `-nolisten tcp -nolisten local`, a cookie only root can read, and its socket chmod 0700 once it exists and before any tool-user process; then Xephyr on `:1` at 1280x800, nested on `:0` at (0, 0) so both displays share coordinates, with the XTEST extension disabled, as the tool user's display, where openbox, the wallpaper, Chromium and every tool process run.
- **One arbiter.** The arbiter is a root process in the sandbox and the only client of `:0`: it gives Xephyr's window input focus there (the outer display has no window manager), reads frames with GetImage of `:0`'s root and injects input with XTEST on `:0`, which Xephyr receives as device events. It is the only reader of the frames and the only writer of input. It serves the agent's tools on a Unix socket in `/run` only root can open, and the orchestrator over the sandbox's host channel.
- **Host channel.** The VMM keeps only its disks, network, vsock and serial console. In a `kvm` guest the arbiter keeps a spare stream open to vsock host port 1026 from a reserved source port, which only root can bind, and the sandbox pairs each with a host channel connection and relays it unparsed; the host channel command is `cubebot-sandbox desktop`. In the `container` runtime the host channel command is `cubebot-agent desktop`, which connects to the arbiter's socket directly. The orchestrator runs the command through the platform's exec into the sandbox container, picked by runtime, so the channel authenticates with the platform's exec authorization for that container.
- **What the tool user cannot do.** It cannot inject device input (no XTEST on its display) or reach `:0` (no cookie, no abstract or TCP socket, a root-only socket), so it cannot send input as a person or replace the frames a person sees. Tool code on `:1` can still send XSendEvent synthetic events, which carry the synthetic flag and which Chromium ignores for keys, and can move the pointer with WarpPointer; the earlier single-server desktop allowed the same. Integrity holds against the model's code and the tool user, not against a root or kernel compromise inside the sandbox, which the `kvm` runtime still contains.
- **Three modes.** `agent`: the agent drives and no person is connected. `watch`: the agent drives and people see the screen read-only. `human`: one person holds control. The arbiter holds the mode; a person takes and releases control through the orchestrator, and the agent is told of every change.
- **Input is tagged and refused at the arbiter.** Every input event carries its source, the agent or the person's account, as the arbiter receives it. In `human` mode the arbiter refuses agent input with an error naming the mode and drops nothing silently; screenshots stay available to the agent so it can resume from what the person left, except during a login handoff. In `agent` and `watch` modes person input is refused unless that person has taken control.
- **A login handoff refuses screenshots too.** When an agent asks a person to log in ([Live browser viewing and explicit human takeover](#live-browser-viewing-and-explicit-human-takeover)) and that person takes control while the request is pending, the orchestrator says so in the mode change, and until control changes again the arbiter refuses every agent request, screenshots and mode queries included, with an error naming the pending login. The agent's browser tools ask the arbiter's mode before every call, reads included, so they are refused too. What the person types into a login page never reaches the model, the ledger or a screenshot; the agent looks again once the hand-back tells it the login completed. Outside a login handoff, `human` mode still serves the agent's screenshots. The arbiter also types vault secrets on the orchestrator's `fill` request under the same refusals ([A vault the desktop arbiter fills](identity.md#a-vault-the-desktop-arbiter-fills)).
- **The orchestrator proxies, never holds pixels.** The orchestrator authorizes and forwards desktop sessions between the browser and the sandbox and records them: who connected, mode changes, and every input event with its source and time. It forwards frames without decoding, storing or caching them, and no recording contains pixels. The browser's WebSocket asks the orchestrator for frames, and the orchestrator asks the host channel for the next frame at most every 50 ms and only after the last was sent; a frame is the 64x64 PNG tiles that changed since that host channel connection's previous frame, with the pointer and who last moved it, in the arbiter's JSON line, which the orchestrator forwards unparsed.
- **Agent screenshots are ledger evidence.** A screenshot the agent takes through its computer-use tool is that tool call's result, and like every tool result it is committed to the turn ledger, as a `screenshot` outcome with the PNG. It is the evidence of what the model saw when it acted, kept and deleted with the conversation ([Retain durable data until explicitly deleted](memory.md#retain-durable-data-until-explicitly-deleted)). This covers only frames the agent requested for a tool call; frames of a person's desktop session are never stored. Views of the conversation in the console and the replay of earlier tool events to the agent leave the image out, and the agent's local crash journal records the result without it, since a screen is not an effect to recover.
- **Formats.** Screenshots are PNG. The agent's requests are JSON lines (`cubebot_protocol::desktop`) on the arbiter's Unix socket.

Usage: the agent's computer-use tools take screenshots and send keys and pointer events to the arbiter. A person opens the agent's desktop in the console, which starts a `watch` session; taking control switches to `human`, and releasing it or disconnecting returns the arbiter to `watch` or `agent`. The session record shows which input came from the agent and which from each person.

The desktop belongs to the agent's sandbox, so the coarse agent authority of [Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary) governs what desktop applications can reach, and its single trust boundary is unchanged. Consequences: frames cross the orchestrator, so desktop sessions cost it bandwidth but not storage. Agent-run code inside the sandbox can still draw anything on the screen; what it cannot do is send input as a person or bypass the arbiter's mode. The guest kernel needs no DRM, virtio-gpu, virtio-input or uinput.

**Rationale.** A desktop run entirely as the agent's own software, such as a VNC server, would let anything agent-run produce the frames a person sees and the input they appear to have sent. Nothing could then tell agent input from human input, or keep the agent off the controls while a person holds them. The arbiter, as the sole reader of frames and writer of input, makes the source tag and the `human`-mode refusal properties of a component the tool user cannot modify rather than promises of software the agent controls. Running it inside the sandbox as root with two X servers gives the `container` runtime the same desktop as `kvm`, keeps the VMM to four devices, and needs no GPU on the node; a spike passed all four checks with a median key latency of 0.29 ms. Keeping pixels out of the orchestrator keeps it a control plane: its storage and memory do not grow with screen sessions, and recordings stay reviewable text.

Alternatives considered: a VNC or RDP server in the guest, which leaves frames and input under guest control and cannot attribute input. Screenshots by a guest tool, which the agent can replace. Storing recordings with frames in the orchestrator, which turns the control plane into a media store. A full virtio-gpu with virgl or Venus, which needs host GPU stacks and a far larger parser for no benefit to a desktop the agent reads as images.

**What changed.** As accepted on 2026-10-30, the desktop was a set of VMM devices, which is why the section keeps that name. `cubebot-sandbox` served a virtio-gpu device with the 2D command set only (no virgl, no 3D, no blob resources), copying the guest's scanout into a framebuffer in the sandbox process on transfer and flush, so a screenshot was the host's copy of what the guest last presented. Two virtio-input devices, a keyboard and an absolute pointer, were the guest's only input devices; the guest kernel had no uinput and the guest display server took input only from evdev, with no XTest injection. The arbiter lived in the sandbox process and served the agent on vsock port 1025. Consequences then were two more device types to review and fuzz, a 2D parser bounding guest-supplied resource sizes and backing pages, and a guest kernel with virtio-gpu DRM and virtio-input. The rationale was that the VMM already sits between the guest and everything outside it. The 2026-11-01 amendment replaced the Screen, Keyboard and pointer, and One arbiter rules with the two-X-server desktop and root arbiter above, deleted virtio-gpu, virtio-input, the desktop module and the PNG encoder from `apps/sandbox`, and moved the agent's port from vsock 1025 to the Unix socket. The open host-channel authentication was settled by the platform's exec authorization; the open live-view transport was settled with the console view. This decision also closed the VMM's sizing detail (2 vCPUs and 2 GiB by default; see [In-house VMM as the agent sandbox](#in-house-vmm-as-the-agent-sandbox)).

**Open details.** Display resolution and whether the guest may change it; recording retention, which follows [explicit deletion](memory.md#retain-durable-data-until-explicitly-deleted).

**Validation scenarios.** A screenshot through the agent's socket and one through the orchestrator show the same frame. Input from the agent and from a person appear in the session record with their own sources. While a person holds control, agent input is refused with the mode named and has no effect on the desktop; screenshots still succeed, except while they hold it for a pending login handoff, when screenshots and browser calls are refused too. A process in the sandbox cannot create an input device or inject input into the display server; a tool-user process cannot read the outer display's cookie, connect to its path, abstract or TCP socket, open the arbiter's socket or bind a reserved vsock port, and finds no XTEST on its display. No orchestrator storage, log or recording contains frame data from a person's desktop session; the only stored frames are the agent's own screenshots, each in the ledger beside the tool call that took it.

## Agent-directed software installation within grants

Accepted 2026-10-23. Amended 2026-10-27: installation runs in the agent's sandbox, not a separate tool container.

**Decision.** Allow agents to install additional software into their writable workspace or user environment within granted permissions. The user selected this behavior on 2026-10-23 and emphasized that installation is important for getting work done. Installation is a supported capability, not an exceptional workflow requiring approval for each package.

Usage: a document-processing task requires a missing library. An authorized agent installs it into an environment in its workspace, verifies that it can use it, and continues the task. A coding agent can similarly install project dependencies or a user-local CLI. The operation runs inside the agent's sandbox as the tool user ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary)); it does not modify the managed sandbox image.

The administrator-managed base image remains the foundation. This decision grants neither root access nor authority to change the managed image, host, or Kubernetes configuration. Requirements that genuinely need unavailable system dependencies must be reported accurately and can be addressed through administrator-managed images.

Installation uses ordinary ecosystem tooling through the agent's ordinary tools. Cubebot does not need a custom package manager or an additional package-by-package approval queue. Resource budgets, allowed network access, filesystem permissions, and available integration credentials still apply. Installation grants do not create new external access or expand an agent's authority. Network access, including package downloads, follows [Public internet access with grants for private destinations](#public-internet-access-with-grants-for-private-destinations), which also allows stricter installation policy.

Ownership: authorization defines permitted execution and resource access. The agent's tool execution runs installation commands, captures outcomes, and applies execution limits. Workspace lifecycle owns persistent paths and quotas. Image administration owns the base environment. The agent owns selecting and using dependencies appropriate to its task.

Grant enforcement must reflect the actual powers of a terminal. An environment that permits arbitrary code execution, downloads, and writes already permits many forms of software installation. A package-manager command denylist is not an enforceable installation restriction. The exact grant vocabulary and underlying filesystem, network, and execution controls remain to be designed together.

Supported installation locations must be clear to the agent. Software placed in designated persistent workspace or user-environment paths survives ordinary sleep and sandbox replacement as files under [Durable storage](memory.md#durable-storage). Changes in disposable storage have no durability guarantee. Persistence does not guarantee binary compatibility after a base-image or architecture change; environment repair and rebuild behavior must be specified separately.

Installation is an external tool effect, not a transactional memory write. A failed or interrupted command can leave partial files. The agent must inspect the outcome before declaring the software ready or blindly repeating installation. Concurrent lanes share the workspace under [Agent execution lanes](agents.md#agent-execution-lanes), so shared environment mutations require coordination; project-local environments can reduce unnecessary sharing.

Consequences: environments can evolve independently across agents. Dependency records and lockfiles should be retained where supported to aid reproduction and repair. Downloads, build artifacts, caches, and installed software consume bounded storage and compute. Exact tool images, persistence paths, and cleanup behavior remain implementation choices. In the `container` runtime, software the agent installs shares the host kernel, so a kernel exploit from it is not contained ([In-house VMM as the agent sandbox](#in-house-vmm-as-the-agent-sandbox)).

**Rationale.** Agents need dependencies, command-line tools, and language environments that cannot all be anticipated in a base image. Requiring an administrator image change for every missing dependency would interrupt useful autonomous work. Alternative considered: permit only preinstalled software and require image updates for missing dependencies. That improves environmental uniformity but blocks work on administrative intervention. The user selected agent-directed installation within existing permissions.

**What changed.** As accepted, installation ran in the tool container through the tool-execution interface and could not modify the Rust runtime container or its credentials. Since [Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary), the runtime and its tools share one sandbox, so the scenario "preserve runtime credential isolation" is replaced by keeping installation inside the sandbox and outside the managed image.

**Open details.** Base images and included toolchains; persistent home and environment layout; grant vocabulary; network enforcement and package-source restrictions; workspace quotas; concurrent installation coordination; environment repair after image changes; and dependency observability.

**Validation scenarios.** Install a missing library and complete the task without another approval; install and invoke a user-local CLI; reuse a persistent environment after sleep and replacement; report a missing system dependency honestly; enforce network and storage limits; keep installation inside the sandbox without changing the managed image; recover from partial installation; and coordinate concurrent edits to a shared environment.

## Public internet access with grants for private destinations

Accepted 2026-10-23. Amended 2026-10-27: enforcement is at the edge of the agent's own sandbox, and disconnected work keeps its long-lived authority.

**Decision.** Agent tools have public internet access by default. Private destinations require explicit grants. The user selected this policy on 2026-10-23. Installation policy may impose stricter restrictions. This applies to browser requests, terminal commands, package downloads, and agent-installed programs, rather than only Cubebot's built-in HTTP tools.

Usage: an agent can research public documentation and download a project dependency without requesting permission for each destination. Connecting to an internal database or private package registry requires an appropriate network grant and, independently, any application credentials and permissions. Installation does not implicitly grant access to internal infrastructure.

Private and infrastructure destinations must be identified by the actual connection target and installation topology, not merely by the spelling of a requested URL. The policy must cover private and special-use addresses, cluster services, nodes, and infrastructure endpoints such as metadata services. Exact address classification, protocols, port scope, and treatment of infrastructure exposed on public addresses remain to be specified.

Enforcement must evaluate redirect targets and address resolution changes, including IPv4 and IPv6. A public hostname that resolves to a prohibited address must not bypass the private-access rule. Direct sockets, alternate resolvers, and tools that ignore proxy settings must be included in qualification. Setting an HTTP proxy environment variable alone does not establish enforcement for arbitrary programs.

Ownership: authorization owns network grants and their scope. Deployment and sandbox controls enforce the resulting policy: the agent's traffic leaves its own sandbox (through the tap device in the pod network namespace under `kvm`), so pod-level NetworkPolicy governs exactly one agent ([In-house VMM as the agent sandbox](#in-house-vmm-as-the-agent-sandbox)). Tool interfaces report denied access clearly without granting additional authority. Network reachability does not authorize an application action, supply credentials, or override a read-only integration grant.

Runtime provider inference and required platform communication retain their separately authorized paths under [Agent state access through the orchestrator](agents.md#agent-state-access-through-the-orchestrator) and [Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication). A connection to the orchestrator is not a grant to its privileged operations. Agent-created local development servers and browser access to them need an explicit local-access design; localhost is not a blanket permission to invoke control endpoints such as the desktop arbiter, which only root can open.

While the orchestrator is unavailable, the agent keeps the private-access grants it already holds under its long-lived sandbox authority ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary)). Agents cannot obtain new private-destination grants while disconnected. Revocation means revoking the agent's credential or stopping its sandbox; revocation behavior for established connections must be specified together with execution cancellation.

Consequences: public internet access allows outbound transmission as well as reading and downloading. This policy does not guarantee prevention of data exfiltration to public destinations or prevent use of a publicly reachable relay. Scoped data access and any stricter installation restrictions remain relevant. Network policy is not a replacement for application authorization. See [One namespace for the entire installation](packaging.md#one-namespace-for-the-entire-installation) for the namespace's network rules.

**Rationale.** Agents need public websites, package sources, and external tools to perform general-purpose work. They also run inside infrastructure that can contain private services and privileged endpoints, so reachability needs a default consistent with autonomous software installation and explicit capability grants. Alternative considered: require an explicit allowlist for every public destination. That restricts data movement more tightly but can block research and dependency installation on repeated configuration changes. The user selected public internet access by default with explicit private access.

**What changed.** As accepted, the runtime and tool containers shared a pod network, so enforcement had to preserve the runtime's required paths while stopping arbitrary tool programs from using them, through an authenticated runtime/tool interface, and ordinary pod-level rules could not tell those callers apart; the mechanism was an open architectural issue. [Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary) dropped the distinction: runtime and tools share the sandbox, its edge is the boundary, and pod-level policy now applies to one agent. The in-pod kernel egress filter and network initializer were removed with the tool container. Disconnected work was limited to the finite per-turn authority of [Bounded continuation during disconnection](agents.md#bounded-continuation-during-disconnection), with private access expiring offline; per-turn windows no longer exist, so the scenario "expire private access during disconnected execution" is replaced by stopping private access when the agent's credential is revoked or its sandbox is stopped.

**Open details.** Enforcement mechanism at the sandbox edge for each runtime; destination and protocol classification; grant schema; DNS and redirect handling; local development access; proxy and tunnel treatment; connection revocation; installation overrides; and denied-access observability.

**Validation scenarios.** Browse a public website; install from a public registry; deny an ungranted private endpoint; permit a specifically granted internal service without granting unrelated destinations; reject a public-to-private redirect and changed DNS resolution; apply the policy to installed programs and direct sockets; preserve required runtime communication with the orchestrator and provider; and stop private access when the agent's credential is revoked or its sandbox is stopped.

## Structured browser tools with visual interaction

Accepted 2026-10-23. Amended 2026-10-27: the browser runs in the agent's sandbox. Amended 2026-10-30: screenshots and visual input go through the desktop arbiter.

**Decision.** Provide structured browser tools as the default interaction path, with screenshots and visual actions available when needed. Both operate on the same browser session. The user selected this model on 2026-10-23. This choice does not select a browser library or provider-specific computer-use engine.

Usage: an agent inspects a page, locates a field by its label, and fills it through a structured action. When the task requires examining a visual layout or interacting with an element that lacks useful structure, it can inspect a screenshot and perform a targeted visual action in that same session. It then observes the resulting state before claiming success.

The structured interface should support bounded page inspection and actions on observed elements. The visual interface should support screenshots and relevant pointer, keyboard, and scrolling actions. Both use explicit session and page identity.

Ownership: a browser module in the agent's sandbox owns sessions, observations, action targeting, and browser outcomes. The agent invokes it under the same authorization and execution accounting as other tools. Browser processes run as the tool user on the sandbox desktop ([Desktop as a VMM device](#desktop-as-a-vmm-device)); the agent's screenshots and visual input pass through the desktop arbiter, and its browser tools ask the arbiter's mode before every call. The runtime's provider credentials do not become browser credentials.

Structured and visual paths share permission and network enforcement under [Autonomous tool use within granted permissions](agents.md#autonomous-tool-use-within-granted-permissions) and [Public internet access with grants for private destinations](#public-internet-access-with-grants-for-private-destinations). A visual click does not bypass a restriction applied to structured actions. Page content is untrusted task data and cannot grant access, alter runtime instructions, or authorize new operations.

Observations and actions must refer to the intended page state. Navigation, changed elements, or a stale screenshot can invalidate a target. The implementation must detect relevant invalidation and re-observe rather than blindly reuse stale coordinates or element references. Browser operations with uncertain outcomes require inspection before retry, especially submissions with external effects. A successful click alone does not establish that the intended business operation completed.

Execution records associate actions and results with the responsible agent, lane, and session. Screenshot and page-content capture must respect output budgets and retention rules. These observations enter the requesting lane as tool results; the agent's own screenshots are kept in the turn ledger ([Desktop as a VMM device](#desktop-as-a-vmm-device)), and this decision does not mandate recording continuous browser video or every page byte.

Visual work requires a configured model capable of consuming the required observations. Model capability validation must expose an incompatible configuration honestly. [Retry and wait for the selected model](agents.md#retry-and-wait-for-the-selected-model) still prohibits silently switching models. Structured work can remain available when supported even if a specific visual operation cannot proceed.

Consequences: Cubebot must maintain consistent targeting, grants, and records across both interaction paths. [Main browser session with separate task sessions](#main-browser-session-with-separate-task-sessions) assigns separate browser sessions to the main lane and tasks that need browsing, and [Reuse authorized website logins across browser sessions](#reuse-authorized-website-logins-across-browser-sessions) permits reuse of applicable authorized website logins across them. Profile persistence remains open. Browser visual interaction does not by itself promise control of a complete operating-system desktop. [Live browser viewing and explicit human takeover](#live-browser-viewing-and-explicit-human-takeover) provides live viewing and explicit human takeover; both structured and visual agent actions obey the current control state.

**Rationale.** Agents need to read websites, complete forms, and test interfaces, handling both accessible page structure and work that requires visual inspection without separate, inconsistent browser states. Visual-only interaction would use one action model but make ordinary text and form work depend on screenshot interpretation. Structured-only interaction would reduce the tool surface but provide no visual path when page structure is insufficient. The user selected both with structured interaction as the default.

**What changed.** As accepted, browser processes ran in the tool container separate from the credential-holding runtime; they now run in the agent's sandbox ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary)). The open live transport and handoff mechanics were settled by [Desktop as a VMM device](#desktop-as-a-vmm-device). Browser authentication for typed logins was settled by [A vault the desktop arbiter fills](identity.md#a-vault-the-desktop-arbiter-fills).

**Open details.** Browser implementation and Rust integration; tool names, schemas, script-evaluation capabilities and observation formats; stale-target handling; model capability requirements; session allocation mechanics and persistence; downloads and uploads; and capture retention.

**Validation scenarios.** Read a page and fill a labeled form; use a screenshot and visual action in the same session; reject a stale target after navigation; inspect an uncertain submission before retrying; enforce private-network restrictions across both paths; reject unsupported visual inference without model fallback; and attribute browser actions to the correct execution lane.

## Main browser session with separate task sessions

Accepted 2026-10-23. Amended 2026-10-27: sessions run in the agent's sandbox.

**Decision.** Give the main lane its own browser session and allocate a separate session to each task that needs browser access, subject to resource limits. The user selected this model on 2026-10-23. Structured and visual actions within a lane address that lane's assigned session under [Structured browser tools with visual interaction](#structured-browser-tools-with-visual-interaction).

Usage: the main lane fills out a form while two admitted tasks research separate websites. Each operates on its own pages and receives observations from its own session. A task navigating, closing a page, or sending keyboard input must not alter the main lane's browser target. Tasks that do not need a browser need no allocated browser session.

Ownership: the browser module owns session identity, task-to-session assignment, page ownership, and lifecycle. Scheduling (the agent loop's lane rule) owns admission against browser and agent resource limits. The runtime carries the execution identity into each browser request so the browser module can reject mismatched or stale references. Callers use the browser interface rather than managing browser processes directly.

Separate sessions must provide independent page state and input targeting. A shared desktop pointer or keyboard focus must not let a task's visual action affect a different session. The implementation may use browser contexts, separate processes, or another supported arrangement; the session contract is selected here, while the concrete browser and display layout remain open.

All sessions belong to the same agent and run in its sandbox ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary)). This decision introduces no additional sandboxes, per-task containers, agent identities, or independent workspace security. Sessions are an execution-coordination mechanism, not isolation between mutually untrusted users. Shared files and concurrent changes to the same external account still require coordination.

Browser concurrency is bounded by the existing lane limits and available resources. It does not guarantee a browser instance can always start. Unavailable capacity must lead to explicit waiting or a reported resource failure, not silent reuse of another lane's active session. The number of browser processes and their resource accounting remain implementation details.

Main-session allocation does not promise that a live browser process, open page state, or website login survives sleep or sandbox replacement. [Agent idle lifecycle](agents.md#agent-idle-lifecycle) still governs loss of in-memory execution state. [Reuse authorized website logins across browser sessions](#reuse-authorized-website-logins-across-browser-sessions) permits reuse of website logins authorized for the agent and applicable to the task, without inheriting every cookie or credential from the main session.

Recovery must reconcile task and session identity before accepting further actions. Browser failure does not prove that a submitted external action failed; continuation must inspect recorded outcomes and re-observe before retrying. A stale session or page handle must not be silently rebound to a different task's browser.

Consequences: Cubebot needs per-session lifecycle tracking, bounded allocation, and reliable visual targeting. External-account conflicts remain possible even when pages are separate. Browser session isolation does not supersede network grants, application permissions, or workspace coordination. [Live browser viewing and explicit human takeover](#live-browser-viewing-and-explicit-human-takeover) supports live viewing and exclusive human takeover, with separate viewing and control permissions.

**Rationale.** An agent can run its main lane alongside bounded concurrent task lanes ([Agent execution lanes](agents.md#agent-execution-lanes)), and browser work needs the same concurrency without one task navigating away from another task's page or redirecting its visual input. Alternative considered: one shared browser session reserved exclusively by one lane at a time. That simplifies shared state but serializes browser work across otherwise concurrent tasks. The user selected separate main and task sessions.

**What changed.** As accepted, sessions ran in the agent's tool container in its one pod; they now run in its sandbox, and lane admission moved from an orchestrator rule into the agent loop ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary)).

**Open details.** Browser context and process layout; visual input routing; profile persistence; login reuse mechanics; allocation limits; task-session retention and cleanup; crash recovery; download naming; and control handoff mechanics for task sessions.

**Validation scenarios.** Main and task lanes browse concurrently without navigation interference; structured and visual actions address the same assigned session; stale or cross-task handles are rejected; browser capacity exhaustion is visible; closing one task session leaves others usable; resource cleanup respects active invocations; and browser restart does not replay an uncertain submission.

## Reuse authorized website logins across browser sessions

Accepted 2026-10-23. Amended 2026-11-01: typed logins are kept in the orchestrator's vault and filled by the desktop arbiter.

**Decision.** Task sessions may reuse website logins already authorized for their agent and applicable to the task. The user selected this model on 2026-10-23. Reuse preserves separate pages and interaction state; it does not merge sessions or require every task to share the main session's entire browser profile.

Usage: an agent has authorized access to a project-management account. A task can use that account in its own browser session while the main lane works in another session. Both remain subject to the granted account permissions. A task does not receive unrelated accounts merely because they have been used in the main browser.

Ownership: authorization determines account eligibility for the agent and task. The browser module associates sessions with the intended website account and applies supported reusable authentication state. It must identify which account a session is using and expose expired, mismatched, or unavailable authentication honestly. Usernames and passwords for typed logins are stored in the orchestrator's vault, and the desktop arbiter types them at the agent's request without returning the text to the agent ([A vault the desktop arbiter fills](identity.md#a-vault-the-desktop-arbiter-fills)); besides installation-managed logins, an agent may hold logins of its own there.

Reusable website authentication is sensitive material. It must not be copied into model prompts, ordinary tool-result text, or unrelated session profiles. Reuse does not authorize exporting credentials, sharing them with another agent, or expanding task grants. It is distinct from model-provider authentication under [Installation-managed provider connections](identity.md#installation-managed-provider-connections), [Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication) and [Orchestrator-owned provider authentication refresh](identity.md#orchestrator-owned-provider-authentication-refresh); those decisions do not automatically make the orchestrator responsible for every website's login or refresh behavior.

Implementation requirements: reuse only the state needed for the authorized website/account where supported. Do not have concurrent sessions mutate one live profile directory or blindly merge every session's cookies and storage. The choice between initial snapshots, explicitly published authentication updates, or other supported mechanisms remains open. Page state and visual targeting retain the independent-session contract.

Not every website login can be reused in another session. Expired state, account challenges, or unsupported authentication must lead to an accurate need for login or intervention rather than a claim that access was established. Reuse is a supported path when technically possible, not a guarantee of permanent login or concurrent-session acceptance by every website.

Account changes and external actions can affect other sessions using the same account even when their browser state is separate. Logout, revocation, and refreshed authentication require coordinated behavior. New session reuse must respect current grants, while existing sessions follow defined revocation rules. Immediate provider-side invalidation cannot be inferred from deleting a local copy.

Separate task sessions remain an execution-coordination mechanism within one agent and its sandbox, not a security barrier against arbitrary code in that sandbox. The isolation design must state what credential protections it actually enforces. Reuse does not add per-task filesystem isolation contrary to [Agent execution lanes](agents.md#agent-execution-lanes).

Consequences: agents can perform authenticated browser tasks without unnecessary repeated login. Cubebot must track account attribution and handle shared-account effects. [Live browser viewing and explicit human takeover](#live-browser-viewing-and-explicit-human-takeover) permits authorized users to take over, including for login assistance. Reusable external account connections are installation-managed ([Installation-managed external account connections](identity.md#installation-managed-external-account-connections)); browser-assisted login does not itself grant authority to register or share a new connection.

**Rationale.** Separate main and task sessions would otherwise require a fresh login for every task, interrupting work even when the agent already has authorized access. Alternative considered: independent login for every session. That would separate initial authentication state but introduce repeated login work and potential human intervention for ordinary tasks. The user selected reuse of authorized logins.

**What changed.** Secret storage was open; [A vault the desktop arbiter fills](identity.md#a-vault-the-desktop-arbiter-fills) settled it for typed logins, and amended the installation-managed rule so an agent may also hold its own logins. As accepted, existing sessions followed bounded-disconnection rules for revocation; per-turn disconnection windows no longer exist ([Agent-centric execution in a sandbox boundary](#agent-centric-execution-in-a-sandbox-boundary)).

**Open details.** Account grant schema; supported authentication-state formats (cookies and stored browser state); update ownership and versioning; reauthentication; persistence across sleep and deletion; session cleanup; account-level concurrency; revocation propagation; and credential isolation from arbitrary tool programs.

**Validation scenarios.** A task reuses an authorized account while keeping separate pages; an unrelated account is not inherited; a task with insufficient grants is denied reuse; expired or non-reusable state requests intervention; account identity is visible without exposing secrets; concurrent sessions do not write one live profile; and revocation prevents new unauthorized reuse.

## Live browser viewing and explicit human takeover

Accepted 2026-10-23. Amended 2026-10-30: viewing and takeover act through the desktop arbiter's modes. Amended 2026-10-31: a login handoff refuses agent screenshots. Amended 2026-11-01: a person or the agent can have a vault login typed instead of typing it.

**Decision.** Provide live viewing and explicit, exclusive human takeover through the web console and mobile PWA. The user selected this model on 2026-10-23. Viewing and controlling have separate permissions. The console shows what is being viewed and its current controller. Viewing and takeover act on the agent's sandbox desktop through the arbiter's `watch` and `human` modes ([Desktop as a VMM device](#desktop-as-a-vmm-device)).

Usage: a user watches an agent's browser work, requests control, completes a website login, and returns control. Once the handoff is confirmed, the agent observes the current page again and continues from the user's resulting state. Unrelated browser sessions may continue under their existing grants and resource limits. A person holding control can instead have a vault login typed for them ([A vault the desktop arbiter fills](identity.md#a-vault-the-desktop-arbiter-fills)), and can save the login and have it typed in one step.

Ownership: authorization owns viewing and control permissions. The desktop arbiter owns exclusive input authority and enforcement: it holds the mode, tags every input event with its source and refuses agent input while a person holds control. The orchestrator coordinates authenticated console requests, proxies frames without storing them, and records control transitions. The console presents live state and submits user input only while authorized control is held.

Takeover is a confirmed transition, not merely a UI toggle. Stop admitting agent browser actions and settle or reconcile in-flight actions before granting human input authority. Pending structured actions and visual input must obey the same ownership rule; the agent's browser tools ask the arbiter's mode before every call. A submitted external action cannot be undone by taking control, so unresolved outcomes must remain visible.

At most one controller may issue input at a time. Multiple viewers do not gain control implicitly. A stale client or queued agent action must not act after its authority has been replaced. If a disconnected runtime cannot be fenced from control, the console must not falsely claim takeover succeeded.

Returning control invalidates stale observations and planned browser actions. The agent re-observes the page and accounts for visible user changes before further interaction. The handoff must not restart the original task or replay already-completed submissions. When the controlling person disconnects, the arbiter returns to `watch` or `agent` as if control were released ([Desktop as a VMM device](#desktop-as-a-vmm-device)), so a dropped connection never leaves the agent locked out or two controllers active; the agent still re-observes before acting.

Agent interaction pauses during takeover. Other sessions may continue, but they still share external account effects and workspace resources under [Main browser session with separate task sessions](#main-browser-session-with-separate-task-sessions). The agent must not bypass the pause through another automation path; enforcement against arbitrary programs in the sandbox is part of the browser and desktop design, not guaranteed merely by hiding browser tools from the model. The arbiter refuses agent input, and the tool user has no injection path to the person's display, though it can still send synthetic events and move the pointer on its own display.

Live viewing exposes website content and must follow content permissions. Controller access can exercise the website account's authority, so it is separate from permission to read recorded agent content. Login secrets entered during assistance must not be copied into model messages, ordinary action logs or screenshots: while a person holds control for a pending login, the arbiter refuses every agent request, screenshots and browser calls included, until control changes again. A login during takeover does not automatically authorize sharing that account with other agents or tasks beyond [Reuse authorized website logins across browser sessions](#reuse-authorized-website-logins-across-browser-sessions).

Record controller identity, session identity, takeover and release times, mode changes, every input event with its source and time, and relevant outcomes. This decision does not require permanent video recording or raw keystroke retention, and no recording contains pixels of a person's session. The live UI must identify stale or disconnected views and unavailable sessions honestly. Browser interaction on mobile requires appropriate touch and keyboard controls.

[Online console operations with local drafts](console.md#online-console-operations-with-local-drafts) requires online console operations. Disconnected browser input is not queued for replay; reconnecting requires establishing current control ownership and page state.

Consequences: Cubebot needs live media delivery, input arbitration, and handoff recovery. Active human control must be accounted for before an ordinary idle shutdown; exact timeout and keep-awake behavior remain open. This feature does not introduce mandatory per-action approval for autonomous agents.

**Rationale.** Users need to inspect ongoing browser work and directly assist with login or an interaction the agent cannot complete. Live viewing without input would allow observation but not direct assistance. Recorded screenshots and action history would reduce streaming needs but provide less immediate support. The user selected live viewing and takeover.

**What changed.** As accepted, viewing and takeover applied to a selected browser session, with a browser module owning per-session input authority and the ownership token, lease and reconnect protocol left open. [Desktop as a VMM device](#desktop-as-a-vmm-device) settled these on the agent's desktop: the arbiter's three modes, source-tagged input, refusal of agent input in `human` mode, the login-handoff refusal of screenshots, and live transport as changed 64x64 PNG tiles proxied by the orchestrator at most every 50 ms over the console's WebSocket. That decision does not say how a task session that is not on the desktop is viewed or taken over; the per-session requirements above still state the intent for it.
