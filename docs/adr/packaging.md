# Packaging and operations

This document covers how an installation is laid out and deployed, which PostgreSQL it runs on, how its first production milestone is qualified, and how it is backed up, restored and upgraded. Backups never pause work; upgrades use a maintenance window that controls writers. Sandbox runtimes, credential storage and durable data retention are covered in their own documents and linked where they constrain these decisions.

## One namespace for the entire installation

Accepted 2026-10-24. Amended 2026-10-27 and 2026-11-02: each agent pod runs one sandbox container, and an installation without a cluster runs sandboxes on Docker.

**Decision.** On Kubernetes, place the installation's namespaced resources in one dedicated namespace. This includes the orchestrator, frontend, bundled PostgreSQL, shared-storage claim, agent pods and per-agent workspace claims. The user selected this layout on 2026-10-24. An externally managed PostgreSQL service retains its existing location ([Bundled PostgreSQL by default with external PostgreSQL support](#bundled-postgresql-by-default-with-external-postgresql-support)); cluster-scoped infrastructure such as storage classes, persistent volumes and RuntimeClass resources is outside the namespaced-resource layout. Referencing an administrator-provided RuntimeClass is consistent with this layout and does not authorize Cubebot to manage the cluster's runtime configuration ([Standard containers with optional sandbox runtimes](sandbox.md#standard-containers-with-optional-sandbox-runtimes)).

Usage: an administrator installs Cubebot into a chosen namespace. The orchestrator provisions agent resources there and distinguishes them by stable installation and agent identity, recorded resource ownership and managed labels. Creating agents, rooms or teams does not create additional namespaces. Each agent pod runs one container: `cubebot-sandbox` with the agent in a KVM guest under the `kvm` runtime, or the agent image directly under the `container` runtime ([In-house VMM as the agent sandbox](sandbox.md#in-house-vmm-as-the-agent-sandbox)). Without a cluster, the orchestrator's Docker implementation of the same `Sandbox` interface runs one container per agent, and the namespace layout does not apply.

- **Ownership.** Installation configuration selects the namespace. The Kubernetes lifecycle module reconciles managed agent resources within it ([PostgreSQL owns agent definitions and lifecycle intent](agents.md#postgresql-owns-agent-definitions-and-lifecycle-intent)). Platform deployment owns the orchestrator, frontend and bundled dependencies. The orchestrator must distinguish those resources from agent resources during reconciliation and cleanup. Merely sharing the namespace does not authorize adoption or deletion.
- **Privileges.** Keep platform and agent privileges distinct through service accounts, scoped RBAC, credential mounts, application authorization and enforced network policies. Agents do not inherit the orchestrator's Kubernetes credentials or database access. Prefer namespace-scoped permissions for namespaced operations; any required cluster-level installation permissions must be separately identified. Exact RBAC rules remain engineering work.
- **Network.** Network rules select the intended workloads and preserve the public-internet default and explicit grants for private destinations ([Public internet access with grants for private destinations](sandbox.md#public-internet-access-with-grants-for-private-destinations)). Namespace membership must not implicitly allow agent-to-agent access or access to PostgreSQL, shared-storage mounts or platform management endpoints. Required agent-to-orchestrator communication still uses authenticated, authorized interfaces. NetworkPolicy enforcement requires a compatible cluster network implementation. Because each agent pod holds exactly one agent's sandbox, and a `kvm` guest's traffic leaves through a tap device in the pod's network namespace, pod-level NetworkPolicy governs exactly one agent.
- **Capacity.** Agents retain individual resource requests and limits and their own workspace claims. Namespace quotas, if configured, cover the shared namespace and therefore also affect platform workloads. Admission must account for platform capacity and report provisioning failures without losing accepted work. Exact capacity reservation and priority policies remain open.
- **Deletion.** Deleting the namespace affects the entire installation's namespaced resources. Sleeping, retiring or removing an agent must never delete the namespace or unrelated platform resources. Persistent data cleanup, uninstall behavior and restore follow explicit retention and backup policies ([Retain durable data until explicitly deleted](memory.md#retain-durable-data-until-explicitly-deleted), [Cubebot-coordinated backup and restore workflows](#cubebot-coordinated-backup-and-restore-workflows)) rather than treating namespace deletion as ordinary agent lifecycle management.

**Rationale.** Alternatives considered: separate platform and agent namespaces; a platform namespace plus one namespace per agent. The user selected a single namespace to keep the installation layout simple. Per-agent permissions and network restrictions remain requirements within that layout.

Platform references: [Kubernetes namespaces](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/) and [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/), reviewed during the preceding architecture discussion. These describe platform mechanisms, not tested Cubebot behavior.

**What changed.** As accepted, each agent pod held a trusted runtime container and a separate tool container sharing one pod network, and this decision noted that one namespace did not solve the runtime/tool distinction inside the pod: ordinary pod-level policies could not distinguish their callers, and the mechanism had to be designed and qualified. [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary) made the sandbox edge the trust boundary and dropped isolation between the runtime and its own tools, and [In-house VMM as the agent sandbox](sandbox.md#in-house-vmm-as-the-agent-sandbox) reduced the agent pod to one container, so that problem no longer exists. The same decision added Docker as the cluster-less place sandboxes run, outside any namespace.

**Open details.** Namespace naming and installation validation; resource labels and ownership records; RBAC and admission controls; network enforcement; quota and platform-capacity protection; workload objects; and uninstall and restore behavior.

**Validation scenarios.** Install into the selected namespace; create and replace agents without additional namespaces; prevent agents from accessing other workspaces and platform credentials; enforce network restrictions between selected workloads; retain platform operation under agent admission pressure; and remove one agent without changing unrelated resources. Implementation and cluster qualification remain pending.

## Bundled PostgreSQL by default with external PostgreSQL support

Accepted 2026-10-23. Amended 2026-11-03: the chart takes operator-made Secrets for the database password and the credential key.

**Decision.** Provide bundled PostgreSQL as the default installation mode and support connecting to externally provisioned PostgreSQL. The user selected this model on 2026-10-23. Both modes use the same Cubebot schema, persistence interfaces and qualified database requirements.

Usage: an individual installs Cubebot with a PostgreSQL workload and persistent database storage supplied by the installation package. An organization selects external mode and supplies connection configuration and credentials for its database. External mode does not also start an unused bundled database.

- **Ownership.** Installation packaging owns provisioning and configuration of the bundled database. In external mode, the operator owns database infrastructure, availability and service maintenance. Cubebot owns its application schema, migrations, connection management and compatibility checks in both modes. Migration authority and runtime database privileges must be explicitly designed; agents receive no database credentials ([Agent state access through the orchestrator](agents.md#agent-state-access-through-the-orchestrator)).
- **Compatibility contract.** The supported PostgreSQL versions, extensions, privileges and connection settings form one documented compatibility contract. Retrieval uses PostgreSQL full-text search and pgvector ([Hybrid memory retrieval](memory.md#hybrid-memory-retrieval)); extension availability must be qualified in both deployment modes. A database that accepts a connection is not necessarily a compatible Cubebot database. Unsupported requirements produce actionable diagnostics rather than silent feature loss.
- **Bundled deployment** requires persistent storage, credential lifecycle handling, health checks and documented upgrade and recovery procedures. This decision does not select an operator, chart dependency, container image, replication topology or database high-availability guarantee. Their selection must respect the installation's dependency-reduction goal and actual recovery requirements.
- **Generated secrets.** The chart generates the bundled database password and the credential key once and keeps them with `lookup`, which returns nothing under Argo CD or `helm template`; there every render would replace them, leaving the initialized database unreachable and stored credentials undecryptable. `postgres.existingSecret` and `credentials.existingSecret` name Secrets the operator owns instead, and both must be set under such tools. The orchestrator refuses to start when its key cannot decrypt a stored credential rather than encrypting new ones beside records it cannot read.
- **Connection secrets** are managed through installation configuration and must not appear in normal logs or agent environments. External connection verification and transport protection must be specified for the deployment context. External support does not authorize Cubebot to modify unrelated databases or perform provider-level administration.
- **Changing database mode** is a migration operation with backup, verification and a controlled cutover. Editing a connection setting alone does not transfer existing state. Application upgrades check schema compatibility and coordinate migrations with active orchestrator ownership; a failed migration must not leave an apparently ready installation serving incompatible state.
- **Recovery.** Database backups alone do not restore Cubebot. Recovery still needs matching shared-file storage and agent workspace data ([Durable storage](memory.md#durable-storage), [Orchestrator-managed file storage on a persistent volume](memory.md#orchestrator-managed-file-storage-on-a-persistent-volume)). External database availability guarantees do not extend automatically to the single orchestrator or its volumes. Cubebot coordinates application-level backup and restore for both database modes, using qualified database and storage mechanisms ([Cubebot-coordinated backup and restore workflows](#cubebot-coordinated-backup-and-restore-workflows)).

**Rationale.** Cubebot requires PostgreSQL for authoritative structured state. Personal installations need a complete deployment path, while organizations may already operate a database they want to reuse. Alternatives considered: require an external database, or support only the bundled database initially. Supporting both preserves a complete personal installation path and established organizational database operations without introducing separate persistence implementations.

**Open details.** Deployment packaging; supported versions and extensions; provisioning components; credential and TLS configuration; migration execution; bundled topology; backup mechanisms and privileges; mode-change procedure; and upgrade and restore qualification.

**Validation scenarios.** Install and restart with bundled storage; connect to a compatible external database; avoid provisioning bundled resources in external mode; reject missing requirements; preserve data during upgrade; fail readiness on incompatible schema; and verify a controlled migration between modes.

## Initial qualification at 100 registered and 25 working agents

Accepted 2026-10-23.

**Decision.** Qualify the first production milestone with 100 registered agents and 25 agents working simultaneously on meaningful goals and workloads. The user supplied these targets on 2026-10-23. These are acceptance targets, not hard product limits or evidence of current capacity. The longer-term ambition of thousands of agents remains unchanged.

- **Registered** means durable agent identities and configuration with representative retained history, memories, skills and workspace data. The remaining agents may sleep or be idle; their records must remain usable through the console. Empty placeholder identities alone are insufficient evidence for the intended workload.
- **Working** means distinct agents executing admitted work, including normal waits for model and tool results within that work. Starting 25 pods or keeping 25 idle connections open does not satisfy the target. Evidence must show sustained overlapping progress toward concrete outcomes. A wholly stalled population does not count as successful sustained work. Duration and acceptable waiting behavior remain to be specified with the workload.
- **Agent count is distinct from active turn count.** An agent may run several lanes ([Agent execution lanes](agents.md#agent-execution-lanes)), so the qualification reports active agents, active lanes, in-flight model calls, and tool and browser concurrency separately. The 25-agent target does not silently set the installation's lane cap to 25 or require every agent to run all lanes continuously.
- **Meaningful goals** need verifiable results: for example, a tested code change, a source-backed research report, or a diagnosed problem with supporting evidence. The workload is mixed organizational work across research, document production, software work and operational investigation, including specialist collaboration ([Mixed organizational workloads for initial qualification](#mixed-organizational-workloads-for-initial-qualification)). Proposed coverage includes independent tasks and delegated room work, tool and skill discovery, memory use and compaction, and artifact publication. Sleeping-agent wakeups and idle dreaming need separate phases consistent with their lifecycle rules; dreaming must not run alongside active work in the same agent ([Idle-only dreaming with visible status and results](memory.md#idle-only-dreaming-with-visible-status-and-results)).
- **Under use.** Qualification exercises the system while users inspect progress and send new work. Record task outcome quality and correctness alongside queue delay, control-plane latency, completion time, storage throughput, resource use and provider limits. Report hardware, storage class, model and connection configuration, data sizes and task mix so results are reproducible. Thresholds and evaluation rubrics remain open.
- **Recovery** qualification includes representative sandbox or orchestrator restarts, lost responses, and provider or tool failures, checking accepted-work preservation, uncertain outcomes and duplicate effects. Capacity measurement and fault injection can use separate labeled runs rather than pretending all conditions are one benchmark.
- **Evidence classes.** Controlled providers and tools can establish repeatable system behavior. Live-provider runs with realistic tools and inspected deliverables are also required before claiming end-to-end production qualification. Report those evidence classes separately; simulated load alone does not establish useful autonomous work or subscription-provider compatibility.

Ownership: the agent runtime and the orchestrator expose execution measurements; domain modules provide verifiable outcomes and recovery records. The qualification plan ties these measurements to acceptance criteria. No new production service or benchmark framework is selected by this decision.

**Rationale.** Cubebot's long-term ambition includes thousands of agents, and its first production milestone needs a concrete, useful workload against which to evaluate correctness, capacity and recovery. The alternative was to begin at 1,000 registered agents with 100 or 1,000 concurrently working. The user selected a smaller initial target with meaningful workloads, making useful behavior and recoverability the first acceptance focus.

**What changed.** As accepted, lanes were admitted by orchestrator scheduling, and execution measurements came from scheduling and runtime modules. Under [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary), lanes are a scheduling rule inside the agent's own loop and each agent runs in one sandbox, so the agent runtime reports its lanes and the restart scenarios cover sandboxes rather than separate runtime and tool containers. The targets are unchanged.

**Open details.** Workload proportions; run duration; task fixtures and quality rubric; data-volume baseline; browser and lane mix; hardware profile; latency and recovery targets; provider budget; and benchmark procedure.

**Validation scenarios.** Maintain 100 representative durable agents; demonstrate 25 distinct agents making overlapping progress; inspect concrete deliverables; retain responsive human interactions; wake sleeping agents; observe dreaming only when eligible; and recover representative interrupted workflows with honest outcome accounting.

## Mixed organizational workloads for initial qualification

Accepted 2026-10-23.

**Decision.** Use mixed organizational work as the initial qualification emphasis, covering research, document production, software work and operational investigation, including collaboration between specialists. The user selected this emphasis on 2026-10-23. The scale remains 100 registered agents with 25 working simultaneously ([Initial qualification at 100 registered and 25 working agents](#initial-qualification-at-100-registered-and-25-working-agents)).

Meaningful work is measured by concrete outcomes with evidence. Representative scenario candidates are below; their exact fixtures, proportions and scoring thresholds remain proposals.

| Workload | Goal | Evidence of completion |
| --- | --- | --- |
| Research | Compare alternatives against a supplied organization's requirements. | A source-backed comparison that addresses the requirements and distinguishes unresolved questions. |
| Document production | Turn source material into an operational guide or project brief. | A usable artifact checked for required content, factual consistency, and referenced inputs. |
| Software work | Diagnose and fix a reproducible issue in a test repository. | A focused change with tests demonstrating the intended behavior and relevant regression coverage. |
| Operational investigation | Investigate an injected fault in a controlled service environment. | A diagnosis supported by observations and a remediation or escalation consistent with the granted authority. |
| Cross-specialist collaboration | Combine delegated research, implementation, or review into a shared deliverable. | Traceable assignments, returned results, and a final integrated outcome with a responsible owner. |

- The concurrent population exercises multiple workload classes with substantive tool use and progress. The benchmark must not count task titles alone as diversity or count 25 delegates waiting on one blocked agent as useful throughput. Include independent work alongside collaboration; exact concurrency allocation remains open and is not fixed to five teams of five.
- Goal-driven scenarios exercise relevant platform behavior: room routing, delegation, tool and skill discovery, memory retrieval, compaction, browser and terminal tools, and artifact publication. Each individual scenario need not invoke every subsystem. Memory continuity is assessed across related tasks, and skill reuse is tested on a later suitable task rather than inferred from successful registration. Idle dreaming runs in separate eligible phases, with reported memory and skill changes checked against actual records.
- Controlled services and repositories provide known outcomes for repeatable tests, while live-provider trials establish behavior with actual inference. Keep those evidence classes labeled. Browser and integration actions that mutate external systems belong in authorized test environments; realistic qualification does not require publishing or modifying unrelated production resources.
- Quality and system capacity are separate acceptance dimensions. A run with responsive infrastructure but incorrect deliverables fails the relevant quality criteria. A run that produces good outputs while losing accepted work or starving the console fails the relevant system criteria. Report scenario-level results rather than hiding a failed workload class inside an aggregate completion rate.

Ownership: the qualification plan defines fixtures, goals, expected evidence and scoring. Domain modules expose operational records needed to trace outcomes. The selected workload mix does not narrow Cubebot's product scope to these examples or require a dedicated benchmark service.

**Rationale.** Cubebot is intended for many kinds of agent work, and qualification centered only on coding or browsing would leave important execution paths and collaboration patterns untested. Alternatives considered: software-engineering-first qualification, or research-and-browser-first qualification. Mixed work better represents the intended general-purpose installation and reveals competition between different kinds of tools and tasks.

**Open details.** Scenario selection and proportions; dataset sizes; collaboration topology; run duration; model and tool configurations; output rubrics; human evaluation; resource budget; latency and recovery thresholds; and repeatability requirements.

**Validation scenarios.** Produce inspectable deliverables across the selected classes; demonstrate overlapping progress by 25 agents; integrate delegated results without losing ownership; reuse relevant memory and skills on later work; keep console interactions responsive; and report workload-specific outcomes through recovery tests.

## Cubebot-coordinated backup and restore workflows

Accepted 2026-10-23. Amended 2026-11-07: an S3-compatible bucket is the destination, restore runs only into a fresh installation, and consistency is settled by [Backups without pauses](#backups-without-pauses).

**Decision.** Cubebot provides coordinated backup and restore workflows using established database and storage mechanisms. The user selected this model on 2026-10-23. Cubebot owns application-level coordination, completeness reporting and restore validation. The user selected on 2026-11-07: the destination is any S3-compatible bucket, signed with the S3 connector's Signature Version 4 code rather than an AWS SDK; administrators set the bucket, a daily schedule (or off, with Back up now), retention of 7 daily and 4 weekly backups, and bandwidth and concurrency limits from Helm values, `.env` or Platform › Backup, where a deployment value is read-only and names its source.

Usage: an authorized administrator starts a backup or configures a backup policy. Cubebot coordinates capture, records the included resources and recovery boundary, and reports a completed or failed backup with inspectable evidence. During restore, Cubebot validates the selected backup, restores its required components, and checks their relationships before allowing ordinary work to resume.

Ownership: a recovery module owns workflow identity, manifest state, progress and reconciliation inside the existing orchestrator ([One orchestrator process](agents.md#one-orchestrator-process)). Database, shared-storage and workspace modules expose the capture and restore operations needed for their state. Established database tools, supported snapshots or file-copy mechanisms perform the underlying data capture. This decision does not introduce a custom PostgreSQL backup engine or require a new always-running service.

- **Completeness.** A backup is a manifest (schema version, Cubebot version, newest migration, a key check, each part with its size and SHA-256, the shared-file blobs it needs and anything missing) plus its parts: one `pg_dump`, the blobs, and one tar per agent workspace. The manifest is written last. A backup counts as complete only after verification reads the manifest back, finds every part in the bucket at its size and re-reads a sample to compare checksums; one that fails loses its manifest. Missing parts, such as a stopped agent's workspace, are listed and make the backup incomplete, never silently skipped. Backups are not encrypted, so the bucket's own access control protects them. The credential key is never in a backup; the console offers one audited download to administrators, Compose prints it with `cubebot key`, and Helm keeps it in the credentials Secret ([Encrypted credentials with a separate installation key](identity.md#encrypted-credentials-with-a-separate-installation-key)).
- **Status.** Backup status distinguishes capture in progress, incomplete or failed capture, complete capture with verification, and a separately exercised restore. A successful database dump alone cannot mark the installation backup complete. Missing workspaces, unreadable files, failed checks or unavailable required keys are reported rather than omitted silently. Backup and restoration retries reconcile their existing workflow identity instead of repeating destructive steps blindly.
- **Consistency.** Nothing pauses; small differences between components are accepted ([Backups without pauses](#backups-without-pauses)).
- **Restore entrypoint.** Restore only happens into a fresh installation: when the orchestrator first starts on an empty database with a restore source configured (`restore:` in Helm values, or install.sh's answer in `.env`), it restores the newest verified backup or a named one before anything else runs. It checks the credential key against the manifest first and stops at once if it is wrong, then loads the database in one transaction and fetches the shared files; each agent fetches its own workspace through the orchestrator before it takes work. Until then the orchestrator serves only restore progress, and any failure stops the restore with a clear message. A marker on the shared-file volume lets an interrupted restore resume rather than start a half-restored installation. Once the database holds data the restore source is ignored, so it may stay set, as under Argo CD. Restoring into an existing installation is not supported.
- **After restore.** Restored tasks, triggers ([Routines](agents.md#routines)) and agent lifecycles are reconciled before execution resumes. A backup cannot undo external actions performed after its recovery point. Old assignments must not be replayed merely because their later completion is absent from restored state. External account validity and uncertain outcomes may require intervention. Restored access records do not prove that an external credential remains valid. Deletion in the active installation does not by itself erase backup copies ([Retain durable data until explicitly deleted](memory.md#retain-durable-data-until-explicitly-deleted)).
- **Destinations** are evaluated against the intended failure scenario. A copy on the same lost volume cannot recover that volume; protection against cluster loss requires surviving recovery data and keys elsewhere. No destination, external storage dependency, recovery-time target or data-loss interval is selected here.

**Rationale.** Cubebot's recoverable state spans PostgreSQL, orchestrator-managed file storage and persistent agent workspaces, and independent copies of those stores do not by themselves establish a consistent application recovery point. The alternative was to delegate the entire workflow to operators. Cubebot-owned coordination better supports personal installations and centralizes the application consistency rules while retaining established capture mechanisms.

**What changed.** The maintenance mechanics, left open here, were first settled as a coordinated maintenance window; on 2026-11-07 [Backups without pauses](#backups-without-pauses) replaced it. The same amendment chose the bucket destination, schedule, retention, key custody (one console download, `cubebot key`, the Secret) and the fresh-installation restore entrypoint, which had been open.

**Open details.** Resumed-work reconciliation beyond lifecycle recovery; recovery objectives; restore-drill procedure; restoring into an existing installation; and encryption at rest beyond the bucket's own.

**Validation scenarios.** Capture all required stores; report a missing component as incomplete; recover an interrupted backup; restore with the console unavailable; verify matching metadata and bytes; handle missing keys; prevent conflicting writers; and avoid automatic replay of uncertain external effects after rollback.

## Backups without pauses

Accepted 2026-10-23 as coordinated maintenance windows for backups. Amended 2026-11-07: backups never pause anything, and the small inconsistency between components is accepted.

**Decision.** Backups must never slow agents or the console. The user selected this on 2026-11-07, replacing the coordinated maintenance window. Cubebot captures each store with a mechanism that does not stop its writers and accepts that the components of one backup are minutes apart. Platform › Backup says so plainly.

Usage: a backup runs daily or when an administrator presses Back up now, while agents keep working and people keep using the console. The tab shows it running, then verified, incomplete with its missing parts, or failed with the reason.

Ownership: the orchestrator's backup module runs one worker that captures, verifies and prunes, and caps the transfers it runs at once and the bandwidth they share. Agents stream their own workspaces through the orchestrator; they never receive the bucket's credentials.

- **Database.** `pg_dump` reads one consistent snapshot without blocking writes. The orchestrator exports that snapshot and lists the shared-file blobs in it, so the dump never names a blob the backup leaves out.
- **Shared files.** Blobs never change once written, so each goes to the bucket once and later backups send only new ones. A blob is deleted from the bucket only when no retained backup's manifest names it.
- **Workspaces.** Each running agent is asked over its runtime channel and streams its workspace as a tar at the lowest CPU and I/O priority, as the tool user, through the orchestrator. A file changed while it is read is accepted. A stopped agent, or one that does not answer within ten minutes, is listed as missing.
- **Accepted inconsistency.** A restored agent's workspace can be minutes newer than its conversation or the shared files, and a file deleted during a backup can be missing from it. Restored external tokens are never claimed to work.

**Rationale.** The maintenance window made one cross-store recovery point easy to qualify but paused all work for every backup, and a personal installation that backs up daily would pause daily. The user judged a visible, small inconsistency better than any pause.

**What changed.** As accepted on 2026-10-23, Cubebot stopped admitting work, brought agents and writers to checkpoints, fenced disconnected agents, captured, then resumed. That barrier, its drain deadlines and its ingress rules no longer apply to backups; upgrades keep their own maintenance window ([Coordinated maintenance upgrades](#coordinated-maintenance-upgrades)).

**Open details.** Snapshot-based capture where storage supports it; measured effect on agent latency under the bandwidth cap; and a consistent point across stores, should one be needed later.

**Validation scenarios.** Back up while agents work and see no pause; report a stopped agent's workspace as missing; send only new blobs on a second backup; refuse a backup whose parts are absent in verification; prune by retention without deleting a needed blob; and restore a fresh installation with its data and workspace files.

## Coordinated maintenance upgrades

Accepted 2026-10-24. Amended 2026-10-27: disconnected agents are fenced by revoking their credential or stopping their sandbox.

**Decision.** Upgrade Cubebot through a coordinated maintenance window. Stop admitting new work, bring affected execution and writers to safe checkpoints, upgrade platform software and agent runtimes, then resume eligible work after recovery checks. The user selected this model on 2026-10-24. Continuous operation with mixed agent-runtime versions is outside the initial upgrade contract.

Usage: an administrator starts an upgrade. Cubebot reports preparation and draining, identifies any operation that cannot settle, applies the release's migrations and workload changes once safe, verifies recovery, and reopens admission. Agents continue from durable progress where possible. Live browser sessions and arbitrary processes may need to restart; replacing an agent's sandbox ends everything running in it.

Ownership: a durable maintenance workflow coordinates admission, checkpoints, lifecycle changes and recovery. Each agent accounts for its active work and filesystem writers inside its sandbox. Persistence owns migrations and data compatibility. Deployment tooling applies release artifacts and must be able to report or recover a failed upgrade when the ordinary application process is unavailable. Exact packaging and command interfaces remain engineering choices.

- **Writer control.** Stop admitting new work and bring writers to safe checkpoints, as backups once did before [Backups without pauses](#backups-without-pauses). Account for dreaming, extraction, tool processes, browser activity, uploads, skill publication, background workers and configuration changes as applicable. Disconnected agents must acknowledge checkpoints or be fenced by revoking their credential or stopping their sandbox. Missing heartbeats do not establish a clean checkpoint. Drain deadlines expose blockers and defer or fail the upgrade; forced termination is not proof of preserved process state.
- **Ingress.** New requests receive explicit maintenance behavior. Never acknowledge acceptance unless the work is durably retained across the upgrade. If database migration prevents safe acceptance, return a retryable maintenance response and retain local drafts ([Online console operations with local drafts](console.md#online-console-operations-with-local-drafts)). Exact queuing and read-only availability during each phase remain open.
- **Durable progress.** Track upgrade progress durably outside assumptions about a particular process surviving. Restart reconciles which release, schema and agent versions are present before enabling execution. Temporary version differences during replacement do not imply supported mixed-version work: incompatible agents remain blocked from new assignments until replaced or recovered. An interrupted migration or failed rollout must not silently reopen the installation.
- **Resume.** Resume rechecks execution ownership, pending tool outcomes, permissions, cancellations and configured budgets. Keep explicitly cancelled, budget-paused or otherwise blocked work in its appropriate state. A checkpoint cannot justify replaying an external action whose outcome is uncertain. Agent identity, recorded progress, history and workspace files survive subject to the durable storage contract; in-memory state is not promised to survive.
- **Release recovery path.** Each release needs a documented migration and recovery path, with a coordinated recoverable backup before changes that require one. Do not assume deploying an older image reverses schema or data changes. Recovery may require restoration of a compatible database, shared files, workspaces and keys ([Cubebot-coordinated backup and restore workflows](#cubebot-coordinated-backup-and-restore-workflows)). The release states whether rollback or forward repair is supported and how unresolved external effects are handled. In a `kvm` installation the sandbox image always carries the guest kernel and root image, so a release replaces them together ([In-house VMM as the agent sandbox](sandbox.md#in-house-vmm-as-the-agent-sandbox)).

Upgrades interrupt coordination and console operations until recovery succeeds, consistent with one active orchestrator ([One active orchestrator with automatic restart](agents.md#one-active-orchestrator-with-automatic-restart)).

**Rationale.** The alternative was to upgrade the orchestrator while compatible older runtimes keep working, then replace agents gradually. The user selected maintenance upgrades, accepting interruption and avoiding a requirement for continuous mixed-version execution in the initial architecture.

**What changed.** As accepted, runtime and tool modules accounted for active work, and disconnected agents were fenced under their finite per-turn authority. [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary) moved tools into the agent's own sandbox and replaced finite authority with one long-lived agent credential, so fencing now means revoking that credential or stopping the sandbox.

**Open details.** Release packaging; migration tooling; exact phase states and deadlines; maintenance ingress; backup prerequisites; version compatibility checks; upgrade diagnostics; and rollback versus forward-repair procedures.

**Validation scenarios.** Drain active and delegated work; report an unsafe tool operation; account for a disconnected writer; preserve drafts and accepted work; recover an interrupted upgrade or migration; block incompatible agents; verify storage and authentication before resuming; retain cancellation and pause state; and resume without duplicating external actions. Implementation and upgrade qualification remain pending.
