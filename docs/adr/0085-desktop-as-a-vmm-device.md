# ADR 0085: Desktop as a VMM device

Status: Accepted

Date: 2026-10-30

Amended: 2026-10-30, to keep the agent's own screenshots in the turn ledger (see "Agent screenshots are ledger evidence").

ADR 0083 puts the agent's terminal, browser and computer use inside one sandbox, and ADR 0084 makes that sandbox a guest of Cubebot's own VMM. Neither says who owns the guest's screen and input. A desktop run entirely inside the guest, such as a VNC server, would let anything in the guest, including agent-run code, produce the frames a person sees and the input they appear to have sent. Nothing could then tell agent input from human input, or keep the agent off the controls while a person holds them.

Decision: The sandbox host owns the desktop as VMM devices. The user selected this on 2026-10-30.

- **Screen.** `cubebot-sandbox` serves a virtio-gpu device with the 2D command set only (no virgl, no 3D, no blob resources). The guest's scanout is copied into a framebuffer in the sandbox process when the guest transfers and flushes it, so a screenshot is the host's copy of what the guest last presented, not something the guest produces on request.
- **Keyboard and pointer.** Two virtio-input devices, a keyboard and an absolute pointer, are the guest's only input devices. The guest kernel has no uinput, and the guest display server takes input only from its evdev devices, with no XTest or equivalent injection path, so input reaches the desktop only through the host.
- **One arbiter.** An arbiter in the sandbox process is the only reader of the framebuffer and the only writer to the input queues. It serves screenshots and input to the agent over a vsock port of its own, and to the orchestrator over the sandbox host's channel to it.
- **Three modes.** `agent`: the agent drives and no person is connected. `watch`: the agent drives and people see the screen read-only. `human`: one person holds control. The arbiter holds the mode; a person takes and releases control through the orchestrator, and the agent is told of every change.
- **Input is tagged and refused at the host.** Every input event carries its source, the agent or the person's account, as the arbiter receives it. In `human` mode the arbiter refuses agent input with an error naming the mode and drops nothing silently; screenshots stay available to the agent so it can resume from what the person left. In `agent` and `watch` modes person input is refused unless that person has taken control.
- **The orchestrator proxies, never holds pixels.** The orchestrator authorizes and forwards desktop sessions between the browser and the sandbox and records them: who connected, mode changes, and every input event with its source and time. It forwards frames without decoding, storing or caching them, and no recording contains pixels.
- **Agent screenshots are ledger evidence.** A screenshot the agent takes through its computer-use tool is that tool call's result, and like every tool result it is committed to the turn ledger, as a `screenshot` outcome with the PNG. It is the evidence of what the model saw when it acted, kept and deleted with the conversation (ADR 0079). This covers only frames the agent requested for a tool call; frames of a person's desktop session are still never stored. Views of the conversation in the console and the replay of earlier tool events to the agent leave the image out, and the agent's local crash journal records the result without it, since a screen is not an effect to recover.

Usage: The agent's computer-use tools take screenshots and send keys and pointer events to its desktop port. A person opens the agent's desktop in the console, which starts a `watch` session; taking control switches to `human`, and releasing it or disconnecting returns the arbiter to `watch` or `agent`. The session record shows which input came from the agent and which from each person.

Rationale: The VMM already sits between the guest and everything outside it, so it is the one place that can see every frame and every input event without trusting the guest. Owning the devices makes the source tag and the `human`-mode refusal properties of the host rather than promises of guest software the agent can modify. virtio-gpu 2D and virtio-input are small, well-specified virtio devices that fit the existing virtio-mmio transport and queue code; a framebuffer copy needs no GPU on the node. Keeping pixels out of the orchestrator keeps it a control plane: its storage and memory do not grow with screen sessions, and recordings stay reviewable text.

Relationship to other decisions: This adds devices to ADR 0084's device set and an input path to ADR 0083's sandbox; its single trust boundary is unchanged. The desktop belongs to the agent's sandbox, so ADR 0083's coarse agent authority still governs what desktop applications can reach. A desktop needs more than ADR 0084's single vCPU and 256 MiB, which closes that ADR's sizing detail: the sandbox runs one thread per vCPU and boots with 2 vCPUs and 2 GiB by default, each configurable up to the VMM's limits.

Consequences: The device surface to review and fuzz grows by two device types, and the 2D command parser handles guest-supplied resource sizes and backing pages, so it bounds both. The sandbox gains a host channel to the orchestrator, which needs its own authentication as the sandbox's attempt. The guest kernel and root image gain virtio-gpu DRM, virtio-input and a display server, and lose uinput. Frames cross the orchestrator, so desktop sessions cost it bandwidth but not storage. Agent-run code inside the guest can still draw anything on the screen; what it cannot do is send input as a person or bypass the arbiter's mode.

Alternatives considered: A VNC or RDP server in the guest, which leaves frames and input under guest control and cannot attribute input. Screenshots by a guest tool, which the agent can replace. Storing recordings with frames in the orchestrator, which turns the control plane into a media store. A full virtio-gpu with virgl or Venus, which needs host GPU stacks and a far larger parser for no benefit to a desktop the agent reads as images.

Open details: The frame encoding and rate between the orchestrator and the browser; display resolution and whether the guest may change it; recording retention, which follows ADR 0079's explicit deletion. Settled in the first implementation: the root image runs Xorg with the modesetting and evdev drivers, openbox, xterm and Chromium as the tool user; screenshots are PNG; the agent's requests are JSON lines on vsock port 1025 (`cubebot_protocol::desktop`); and the host channel is `cubebot-sandbox desktop`, which the orchestrator runs through the platform's exec into the sandbox container, so it authenticates with the platform's exec authorization for that container.

Validation scenarios: A screenshot through the agent's port and one through the orchestrator show the same frame. Input from the agent and from a person appear in the session record with their own sources. While a person holds control, agent input is refused with the mode named and has no effect on the guest; screenshots still succeed. A process in the guest cannot create an input device or inject input into the display server. No orchestrator storage, log or recording contains frame data from a person's desktop session; the only stored frames are the agent's own screenshots, each in the ledger beside the tool call that took it.
