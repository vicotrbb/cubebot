# Identity, access and credentials

This document covers who an installation belongs to, who owns its agents, how people sign in, are admitted, grouped into teams and granted access, and how the installation's provider, integration and external account connections are owned, shared, refreshed and stored. It ends with the vault an agent fills logins from and the encrypted credential store every secret lives in. Agent execution, the sandbox boundary and memory are covered in their own documents and linked where they constrain these decisions.

## Installation and tenancy

Accepted 2026-10-22.

**Decision.** One individual or organization owns each installation (Option A). The user selected this on 2026-10-22. Each installation has one owner. Multiple users, teams, rooms and agents may operate within it, subject to internal permissions. An organization can have multiple users, teams, private rooms, agents and scoped integrations, and internal access controls remain necessary: one owning organization does not imply that every member or agent can access all organization data. Independent organizations operate separate installations, which may share underlying infrastructure if its isolation policy permits. This decision does not require a dedicated Kubernetes cluster per installation.

Related decisions within this model: agents are installation-owned with assigned managers and scoped access ([Agent ownership](#agent-ownership)); installation administrators have full content access by default ([Administrator content access](#administrator-content-access)); human sign-in uses installation-wide built-in accounts and optional OpenID Connect, with one shared identity and authorization model across the platform ([Platform-wide built-in accounts and optional OpenID Connect](#platform-wide-built-in-accounts-and-optional-openid-connect)).

**Rationale.** Option A directly serves the self-hosted audience and reduces the isolation and administration rules the initial implementation must own. The alternative, Option B, let one installation host multiple independent organizations: a platform operator manages shared infrastructure while organization administrators manage their own users and agents, tenant isolation must apply throughout storage, scheduling, credentials, memory retrieval, tool execution and operational access, and the operator's access to tenant data must be defined separately. Shared tenancy for unrelated organizations is outside the initial design. A future hosted offering can use separate installations or introduce shared tenancy through a later decision; shared tenancy is not guaranteed to be a configuration-only change.

**What changed.** This decision left administrator powers, member permissions and infrastructure isolation to separate decisions. Administrator content access was settled by [Administrator content access](#administrator-content-access); the permission model (built-in roles with scoped grants, no custom roles) by [Built-in roles with scoped resource grants](#built-in-roles-with-scoped-resource-grants); and isolation inside an installation by [One namespace for the entire installation](packaging.md#one-namespace-for-the-entire-installation) and one sandbox per agent under [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary) and [In-house VMM as the agent sandbox](sandbox.md#in-house-vmm-as-the-agent-sandbox). None of these settles isolation between installations that share underlying infrastructure.

**Open details.** The remaining administrator powers; the member permission matrix (it stays open under [Built-in roles with scoped resource grants](#built-in-roles-with-scoped-resource-grants)); and the isolation policy for installations that share underlying infrastructure.

**Validation scenarios.** An individual manages personal agents; colleagues use private and shared rooms; an agent attempts to retrieve unauthorized memory and is refused; a credential is revoked during active work. These scenarios will be refined as the permission model is specified.

## Agent ownership

Accepted 2026-10-22.

**Decision.** All agents belong to the installation, with assigned managers and scoped access. The user selected this model on 2026-10-22. Creating an agent does not make its lifecycle depend on the creator's account. A private assistant and a shared specialist use the same ownership model.

Managers administer agents according to permissions. Ownership alone does not grant every installation member access to an agent. Management authority, conversation access, memory access, workspace access and credential use require separately defined permissions. Installation ownership does not transfer ownership of a user's provider credentials or preserve authorization after those credentials are revoked.

An agent's durable identity and history can remain after its creator's account is removed. Continued execution still depends on valid managers, permissions, credentials and operating policy. Account removal must not silently confer new authority on the agent or other users.

Installation administrators have full content access by default ([Administrator content access](#administrator-content-access)); agent management alone does not confer that role. Provider connections are installation-managed only ([Installation-managed provider connections](#installation-managed-provider-connections)); external account ownership and authorization remain distinct from ownership of Cubebot records. Users and teams receive built-in roles and scoped resource grants, without installation-defined custom roles initially ([Built-in roles with scoped resource grants](#built-in-roles-with-scoped-resource-grants)).

**Rationale.** The model must support private assistants and shared specialists, including continuity when their creator leaves. User-owned agents would require ownership transfer or another lifecycle decision when a user leaves. Supporting both user-owned and installation-owned agents would introduce separate ownership categories and transfer rules. The selected model supports the intended personal and organizational deployments with one lifecycle model.

**Open details.** The exact permission matrix; manager assignment and transfer rules; behavior when no manager remains; and handling of active work during revocation.

**Validation scenarios.** A creator leaves while an agent has an active task; a new manager takes responsibility without automatically acquiring unrelated private content; a credential behind an installation-managed provider connection is revoked; an agent is shared with a team under explicit grants. Expected transitions will be specified with the permission and execution models.

## Administrator content access

Accepted 2026-10-22.

**Decision.** Installation administrators have full content access by default. The user selected this model on 2026-10-22. Administrators can inspect all agent conversations, memories and workspace files, including content private to ordinary members. No exceptional-access override or additional content grant is required for an administrator.

Direct access to private content is restricted for unauthorized ordinary members, not installation administrators. Product language and permission displays must communicate that distinction. An agent manager is not automatically an installation administrator. This decision does not grant ordinary users or agents direct access to other users' private content. Under [Unified memory per agent](memory.md#unified-memory-per-agent), an agent may nevertheless reuse knowledge learned from private conversations in other contexts; transcript access restrictions do not isolate its knowledge.

Scope: this decision concerns reading agent content. Credential disclosure, credential use, destructive operations, role assignment and audit logging remain separate decisions. Full content access does not by itself settle those permissions.

**Rationale.** The selected model gives installation administrators direct access for organizational oversight and troubleshooting, using one ordinary administrative role rather than an exceptional-access workflow. Two alternatives were declined in favor of default administrative access: scoped access with an explicit audited override, which would make private-content inspection a separate deliberate action; and scoped access with no administrator override, which would require an ordinary content grant.

**Open details.** Role revocation behavior, to be specified with the authorization model.

**Validation scenarios.** An administrator can inspect private agent content without a special override; an ordinary member without a content grant is denied; assigning an agent manager does not implicitly grant installation-wide content access.

## Platform-wide built-in accounts and optional OpenID Connect

Accepted 2026-10-23.

**Decision.** Support built-in user accounts plus optional OpenID Connect, managed centrally for the entire Cubebot installation. The user selected this model on 2026-10-23. Both sign-in paths use the same platform identity and authorization model across human-facing features: the management console, chat and installed PWA. Individual agents, rooms and frontend surfaces do not maintain separate human account systems.

Usage: an individual operates Cubebot using a built-in account. An organization configures its identity provider for sign-in. A user accesses chat, agent management, memories, trigger configuration and browser viewing or takeover according to their Cubebot permissions, whether using the web console or the PWA.

Ownership: an identity module within the orchestrator owns human accounts, configured login methods, external identity associations and platform sessions. An OpenID Connect adapter handles the external authentication flow. Authorization owns roles and resource access. Frontend clients use this shared boundary; they do not independently decide access from login claims. This follows [One orchestrator process](agents.md#one-orchestrator-process) and does not require a separate identity service.

- Installation administrators manage authentication configuration. Successful authentication identifies a person but does not automatically confer membership, administrator status, agent management or private-resource access. Admission uses invitations and optional administrator-configured OpenID Connect rules ([Invitations and optional OpenID Connect admission](#invitations-and-optional-openid-connect-admission)); roles and scoped grants follow [Built-in roles with scoped resource grants](#built-in-roles-with-scoped-resource-grants); human team membership is kept entirely in Cubebot ([Human teams managed entirely in Cubebot](#human-teams-managed-entirely-in-cubebot)). [Administrator content access](#administrator-content-access) applies after the role is assigned.
- Platform user records have durable internal identities independent of a particular login method. Connecting another login identity to an existing account requires a defined verified linking process; matching a display name or email alone must not silently merge accounts. Removing or disabling a login method must not transfer ownership of installation-owned agents or confer new authority.
- Platform human sign-in is separate from model-provider authentication, external integration accounts, website logins used by agents and agent-to-orchestrator authentication. A person's Cubebot session does not automatically become an agent credential or authorize use of that person's external accounts.
- All protected human-facing operations enforce the same identity and access decisions at the backend, including streaming and interactive browser controls. The console and PWA share account lifecycle rules; they need not share a literal browser session. Logout, account suspension, session expiry and role changes require consistent enforcement, with exact session and connection termination behavior specified before implementation.

**Rationale.** Human authentication must be consistent across the console, chat and the installed PWA, for personal installations and for organizations with existing identity systems. Alternatives considered: built-in accounts only, which leaves organizations managing separate credentials; or an external identity provider only, which adds a prerequisite for personal installations. Supporting both meets the intended audiences while preserving one platform account and permission model.

**What changed.** Admission mechanics were settled as invitations plus optional automatic OpenID Connect admission, and initial administrator setup was settled by the 2026-11-02 bootstrap rule, both in [Invitations and optional OpenID Connect admission](#invitations-and-optional-openid-connect-admission). The remaining membership lifecycle details are listed there.

**Open details.** Built-in login mechanism; account recovery and MFA; session storage and expiry; identity linking; supported provider configuration; whether local login can be disabled; emergency access; and human API credential support.

**Validation scenarios.** Sign in using either configured method; apply identical resource restrictions across console and PWA; deny access based solely on an untrusted role claim; prevent unsafe account linking; enforce suspension across protected operations; preserve agents when a user leaves; and report identity-provider unavailability without bypassing authentication.

## Invitations and optional OpenID Connect admission

Accepted 2026-10-23. Amended 2026-11-02: a new installation is open for exactly its first account, which becomes the administrator. Amended 2026-11-06: a deployment may name that administrator.

**Decision.** Use invitations or authorized account creation for built-in membership, with optional automatic admission through administrator-configured OpenID Connect rules. The user selected this model on 2026-10-23. Open public registration for built-in accounts is outside this model.

Usage: an administrator invites a colleague to join. Alternatively, an organization enables automatic admission for eligible users of its configured identity provider. At first successful qualifying login, Cubebot creates the member record with the configured baseline role. An authenticated identity that does not qualify and has no existing admitted membership receives no platform access.

Ownership: the orchestrator's identity module owns invitations, membership and admission decisions. Installation administrators configure automatic admission and its baseline role. Authorization determines who may invite or create members and enforces the permissions of resulting memberships. Delegation of invitation authority remains to be specified.

- **Automatic admission** is disabled unless configured. Rules apply to a specific trusted provider and validated identity attributes, using explicit eligibility criteria; the exact rule vocabulary remains open. A provider role or group claim does not independently grant Cubebot privileges; admission and any later role mapping follow installation configuration.
- **Baseline authority.** New members receive only their configured baseline authority. Membership does not automatically grant access to private agents, rooms, memories or workspaces. The detailed matrix under [Built-in roles with scoped resource grants](#built-in-roles-with-scoped-resource-grants) must make baseline access and any privileged assignment explicit. This decision does not select automatic administrator assignment or group synchronization; team membership stays local ([Human teams managed entirely in Cubebot](#human-teams-managed-entirely-in-cubebot)), and admission does not synchronize identity-provider groups into teams.
- **Invitations** have a defined recipient or redemption constraint, expiry, revocation and one-time acceptance semantics. Concurrent acceptance or repeated qualifying logins must not create duplicate memberships. Account linking follows the verified linking requirement in [Platform-wide built-in accounts and optional OpenID Connect](#platform-wide-built-in-accounts-and-optional-openid-connect) rather than silently merging records by email.
- **Lifecycle.** Suspending a member must prevent automatic admission from silently recreating or reactivating that membership. Ongoing eligibility, identity-provider changes, member removal and re-admission require explicit lifecycle rules. The first-login admission decision alone does not establish continuous synchronization with an organization's directory.
- **Initial administrator provisioning** is a separate bootstrap path, not public registration. A new installation is open for exactly its first account, which becomes the administrator. The console's setup form or the unauthenticated `POST /api/identity/setup` creates it and signs it in; the operator CLI (`cubebot-admin bootstrap`, `cubebot admin`) and a deployment-provided administrator, which the orchestrator creates at start from `CUBEBOT_BOOTSTRAP_LOGIN` and `CUBEBOT_BOOTSTRAP_PASSWORD_FILE` (the Helm chart's `admin` values) while setup is open, are the others. Both run the same bootstrap under the installation row's lock, so concurrent attempts yield one administrator, and setup closes permanently once either succeeds. Setup takes no invitation, so until it closes, whoever reaches the console first claims the installation; operators exposing a public domain before signing in should use the CLI or the deployment's administrator.

**Rationale.** Platform authentication establishes identity, but an installation also needs to control who may become a member. Personal installations need explicit admission; organizations may want eligible employees to join through their existing identity provider. Alternatives considered: admit every member individually, including identity-provider users; or allow optional public built-in registration. The selected model supports organizational onboarding without requiring an open registration surface.

**Open details.** Invitation delivery and redemption; delegated inviter authority; eligibility rule vocabulary; baseline roles; changes to eligibility; account removal and re-admission; and lifecycle audit records.

**Validation scenarios.** Open setup on a fresh installation, refuse it once bootstrapped by either path, and create one administrator from concurrent attempts; accept a valid invitation once; reject expired or revoked invitations; admit an eligible identity-provider user when enabled; deny automatic admission when disabled or ineligible; prevent duplicate membership and unsafe linking; enforce baseline resource restrictions; and prevent login from undoing a suspension.

## Built-in roles with scoped resource grants

Accepted 2026-10-23.

**Decision.** Use Cubebot-defined roles and permissions with scoped resource grants assigned to users or teams. The user selected this model on 2026-10-23. Installation-defined custom roles are outside the initial design. Exact built-in role names and their permission matrix remain to be specified.

Usage: an administrator grants a team conversation access to a particular agent and its shared room. A designated manager can administer that agent within their assigned scope. Another user may inspect memory without editing it. These distinctions must be expressible through the built-in roles and supported scoped grants, without requiring a custom role definition.

Ownership: the authorization module owns role definitions, grants and effective-access evaluation. Identity and team membership supply the human subjects to which grants apply. Domain modules enforce authorization for their operations through this shared boundary. The console exposes assignments and effective access; frontend visibility alone does not enforce permissions.

- A grant identifies its recipient, permitted built-in role or supported permission, and resource scope. Installation-wide administration remains distinct from managing a particular agent. An agent manager does not become an installation administrator, and conversation access does not implicitly include memory editing, workspace modification, browser takeover or credential administration. The detailed matrix must preserve the separations selected in the earlier decisions.
- [Administrator content access](#administrator-content-access) remains in force. Administrator access to content does not by itself settle credential disclosure or every destructive operation. Initial membership and its baseline role under [Invitations and optional OpenID Connect admission](#invitations-and-optional-openid-connect-admission) do not automatically confer access to private resources.
- Grant-management authority is itself scoped. A delegated manager cannot confer more authority than they are allowed to assign. Access evaluation accounts for current user status, team membership and resource grants, and produces an explainable result. Combination rules, revocation propagation and any explicit-deny semantics remain to be designed; this decision does not introduce a general policy language.
- Human roles are separate from agent execution grants. Giving a person access to chat with an agent does not create new tool permissions for that agent. Likewise, agent tool access does not grant a human access to its stored credentials or unrelated content. Unified agent memory ([Unified memory per agent](memory.md#unified-memory-per-agent)) remains a shared knowledge pool across that agent's work; transcript restrictions do not create separate memory partitions.
- Human team membership is entirely local to Cubebot, without identity-provider group synchronization ([Human teams managed entirely in Cubebot](#human-teams-managed-entirely-in-cubebot)).

**Rationale.** Cubebot needs consistent human permissions for administration, agent management, conversations, memory, workspaces and interactive controls, and organizations need to share selected resources with teams without granting installation-wide authority. The alternative was built-in roles plus installation-defined custom permission bundles. Custom roles offer organizational naming and reuse but add configuration, migration and explanation requirements. Built-in roles with scoped grants are selected for the initial product.

**Open details.** Role and permission matrix; resource scope types; delegated team administration; grant combination and delegation rules; access explanations; and revocation behavior for active sessions and operations.

**Validation scenarios.** Grant team access to selected resources; deny access outside the grant; separate reading from editing and viewing from takeover; prevent a manager from assigning greater authority; preserve administrator content access; explain access inherited through a team; and enforce membership or grant removal according to the defined revocation contract.

## Human teams managed entirely in Cubebot

Accepted 2026-10-23.

**Decision.** Manage human teams and their membership entirely in Cubebot. The user selected this model on 2026-10-23. Authorized humans add and remove members locally. Identity-provider groups do not create, synchronize or change Cubebot team membership. OpenID Connect remains responsible for sign-in and optional admission under [Platform-wide built-in accounts and optional OpenID Connect](#platform-wide-built-in-accounts-and-optional-openid-connect) and [Invitations and optional OpenID Connect admission](#invitations-and-optional-openid-connect-admission).

Usage: an administrator creates an Engineering team, adds admitted installation members, and grants the team access to selected agents and rooms. A member's external group changes do not alter that local membership. A user admitted automatically through OpenID Connect receives the configured baseline authority and joins teams through Cubebot's local management process.

Ownership: the orchestrator's identity and membership module owns team records and membership changes. Authorization owns team-scoped grants and evaluates them against current local membership. Team administration uses the platform's shared human identity and authorization boundary. Exact delegated team-management powers remain to be specified.

- Human teams are access-control groups, distinct from rooms, agent teams or delegated agent work. Creating a human team does not create agents or a conversation. The installation continues to own agents regardless of who belongs to a team with access to them.
- Team changes record the actor and affected membership and support explanation of effective access. Removing a member removes access derived from that membership according to the revocation contract. The person may retain access through a separate direct grant or another team; the console must make those remaining sources understandable. Suspension of an installation member prevents use of team-derived access even if membership records remain.
- Managing team membership and assigning grants to a team are separately authorized operations. Adding someone to a privileged team conveys its existing access, so delegated membership administration must respect the permitted scope. The exact role matrix and delegation limits remain part of [Built-in roles with scoped resource grants](#built-in-roles-with-scoped-resource-grants).

**Rationale.** Human teams group installation members for scoped access, and Cubebot needs a single authority for that membership when users may sign in through either built-in accounts or OpenID Connect. Alternatives considered: local teams with optional identity-provider group mapping, or exclusively provider-managed teams. Local management gives both login methods the same team workflow and avoids synchronization and conflicting membership sources in the initial design.

**Open details.** Team creation and deletion rights; delegated membership administration; team deletion effects on grants; membership audit presentation; and revocation timing for active sessions and operations.

**Validation scenarios.** Add and remove members locally; apply team-scoped grants; preserve local membership across external group changes; prevent login from restoring a removed team membership; deny unauthorized membership changes; explain access through multiple grants; and deny suspended users despite retained membership records.

## Installation-managed provider connections

Accepted 2026-10-23. Amended 2026-10-25: enabled connections are available to all eligible agents by default, with a per-connection specific-grants mode. Amended 2026-10-27: provider material is propagated to each agent's sandbox for its lifetime rather than per turn. Amended 2026-11-05: a connection signed in with a personal subscription is personal ([Personal subscription connections](#personal-subscription-connections)).

**Decision.** Support installation-managed provider connections, plus personal subscription connections under [Personal subscription connections](#personal-subscription-connections). The user selected this model on 2026-10-23. Installation administrators configure connections and choose each connection's access: all eligible agents (the default) or specific grants, under [Installation-wide connection access by default](#installation-wide-connection-access-by-default). Apart from personal subscription connections, Cubebot does not introduce a separate category of user-owned personal provider connections.

Usage: an administrator configures a provider connection and chooses all-agents access or specific grants. A manager selects from effectively authorized connections. New agents receive the all-agents baseline automatically; human users still require their applicable management permissions. A single-person installation follows the same model through its administrator account.

- Installation-managed describes ownership of the Cubebot connection record and its administration. It does not transfer ownership of an external account, change subscription eligibility or guarantee continued authorization. Supported API credentials, subscription authentication and local-model endpoints can fit this ownership model; actual authentication paths still require qualification under [Native Rust agent engine](agents.md#native-rust-agent-engine). A connection need not have a secret when its supported endpoint does not require one.
- The connection record is independent of the administrator account that created it. Removing that administrator must not silently delete the connection or expand anyone else's authority. Continued use still depends on valid external authorization, an authorized administrator, agent eligibility and installation policy. External revocation or required reauthentication remains a real loss of access even when the Cubebot record survives.
- Ownership: provider configuration owns connection metadata and lifecycle. Authorization owns agent-use grants and administration rights. Provider adapters implement supported authentication behavior and inference. The orchestrator propagates applicable authentication material to authorized agent sandboxes for their lifetime, and agents call providers directly ([Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication), [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary)). Runtime credential access does not imply user, model or tool permission to inspect or export the secret. The orchestrator alone owns refresh ([Orchestrator-owned provider authentication refresh](#orchestrator-owned-provider-authentication-refresh)); authoritative credentials are stored encrypted ([Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key)).
- Connection-wide provider limits must be accounted for across all agents using the same connection. Multiple records pointing to the same external account must not be assumed to have independent quotas. The accounting and external-account identity mechanisms remain open.
- Disabled or revoked access is enforced according to the credential and execution contracts. During disconnection, [Bounded continuation during disconnection](agents.md#bounded-continuation-during-disconnection) still limits use to existing valid authority; this decision does not promise immediate offline revocation or offline credential refresh.

Users cannot independently attach private provider connections outside installation administration. Organizations manage provider availability and spending centrally. Personal installations retain access to supported authentication methods through the same administrator workflow.

Scope: this decision covers model-provider connection ownership. Ownership of email, calendar, repository, browser and other tool integrations is covered by [Administrator-managed integration configuration](#administrator-managed-integration-configuration) and [Installation-managed external account connections](#installation-managed-external-account-connections). Model selection, failure behavior and direct inference are covered by [Default agent model with optional purpose overrides](agents.md#default-agent-model-with-optional-purpose-overrides) (a default model per agent with optional overrides for extraction, dreaming and compaction, using eligible connections), [Retry and wait for the selected model](agents.md#retry-and-wait-for-the-selected-model) (bounded retries and visible waiting instead of automatically switching connections or models) and [Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication).

**Rationale.** Cubebot agents belong to the installation and use model providers through the native Rust engine, so provider access needs an administrative owner and explicit rules for which agents may use each connection. The alternative, supporting both installation and personal connections, would permit separately owned user accounts with their own sharing and departure rules. The user selected one administrative ownership model for simpler management.

**What changed.** As accepted, every provider connection was installation-managed and could be offered to all agents; [Personal subscription connections](#personal-subscription-connections) makes a connection signed in with a consumer subscription personal to the person who signed in. As accepted, administrators had to grant each agent access to each connection individually. [Installation-wide connection access by default](#installation-wide-connection-access-by-default) replaced that with an all-agents default and a per-connection specific-grants mode; installation-managed ownership is unchanged. Propagation originally followed per-turn inference grants; [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary) replaced them with material propagated for the sandbox's lifetime. The credential backend, left open here, was settled as encrypted PostgreSQL records by [Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key), and refresh ownership by [Orchestrator-owned provider authentication refresh](#orchestrator-owned-provider-authentication-refresh).

**Open details.** Connection schema; secret delivery; supported authentication methods; rotation and refresh mechanics; revocation propagation; shared-account limit tracking; usage accounting; and provider qualification.

**Validation scenarios.** Use a default connection from existing and new agents; restrict a connection to specific grants and give selected agents access; deny agents without effective access; prevent secret disclosure through use authority; retain the connection record after its creator leaves; handle external revocation without granting replacement access; and apply aggregate limits when several agents share a connection.

## Orchestrator-owned provider authentication refresh

Accepted 2026-10-23. Amended 2026-10-27: during an orchestrator outage an agent works under its long-lived sandbox authority rather than a bounded per-turn authorization window.

**Decision.** The orchestrator alone owns provider authentication refresh. It refreshes supported connections and propagates updated authentication material to authorized agent sandboxes. The user selected this model on 2026-10-23. Agents use valid supplied material for inference and do not independently refresh the shared connection.

Usage: several agents use the same renewable provider connection. The orchestrator performs its refresh, records the new authentication revision and distributes the applicable update. Each agent continues calling the provider directly. No per-agent login or inference proxy is introduced.

Ownership: the provider-connection module in the orchestrator owns refresh scheduling, coordination, persistence and distribution. Provider adapters implement the supported exchange and failure classification. Agent adapters consume supplied authentication state and report failures or the need for an update; they do not write replacement authoritative credentials. This uses the existing orchestrator process ([One orchestrator process](agents.md#one-orchestrator-process)).

- Refresh operations for the same underlying authentication state are coordinated. Creating two Cubebot connection records for one credential must not be assumed to create independent refresh authority. Version checks prevent a late refresh response or stale agent report from replacing newer state. Exact external-account identification and serialization mechanics remain open.
- Propagate the material required for inference while keeping refresh-only secrets under orchestrator control when the provider's credential format permits that separation. Whether a particular authentication format supports such separation requires qualification. Shared authentication semantics do not require copying the orchestrator's entire credential store into each agent.
- During an orchestrator outage, an agent's current work continues only while its supplied authentication and its sandbox authority remain valid. If authentication becomes unusable, affected inference waits for the orchestrator to restore access. The agent does not bypass this policy by attempting local refresh or another model. This narrows availability according to credential lifetime.
- Refresh failure distinguishes a temporary provider problem from invalid authorization or required administrator reauthentication. An expired or rejected credential must not be reported as healthy. Static credentials are rotated through installation administration; they do not acquire a refresh operation merely to fit a common interface.
- Implementation requirements: preserve an identifiable committed authentication revision, propagate updates only to currently authorized recipients, and reconcile lagging agents on reconnect. Refresh can involve an external effect followed by local persistence; a crash between those steps cannot be assumed to roll back the provider's change. Recovery behavior and safe retries must be qualified per provider, with uncertain outcomes visible rather than blindly repeating exchanges.
- Authoritative credentials are encrypted PostgreSQL records ([Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key)). External refresh revisions and storage-key versions remain distinct and must coordinate without losing newer authentication state.

Agents remain independent for inference while supplied credentials are usable. Renewal depends on orchestrator availability. Refresh health and propagation failures need inspectable status, without exposing credential contents. Token lifetimes do not replace Cubebot's own execution authority.

**Rationale.** Agent runtimes call providers directly using propagated authentication, and multiple agents can share one connection, so renewable authentication needs a clear owner for refresh and authoritative updates. The alternative gave agent runtimes refresh authority and synchronized the results. That could extend independence for some providers but adds shared-state coordination and recovery across disconnected agents. The user selected one refresh owner. Refresh ownership stays with the orchestrator after the move to agent-owned execution; it is one of the switchboard's remaining duties under [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary).

**What changed.** As accepted, outage continuation also depended on a bounded per-turn execution authorization and on the finite continuation limits of [Bounded continuation during disconnection](agents.md#bounded-continuation-during-disconnection). [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary) removed per-turn grants and authority windows: a sandbox holds one agent-scoped credential for its lifetime, and revocation means revoking that credential or stopping the sandbox. Credential lifetime is now the limit on continuing inference through an outage.

**Open details.** Refresh lead time and retry policy; authentication revision schema; delivery acknowledgements; shared-credential identification; provider-specific uncertain-outcome recovery; reauthentication UX; and credential storage and deletion in agent sandboxes.

**Validation scenarios.** Several agents receive one coordinated refresh update; agents never initiate refresh; stale reports cannot restore old credentials; a disconnected agent waits when its supplied authentication expires; a reconnecting agent receives the current authorized revision; revoked agents receive no further updates; static-key rotation works without a refresh exchange; and a crash after provider-side rotation exposes a recoverable or explicitly unresolved state.

## Personal subscription connections

Accepted 2026-11-05.

**Decision.** A person may power Cubebot with their own consumer AI subscription instead of an API key, through a sign-in the vendor offers for that purpose. The resulting connection is personal: it serves only work done for the person who signed in, and is never installation-wide or granted to anyone else. A personal plan must not be shared. The user selected this on 2026-11-05, following the [subscription research](../research/subscription-providers.md).

- **Providers.** ChatGPT Plus and Pro through OpenAI's [Sign in with ChatGPT](https://developers.openai.com/siwc) program for open-source apps: PKCE with `client_id=dynamic_agent_client` on first sign-in, the issued `oaiapp_…` client id kept per installation, one stable `ext_agent_host_id` per installation, and inference at `api.openai.com/v1/responses` with `store:false`, `stream:true`, the system prompt in `instructions` and no `max_output_tokens` or `temperature`. Never Codex's client id or `chatgpt.com/backend-api`. SuperGrok and X Premium through device-code sign-in at `auth.x.ai` and `cli-chat-proxy.grok.com/v1`, which reuses the Grok CLI's client id as xAI's endorsed partners do: offered only as an opt-in labelled that way, and isolated so one change can remove it. MiniMax's M Plan has no sign-in, so its owner pastes the plan's own key; MiniMax limits it to "individual, interactive developer use" and says not to share it, so it is personal exactly like a signed-in plan, while a pay-as-you-go MiniMax key stays installation-managed. Claude (only an unmodified-CLI runtime is allowed, which needs its own decision) and Google (consumer sign-in is gone) stay on API keys.
- **Personal.** The connection records its owner, the person who signed in. It serves agents that person created and the room routing and task orchestration of messages and tasks that person started. It has no access setting: [Installation-wide connection access by default](#installation-wide-connection-access-by-default) and specific grants do not apply. Agents stay on one active connection at a time, so while a personal connection is the one in use, other people's agents have no provider and their turns wait. Only the owner can make their subscription the connection in use; the owner or an administrator can sign it out.
- **Tokens.** The access, refresh and ID tokens are one Credentials record ([Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key)) bound to the connection and its token revision. The refresh token never leaves the orchestrator. Agents receive only the short-lived access token and its expiry, and ask the orchestrator for the current one when it nears expiry; OpenAI allows a refresh only in the last minutes of the token's hour, so a long turn always outlives the token it started with.
- **Refresh.** The orchestrator refreshes under [Orchestrator-owned provider authentication refresh](#orchestrator-owned-provider-authentication-refresh): one refresh at a time per connection, serialized on its row, saving the rotated refresh token with the new access token in the same transaction. A refresh the vendor refuses (`invalid_grant` and its kin) marks the connection as needing a new sign-in and stops serving it; a transient failure keeps the tokens and retries.
- **Sign-in on a server.** OpenAI's flow redirects to `http://127.0.0.1/auth/callback`, which only the browser's own machine can receive, and it has no device code. Following its [Self-hosted VMs guide](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms), the person completes OAuth on their own device and the result crosses to the server over the console's authenticated HTTPS session: they paste the `127.0.0.1` address the browser lands on, the orchestrator checks its state and exchanges the code with the verifier it kept, and from then on the server owns refreshes under its own host id. This works from the installable PWA too. Grok's device code needs no paste.
- **Usage limits.** A subscription limit stops inference. A turn refused for it waits with `provider_usage_limit` under [Retry and wait for the selected model](agents.md#retry-and-wait-for-the-selected-model); it never falls back to another connection or billing path, and since vendors give no reset time, a person retries it.
- **No hosted offer.** A hosted, multi-tenant Cubebot must not offer subscription sign-in; OpenAI requires approval for paid or remotely hosted apps, and xAI has given no permission beyond its named partners.

This amends [Installation-managed provider connections](#installation-managed-provider-connections), which allowed no personal provider connections, and the scope of [Installation-wide connection access by default](#installation-wide-connection-access-by-default), which offered every provider connection to all agents.

**Rationale.** Vendors offer subscription use for the subscriber's own use: Anthropic's consumer terms forbid making an account available to anyone else, and OpenAI keeps credentials per account registration. An installation-wide subscription would let other people's agents spend one person's plan. Alternatives considered: per-agent connection selection, so each person's agents could use their own plan at once, which is a larger change to model selection; and a local helper that signs in and uploads a token file, which does not work from a phone.

**What changed.** Nothing earlier is replaced beyond the two amendments above.

**Open details.** Whether OpenAI counts a self-hosted server reached remotely as the Self-hosted VMs case and accepts the pasted callback (the [research](../research/subscription-providers.md) lists this as open); written permission from xAI; per-agent connection selection; usage-limit reset detection; revocation of transferred sessions, which OpenAI does not offer yet.

**Validation scenarios.** A person signs in with each provider and an agent they created answers with a real model; another person's agent cannot use the connection; a token refreshed by one caller is reused, not refreshed again, by a concurrent caller; the rotated refresh token is the one saved; an expired access token is never handed out; a refused refresh asks for a new sign-in; a usage-limit refusal waits the turn; sign-out revokes and stops the connection; no token reaches a log, an API response other than the agent's own access token, or the model.

## Administrator-managed integration configuration

Accepted 2026-10-23. Amended 2026-10-25: approved connections are usable by all eligible agents by default, with a per-connection specific-grants mode.

**Decision.** Only installation administrators register and configure integrations. The user selected this policy on 2026-10-23. Administrators define available servers, applicable configuration, credential references and tool availability. Managers may issue specific grants for approved integrations only within explicitly delegated assignment authority; ordinary agent management does not grant integration-registration rights.

Usage: an administrator registers a local workspace-analysis server or a remote project-management endpoint and determines which tools are approved. With the default all-agents access, every eligible agent can discover and use the approved tools without per-agent assignment; for a connection in specific-grants mode, a manager with the appropriate delegation enables an approved tool for an agent they manage. The manager cannot replace the server address, executable, credential reference or configured authority to obtain access outside that delegation.

Ownership: integration configuration owns the registered definition and its revision history. Authorization restricts definition changes to administrators and separately evaluates assignment and invocation rights. The MCP adapter discovers tools against the configured server; discovery is not an administrative grant. Native external integration configuration follows the same administration rule where applicable.

- The rule applies to both transport modes in [Local and remote MCP server support](agents.md#local-and-remote-mcp-server-support). Agents cannot register their own managed MCP integrations merely because they may install software under [Agent-directed software installation within grants](sandbox.md#agent-directed-software-installation-within-grants). Approved local launch definitions retain their identity through updates; changing code behind a writable executable path must not silently be treated as the same administrator-approved implementation. Executable provenance, package pinning and update enforcement remain implementation details.
- This controls Cubebot's integration registry and managed credential distribution. It does not pretend to prevent arbitrary protocol clients in an environment already granted code execution and network access. Such programs retain only the filesystem, network and credential authority actually available to them. Preventing access outside grants requires enforcement of those underlying capabilities rather than relying on a registry check alone.
- Definition updates are attributable and must not silently approve tools merely because a server advertises them. Once an administrator approves a capability, the connection's effective audience may use it ([Installation-wide connection access by default](#installation-wide-connection-access-by-default)). Human administration rights remain separate. Exact handling of configuration revisions, changed tool schemas and in-flight calls remains open.
- External account identity and credential ownership are separate from integration-definition administration and are installation-managed only ([Installation-managed external account connections](#installation-managed-external-account-connections)); that does not override provider-specific consent or confer ownership of an external account. Model-provider connections keep their own installation-managed policy ([Installation-managed provider connections](#installation-managed-provider-connections)).

Adding or changing managed integrations requires administrator involvement. Once configured and available to an agent, tools are invoked autonomously under [Autonomous tool use within granted permissions](agents.md#autonomous-tool-use-within-granted-permissions) without approval for each call. A single-person installation follows the same rule through its administrator account.

**Rationale.** Cubebot supports native core tools and both local and remote MCP integrations. Registering an integration adds an executable or endpoint and its configuration to the platform's available tools, and that authority must be distinct from using an existing tool or managing an agent. The alternative let managers register integrations within delegated limits. That would reduce administrator involvement but require another delegated configuration model. The user selected administrator-only registration and configuration, with scoped assignment of approved integrations.

**What changed.** As accepted, an approved integration reached an agent only through a manager's per-agent assignment. [Installation-wide connection access by default](#installation-wide-connection-access-by-default) made approved connections usable by all eligible agents by default; per-agent assignment now applies to connections in specific-grants mode. Credential storage, left open here, is encrypted PostgreSQL records under [Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key).

**Open details.** Credential lifecycle; assignment delegation vocabulary; configuration revisions and activation; executable provenance and updates; catalog visibility; tool-schema changes; audit retention; and in-flight revocation behavior.

**Validation scenarios.** An administrator registers each transport mode; a delegated manager grants an approved integration on a specific-grants connection; a manager or agent cannot register or replace a definition; an unapproved or ungranted tool remains unavailable after discovery; configuration edits are attributable; and an agent's ability to install software does not grant managed integration credentials or registry authority.

## Installation-managed external account connections

Accepted 2026-10-23. Amended 2026-10-25: enabled external account and reusable website connections are usable by all eligible agents by default, with a per-connection specific-grants mode. Amended 2026-11-01: an agent may hold website logins of its own in the vault. Amended 2026-11-05: [Native connectors](#native-connectors) settles most open details.

**Decision.** External account connections are installation-managed. Administrators manage connection records and choose each connection's access: all eligible agents (the default) or specific grants ([Installation-wide connection access by default](#installation-wide-connection-access-by-default)). The user selected this model on 2026-10-23. Cubebot does not introduce a user-owned connection category for email, calendars, repositories or other external integrations. Reusable website account access follows the same administrative model, with one exception: an agent may hold website logins and secrets of its own as agent-scoped vault items ([A vault the desktop arbiter fills](#a-vault-the-desktop-arbiter-fills)), besides installation-managed ones.

Usage: an administrator connects a mailbox through an approved integration and leaves all-agents access enabled, or selects specific grants for restricted access. A manager may grant a restricted connection only within delegated authority. The external account holder may still need to authenticate or consent, but the resulting Cubebot connection remains an installation resource rather than a personal connection owned by the assisting user.

- Installation management does not transfer ownership of the external account, bypass its consent requirements or guarantee authorization after revocation. It also does not expose the connection's content or raw credentials to every installation user. Existing content access, agent-use eligibility and external account permissions remain independently applicable.
- Ownership: integration configuration owns connection identity, administrative configuration and lifecycle. Authorization owns assignment and use grants. Integration adapters implement supported authentication and account-specific operations. The browser module uses authorized account state under [Reuse authorized website logins across browser sessions](sandbox.md#reuse-authorized-website-logins-across-browser-sessions). Model-provider refresh ownership ([Orchestrator-owned provider authentication refresh](#orchestrator-owned-provider-authentication-refresh)) does not automatically define every website or integration's authentication flow.
- Connection identity distinguishes the integration definition from the external account used through it. Several accounts may use one approved integration without becoming interchangeable. Invocation records identify the selected connection, without logging its secrets. A tool must not silently select a different account when the configured one is unavailable.
- A connection record is independent of the administrator or assisting user who created it. User departure does not itself transfer or broaden its grants. Continued execution requires valid external authorization and current installation policy. Disconnection, revocation and removal are recorded explicitly, with treatment of already-running work governed by execution and credential recovery contracts.
- Browser takeover ([Live browser viewing and explicit human takeover](sandbox.md#live-browser-viewing-and-explicit-human-takeover)) may assist with authentication, but control of a browser session is not permission to register a new installation connection or broaden reusable account grants. The onboarding flow distinguishes an administrator-authorized connection setup from ordinary session assistance. A login alone must not silently publish credentials to additional agents or tasks.
- Grant policy: named tool allowlists plus Cubebot resource restrictions where enforceable, alongside external credential scopes ([Tool allowlists with supported resource restrictions](agents.md#tool-allowlists-with-supported-resource-restrictions)).

External account onboarding and installation connection administration require administrator involvement. Ordinary users cannot independently create private connection records. Personal installations use the same workflow through their administrator account. External consent and credential validity still constrain what the installation can do.

**Rationale.** Administrators configure integration definitions, and the accounts and credentials used through those definitions need an ownership model independent of the external service's own account ownership. The alternative supported both installation-managed and user-owned connections through administrator-approved integrations. That would support user-controlled account sharing but add another ownership, consent and departure model. The user selected one administrative model, consistent with model-provider connection ownership.

**What changed.** As accepted, each agent needed an individual grant for each connection; [Installation-wide connection access by default](#installation-wide-connection-access-by-default) made all-agents access the default, with specific grants per connection. As accepted, website logins were installation-managed only; [A vault the desktop arbiter fills](#a-vault-the-desktop-arbiter-fills) lets an agent save and fill logins of its own, managed with `browser.control` on that agent. Secret storage, left open here, is the vault's encrypted Credentials records for typed website logins and [Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key) for recoverable connection secrets.

**Open details.** Assignment delegation; per-resource restrictions; audit retention; and in-flight disconnect behavior. [Native connectors](#native-connectors) settled the identity schema (a `connections` row per account, its slug naming its tools), grant representation (access plus a permission level and tool switches), onboarding (a setup wizard per connector), secret delivery, renewal and revocation at the next credential fetch.

**Validation scenarios.** Administrators connect an external account and set its access; delegated managers stay within assignment authority; ordinary users cannot create personal connection records; two accounts on one integration remain distinguishable; browser-assisted login does not broaden grants; creator departure preserves the record without extending authority; and external revocation makes affected access unavailable honestly.

## Installation-wide connection access by default

Accepted 2026-10-25.

**Decision.** Keep all integrations and connections installation-managed and make enabled, approved connections usable by all eligible installation agents by default. Each connection has an access setting: all agents, or specific grants. All agents is the default for newly configured connections. The user explicitly selected this change on 2026-10-25.

This amends the agent-eligibility assumptions of [Installation-managed provider connections](#installation-managed-provider-connections), [Native core tools with MCP integrations](agents.md#native-core-tools-with-mcp-integrations), [Local and remote MCP server support](agents.md#local-and-remote-mcp-server-support), [Administrator-managed integration configuration](#administrator-managed-integration-configuration), [Installation-managed external account connections](#installation-managed-external-account-connections), [Tool allowlists with supported resource restrictions](agents.md#tool-allowlists-with-supported-resource-restrictions) and [Explicit tool search with on-demand discovery](agents.md#explicit-tool-search-with-on-demand-discovery). Installation ownership, administrator-managed configuration, tool and resource restrictions, and on-demand discovery remain in force. Earlier statements requiring a separate per-agent assignment apply to connections configured for specific grants.

Usage: an administrator configures a repository integration and an account connection. With all-agents access, existing and newly created agents can discover and use its approved tools under the connection's configured scope without individual assignment. The administrator can instead select specific grants for a sensitive account and authorize only selected agents within that scope.

- **Scope.** The policy applies consistently to model-provider connections (except personal subscription connections, which are never offered beyond their owner: [Personal subscription connections](#personal-subscription-connections)), external integration accounts, reusable website accounts, approved credential-free integration connections and installation vault items ([A vault the desktop arbiter fills](#a-vault-the-desktop-arbiter-fills)). The integration definition identifies the implementation and approved tool set; each configured connection identifies its endpoint or account and effective access policy. A connection without credentials still has an access policy.
- **Dynamic baseline.** All-agents access is a dynamic baseline, not a copied grant on each agent. It includes agents created later, including task-bound workers, subject to their applicable execution constraints. These workers obtain eligibility from installation policy, not by inheriting their parent's credentials or memory. Suspended or retired agents do not regain execution eligibility through this default.
- **Tools.** For integrations, baseline access includes use of the administrator-approved tools and resource scope configured on the connection. Do not require an additional per-agent tool assignment merely to make all-agents access functional. Specific grants may select a subset of those tools and resources. Installation and execution restrictions and upstream credential scopes still constrain both modes. Newly advertised server tools remain unapproved until administrator approval; once approved, the current connection audience can use them.
- **Health and administration.** Access is distinct from connection health and enablement. A disabled, revoked or invalid connection remains unavailable in either mode. Administrators configure access modes; delegated managers may issue specific grants only within existing assignment authority. This change does not grant ordinary members or agents permission to register integrations, alter endpoints, broaden policy or inspect raw credentials.
- **One evaluation.** Use the same effective-access evaluation for discovery, provider and model selection, website account selection, credential issuance and invocation. When all-agents mode is turned off, only independently valid specific grants remain effective. When turned on, current and future eligible agents receive the baseline. Do not retain stale copied defaults as grants.
- **Changes.** Policy changes are versioned and audited. Recheck authorization before starting operations and reconcile catalog and credential caches. Stop issuing or refreshing credentials to agents that lose eligibility. Already-issued effects and credentials an agent already holds keep the limits in [Bounded continuation during disconnection](agents.md#bounded-continuation-during-disconnection) and [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary); a policy change must not be displayed as instantly undoing external actions. Exact connection revocation mechanics remain qualification work.
- **No implied selection.** Connection availability does not automatically choose a model, switch accounts, start a tool process, distribute every secret to every sandbox or load every tool schema into a prompt. Keep explicit account and model selection, purpose-scoped credential delivery and on-demand tool discovery. Existing agent data and human content permissions are unaffected.

Proposed schema: `access_mode = all_agents | explicit_grants`, plus the existing enabled state, approved tool and resource scope, and policy revision. Per-agent exclusions in all-agents mode are not introduced; restricted access uses explicit-grants mode. Existing deployed restricted records, if any, must not be silently broadened by a future migration. When accepted, this recorded a design change, not a live configuration mutation.

**Rationale.** The alternative was to require an explicit assignment for every agent and connection. The user replaced that default with installation-wide availability and optional restricted access. The policy is unchanged by the move to agent-owned execution in [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary).

**Open details.** Exact connection revocation mechanics (qualification work); per-agent exclusions from all-agents connections and vault items are not introduced and stay open for vault items ([A vault the desktop arbiter fills](#a-vault-the-desktop-arbiter-fills)).

**Validation scenarios.** New connections default to all agents; existing and new agents can discover and use approved capabilities without assignment; restricted connections require grants; turning the default off removes baseline eligibility; stale caches cannot authorize new operations; approved tool additions follow the current audience; new unapproved tools remain unavailable; disabled connections stay unavailable; and broad usability does not expose raw secrets or change model or account selection.

## Native connectors

Accepted 2026-11-05. The user decided D1–D4 below on 2026-11-05 after [the research](../research/connections.md).

**Decision.** External accounts connect through compiled-in **connectors**. A connector is one file in the shared crate `modules/connectors` implementing one trait: a static manifest (name, category, sign-in methods, settings, products, tools each tagged `Read`, `Write` or `Send`, events, setup guide), `check` (proves the credential and names the account), `call` (runs one tool) and an optional `poll` (events since a cursor). A **connection** is one account on a connector: a row with the connector, a unique slug, settings, one sealed credential, access, a permission level, switched-off tools, status and poll cursor. Adding a connector is its file plus one registry line; contract tests run against every registered connector and fail until its manifest keeps the rules and its `check` passes against a recorded fixture.

- **Sign-in without Cubebot-registered apps (D4).** Each connector declares how it authenticates and never implements OAuth itself: a pasted API key, a username and app password, OAuth with the person's own client (PKCE, landing on a pasted `127.0.0.1` address or, with a public address, this installation's callback), the device-code grant for public clients, a GitHub App created from a manifest on the person's account, another connection's token (Email signs in to Gmail with XOAUTH2 through a Google connection), the client-credentials grant with the person's own app (Zoom's Server-to-Server OAuth: the id and secret in Basic authentication, no refresh token), or nothing at all (public feeds). The orchestrator runs these flows with the subscriptions' code ([Personal subscription connections](#personal-subscription-connections)), renews tokens ahead of expiry, asks a client-credentials app again before its token lapses or as soon as its secret changes, mints GitHub App installation tokens with the app's key, records a refused renewal as needing a new sign-in, and rechecks health every six hours.
- **Uploads come from the workspace.** A tool input property `workspace_file` names a file the agent reads as the tool user before the call, at most 25 MiB, so an upload reaches only what `bash` could and the model never handles raw bytes.
- **Private servers.** Self-hosted connectors (Home Assistant, Nextcloud, Paperless-ngx, a self-hosted Cal.com) send their credential only to the configured address. The orchestrator checks and polls them from its own pod; agents call them from their sandbox, which under the Helm chart reaches a private address only when the administrator grants it in `sandbox.networkPolicy.privateDestinations` ([Public internet access with grants for private destinations](sandbox.md#public-internet-access-with-grants-for-private-destinations)). Their setup wizard ends with that step.
- **Calls run in the agent (D1).** Agents receive each turn's connections without credentials. The agent runtime fetches a short-lived credential (`GET /api/runtime/connections/{id}/credential`, which rechecks access) and runs connector calls in its own process, never as the tool user, so `bash` cannot read them from an environment or file. Refresh tokens, client secrets and app keys never leave the orchestrator. Pasted API keys and passwords do not expire, so the runtime holds them for a turn; a prompt-injected agent can misuse granted tools but cannot read the credential. Every result is struck of the credential's values before the model, journal or ledger see it.
- **Permission level.** Access keeps [Installation-wide connection access by default](#installation-wide-connection-access-by-default). Each connection also has a level, *Read*, *Read and write* or *Full* (includes `Send`: irreversible or reaching other people), and the agent is offered only tools at or below it, without the ones switched off. With no approval queue this is the safety control. A new connection takes its connector's default; Email, Google, Microsoft 365, Telegram, Linear and Discord default to *Full*, because agents send email by default (D2) and a chat bot or issue tracker is there to answer; Stripe, Zoom, Calendly, Readwise and RSS default to *Read*, and a Stripe refund is `Send` because it moves money.
- **MCP servers stay separate (D3).** Vendor remote MCP servers are configured only under MCP servers, never as connector cards.
- **External content is untrusted.** Mail, documents and messages are vendor data: tool results and polled events are marked as untrusted in the agent's instructions and routine messages, and cannot grant tools or select accounts.

Usage: an administrator opens Platform › Connections, picks Google, follows the wizard to create a Desktop OAuth client, signs in, ticks Gmail and Calendar, and leaves the level at *Full*. Agents find `gmail-work__gmail_send` through tool search and use it; a second Google account becomes `gmail-personal` and stays distinguishable. A routine waiting for `gmail-work`'s `mail.received` runs when new mail arrives.

Wave 1 connectors: Email (IMAP and SMTP), Google (Gmail, Calendar, Drive, Contacts, Sheets, Docs), Microsoft 365 (Outlook, Calendar, OneDrive, To Do), CalDAV and CardDAV, GitHub, Notion, Slack, Telegram bot and a generic HTTP API.

Wave 2 connectors: Linear, Jira and Confluence (Atlassian Cloud), Asana, Todoist, Trello, Airtable, HubSpot, Discord bot, Readwise, RSS and Atom feeds, Calendly, Home Assistant, Nextcloud Files, Paperless-ngx, Dropbox, Cal.com, Zoom and Stripe.

**Rationale.** One trait with declarative sign-in keeps each integration small and reviewable while the security-sensitive flows live once in the orchestrator. Running calls in the agent keeps the rule that agents run their own tools, and short-lived, process-held credentials keep the long-lived ones out of reach. Alternatives considered: the orchestrator proxying every call, which makes it a tool runner; vendor MCP servers as the catalog, which needs OAuth support most installations cannot complete and offers no permission levels; Cubebot-registered OAuth apps, which a self-hosted installation cannot rely on.

**Open details.** Vendor webhooks for installations with a public address; per-resource restrictions inside a connection; whether Gmail's restricted scopes on an unverified app in production need more for a single user; sign-ins held in memory are lost on an orchestrator restart; polled events are bounded per poll (a burst larger than one page between polls can be missed, and Home Assistant reports only the latest change of a watched entity); Dropbox's acceptance of the loopback redirect and several Wave 2 vendors' behavior are verified only against recorded fixtures.

**Validation scenarios.** A refused key saves nothing; a sealed credential never appears in an API response, turn, journal or ledger; a connection limited to specific agents stops issuing credentials to others at the next fetch; a level hides tools above it; a refused renewal marks the connection for a new sign-in and agents are told so; a device sign-in waits for approval; a GitHub App waits for its installation and then mints tokens; a polled event starts the routine waiting for it once; and every connector checks against its recorded fixture.

## A vault the desktop arbiter fills

Accepted 2026-11-01.

**Decision.** The orchestrator keeps a vault of logins and secrets, and the desktop arbiter ([Desktop as a VMM device](sandbox.md#desktop-as-a-vmm-device)) types them for the agent. The user selected this on 2026-11-01.

- **Items.** One `vault_items` table: scope installation or agent, kind `login` (site, username, password) or `secret`, a name, the secret as a Credentials record ([Encrypted credentials with a separate installation key](#encrypted-credentials-with-a-separate-installation-key)) bound to the item's id, who created it, and when it was last filled. Usernames, sites and names are metadata; only the secret is encrypted.
- **Access.** An installation item has an access policy under [Installation-wide connection access by default](#installation-wide-connection-access-by-default), all agents by default or explicit grants, and only administrators manage it. An agent's own item belongs to that agent alone and is managed with `browser.control` on it; `browser.view` lists the items an agent may fill. No API response carries a secret.
- **Filling.** The agent's `vault_list` returns metadata only. `vault_fill` (item, field) asks the orchestrator, which decrypts the field and sends a `fill` request on the desktop host channel; the arbiter types it at the focus, refusing it like the agent's own input while a person holds control, during a login handoff, or before the agent looks again. A person holding control fills from the Desktop tab the same way, as themselves. The text never returns to the agent, and the arbiter logs only the item id and the text's length.
- **Saving.** The agent's `vault_put` saves a secret it made, such as for a new account, as its own item, replacing one with the same name. Its `secret` argument is replaced with `[redacted]` before the call reaches the agent's journal or the turn ledger; the model's own request still held it. During a login handoff the person can save the login and have it typed in one step.
- **Typable only.** The arbiter types printable ASCII and spaces on a US layout, so a username or secret with any other character is refused when saved, not when filled.

This amends [Installation-managed external account connections](#installation-managed-external-account-connections) for website logins: an agent may hold logins of its own besides installation-managed ones. It settles secret storage for typed website logins left open in [Reuse authorized website logins across browser sessions](sandbox.md#reuse-authorized-website-logins-across-browser-sessions).

**Rationale.** Website login secret storage was open, and the login handoff in [Live browser viewing and explicit human takeover](sandbox.md#live-browser-viewing-and-explicit-human-takeover) needs a person at the desktop every time. An agent that can read a password can leak it into its context, tool output or files; one that can only ask for it to be typed cannot. Alternatives considered: giving the agent the secret as tool output, which puts it in the ledger and model context; a password manager inside the guest, which agent-run code can read; typing through the browser tools' DevTools pipe, which bypasses the arbiter's mode and its record of who typed.

**Open details.** Key rotation for vault records; per-agent exclusions from all-agents items; filling more than one field per call; items for non-US layouts.

**Validation scenarios.** A fill types the secret and neither the turn ledger, the model's requests nor the desktop records hold it; a `vault_put` secret is redacted in the ledger; an item with an untypable character is refused; the agent's fill is refused while a person holds control; a person's fill is refused unless they hold control; an agent without access to an installation item can neither list nor fill it.

## Encrypted credentials with a separate installation key

Accepted 2026-10-23. Amended 2026-10-27: the agent sandbox, not a separate tool container, is the environment the key never reaches.

**Decision.** Store recoverable credential material as encrypted records in PostgreSQL, with the installation encryption key held separately and initially supplied through a Kubernetes Secret. The user selected this model on 2026-10-23. Database records do not contain the plaintext installation key. An external vault is not required.

Usage: an administrator establishes a provider connection. The orchestrator encrypts its authentication material before persistence. When an eligible agent needs inference credentials, the orchestrator reads the applicable record, decrypts it in the trusted runtime path, and delivers only the material that agent is allowed to use ([Direct provider inference with propagated authentication](agents.md#direct-provider-inference-with-propagated-authentication)). The installation encryption key is never delivered to agents.

Ownership: a credential-storage module owns encryption, decryption, encrypted-record format and key-version handling. Connection modules own external authentication state and refresh behavior. Authorization determines permitted use and distribution. Installation administration owns provisioning and recovery of the separately stored key. Domain modules do not implement their own cryptographic formats.

- **Format.** Use an established authenticated-encryption implementation with explicit format and key versions, binding ciphertext to its intended record context (vault items bind it to the item's id). Algorithm, library, nonce handling and direct versus envelope encryption remain implementation choices requiring qualification. A malformed or unauthentic record fails explicitly; missing keys must not cause fallback to plaintext or automatic replacement with a new unrelated key.
- **Revisions and keys.** Credential revision and encryption-key version are distinct. Provider refresh ([Orchestrator-owned provider authentication refresh](#orchestrator-owned-provider-authentication-refresh)) updates the authoritative authentication revision; rotating the storage key changes protection of stored data, not the external credential itself. Rotation must be restartable, preserve readable records during transition, and retain required old keys until live records and supported recovery points no longer depend on them. Concurrent refresh and re-encryption must not restore older authentication state.
- **Key custody.** The key is accessible only to the orchestrator and explicitly authorized recovery paths, not agent sandboxes or ordinary user sessions. Decrypted material stays out of model context, normal logs, shared artifacts and workspace files. External-tool credential delivery and agent-local credential persistence still need their own contracts. This decision covers recoverable secrets; it does not select the representation of built-in account password verifiers or other non-recoverable authentication data.
- **Limits of encryption.** Encryption separates database contents from key custody. It does not prevent an actor who controls both the orchestrator and its key from accessing credentials. Kubernetes access controls and deployment configuration must enforce the intended key-access boundary; choosing a Kubernetes Secret does not by itself establish the entire security posture.
- **Backups.** Backups ([Cubebot-coordinated backup and restore workflows](packaging.md#cubebot-coordinated-backup-and-restore-workflows)) identify the key versions required for recovery without exposing key material in ordinary manifests. The database backup alone cannot restore encrypted credentials. Key recovery material must be available through a separately protected procedure, including for cluster loss. Exact key export or escrow mechanics remain open. Restoring old ciphertext does not establish that an external token remains valid.

The vault's secrets ([A vault the desktop arbiter fills](#a-vault-the-desktop-arbiter-fills)) are records of this kind.

**Rationale.** Installation-managed connections contain authentication material used by the orchestrator and authorized agents, and their storage must support durable updates and recovery without requiring an external secret-management service. Alternatives considered: store each credential in Kubernetes Secrets, or require an external secret manager. Encrypted PostgreSQL records with separately held keys keep connection persistence in Cubebot's existing state model while limiting required services.

**What changed.** As accepted, the key and decrypted material had to stay out of agent tool containers, the separate container in each agent pod where agent-run code executed. [Agent-centric execution in a sandbox boundary](sandbox.md#agent-centric-execution-in-a-sandbox-boundary) removed that container: the agent's runtime and tools share one sandbox, and the provider material an agent is eligible for is reachable by code running there. The key itself still never leaves the orchestrator and recovery paths.

**Open details.** Cryptographic library and record format; key generation and provisioning; rotation mechanics (including for vault records); recovery custody; protected export; bootstrap permissions; and agent-local secret storage and deletion.

**Validation scenarios.** Encrypt and retrieve an authorized credential; deny ungranted distribution; keep the key out of agent sandboxes; reject altered ciphertext; report missing or wrong keys; resume interrupted key rotation alongside refresh; and restore records with the correct key version without claiming revoked external credentials are usable.
