# OpenBot agent runtime, context, and memory

Research date: 2026-10-22. Source revision: `cfee2971f29cdb7c16272e60ae912de7fbb30693` in `nightly-labs/openbot`. This report traces the checked-out source. No provider turns, dependency installation, application startup, or upstream edits were performed. Tests below were inspected, not run. Source behavior is evidence of implementation, not proof of live model behavior.

## Core model

OpenBot gives an agent a durable identity, profile, workspace, and public conversation. Provider sessions sit behind that public conversation. Replacing a provider session does not require replacing the agent or its conversation. Agent creation generates an `agent-<UUID>` identity, creates its workspace with mode 0700, persists the roster, and rolls back the new workspace if persistence fails. The initial profile has a null thread, provider/model/effort settings, access mode, and Computer Use enabled. [Agent creation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-store.ts#L309-L343) [Stored profile](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-store.ts#L1553-L1573)

The practical distinction is between agent identity, public thread identity, native provider session identity, and turn identity. A new native session receives a provider-independent handoff, then binds to the public thread. The handoff is written before the binding so a crash cannot leave a replacement session active without its first-turn context. [Native session preparation and binding](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L490-L617)

`AgentService` composes separate owners for profile storage, provider runtime, thread lifecycle, mailbox draining, conversation updates, memory, compaction, and boot recovery. Startup initializes the agent store and mailbox, restores channel links, recovers persisted turns, then enables operation. The queue and recovery code inspect durable state rather than treating an in-memory active flag as sufficient evidence. [Service initialization](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-service.ts#L2854-L2895) [Boot recovery ownership](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/boot-recovery.ts#L46-L84)

## Provider adapter contract

The internal `AgentClient` API is Codex-shaped. It exposes `request(method, params, decoder)`, notifications, server requests, responses, start/stop, and optional history/session-release methods. Capabilities include explicit compaction modes: `events`, `request`, `native`, `handoff`, or `unsupported`. The same service can send `thread/start`, `thread/resume`, `turn/start`, `turn/steer`, `turn/interrupt`, and `thread/compact/start`, while adapters translate them to each native runtime. A timeout has a distinct error class because a request may already have reached the provider. [AgentClient contract](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-client.ts#L13-L103)

All built-in descriptors advertise concurrent turns except custom ACP. Codex, Claude, Pi, Muse, and Inception advertise native steering; ACP-family providers defer messages. These are application capabilities, not claims that every native model behaves identically. [Provider capabilities](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/agent-providers.ts#L168-L398)

`ProviderRuntime` normally shares a provider client. An agent gets its own process when its access mode requires process confinement or it selects an additional provider account. The process that holds a running turn stays addressable even after settings change. The next safe start replaces a mismatched process. Its key includes provider/configuration ownership, and concurrent starts wait on a shared deferred result. [Provider process ownership](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/provider-runtime.ts#L1733-L1841)

On shared-provider exit, the runtime records the loss and has bounded restart behavior. The inspected exit path stops after three restart attempts or the earlier repeated-start-failure guard; retry delays are `500 * 2 ** attempts` milliseconds. Other available providers can keep the service ready. This is process recovery, not automatic replay of failed user work. [Bounded restart path](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/provider-runtime.ts#L3090-L3127)

## A turn from queue to completion

1. Each main chat and each task has a queue lane. A lane may run one turn at a time. Drain guards check active turns, custom-provider one-turn restrictions, task limits, process changes, hidden agents, channel ownership, profile saves, duplication, compaction, routine holds, and usage limits. An agent has two task slots by default, configurable from one to four; its main chat is outside that task count. [Drain guard clauses](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L239-L304) [Task concurrency limits](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-agent-tasks.ts#L7-L21)
2. A server-wide `TurnSlots` policy can limit concurrent lanes. If configured with no limit, it admits all eligible lanes. When space is scarce it favors user messages, then older queue heads, then lane ID for a stable tie. Starting turns and compaction consume slots. [Global turn scheduling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-slots.ts#L1-L59)
3. The scheduler claims deliveries, prepares attachments and the native session, constructs input from the delivery batch, and adds a pending session handoff. It then sends `turn/start` with the delivery ID as `clientUserMessageId`, model/effort, workspace roots, and access/approval policy. [Provider turn request](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L665-L744)
4. Once the provider accepts, it publishes the active turn before mailbox writes can yield. The same turn can complete before the start response is read, so an ended-turn guard prevents restoring a completed turn as active. Deliveries then move to running with the accepted turn ID. [Turn-start recovery and acknowledgement](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L745-L800)
5. `TurnLifecycle` handles item/turn events, flushes text, waits for image operations and delivery association, commits successful memory mutations, clears active state, settles mailbox rows, emits completion, and schedules further work. Native/provider-generated turns also enter this event system. [Turn completion and retry guards](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L720-L883)

The start-failure paths distinguish certainty:

- A missing session can be resumed or replaced before a single retry. A Codex compaction refusal restores the queued deliveries and waits for compaction. An already-running provider-generated turn also returns the input to the queue. [Turn-start recovery and acknowledgement](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L745-L800) [Certain and uncertain start failures](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L824-L900)
- A `turn/start` timeout does not resubmit the same input. The scheduler retains a reservation, waits for lifecycle events, and starts a five-minute grace period. [Start grace constant](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L43-L45) If no turn takes the still-starting delivery by the deadline, it marks the delivery interrupted and releases the reservation. This limits queue blockage without asserting that a provider never ran. [Certain and uncertain start failures](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L824-L900) [Unconfirmed-start deadline](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L934-L965)
- Failure after a confirmed native start only retries mailbox reconciliation. It does not repeat provider execution. [Certain and uncertain start failures](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L824-L900)
- A refused history/session can get one fresh-session retry only if the turn produced no output, the delivery has not already received that retry, and it belongs to a main chat or task. A usage-limit failure can requeue only if no action occurred. [Turn completion and retry guards](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L720-L883) [Single retry of refused history](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L1023-L1041)

Steering checks the expected active turn and queued delivery ownership. It uses the running turn's endpoint even if the saved model changed. Unsupported providers leave the delivery queued and record a fallback reason. Messages cannot steer into the temporary session of a routine run because that would omit them from the main native chat session. A failed steer restores the message and asks the drain to run again. [Queue steering](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/queue-controls.ts#L217-L296)

Interruption resolves the exact active public/native session and guards against sending a late Stop to a newer turn. Orphaned OpenBot state can be settled without asking an absent provider to stop. The service then calls native `turn/interrupt`; this code does not claim rollback of completed tool side effects. [Targeted turn interruption](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-service.ts#L3947-L4000)

## Restart recovery

Before providers start, `BootRecovery` records the unresolved deliveries as orphans, clears stale active turns, expires unanswered prompts, and marks streaming messages interrupted. Once providers are ready, it reconciles only orphaned deliveries, so readiness from another provider cannot settle a live turn from this process. [Boot recovery ownership](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/boot-recovery.ts#L46-L84)

Recovery reads provider history by native turn ID, or by the delivery's `clientUserMessageId` when start acknowledgement was lost. It preserves a recovered completed/failed outcome when evidence exists. Otherwise it records interrupted. A missing reader, missing session, unreadable history, or failed read does not cause automatic replay. History backfill can recover visible provider output separately. This is a conservative at-most-once attempt policy for uncertain work, not an exactly-once execution guarantee. [Orphan reconciliation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/boot-recovery.ts#L137-L280)

## Context construction and compaction

Standing context includes product rules, profile/title/description, workspace/access information, section teammates, tool-discovery instructions, relevant connection state, and selected agent memories. `ThreadLifecycle` passes this at native thread start/resume. It sends only essential memories, while reporting the total saved count and storage limit. [Instruction assembly](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L913-L937) [Bounded memory prompt](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/developer-instructions.ts#L60-L94)

Provider differences matter:

- Codex receives developer instructions in its native thread parameters. Dynamic tools are fixed when a native session starts, so a persisted tool/configuration fingerprint decides when to replace the session. [Native session preparation and binding](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L490-L617)
- Claude gets stable instructions in its preset append and mutable memory in separate user-message content. It sends a full memory block on first use, a delta or full block after edits, whichever is shorter, and nothing if unchanged. Compaction clears the delivered-memory marker so the next normal turn gets the full block. [Claude compaction memory refresh](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/claude-client.ts#L1105-L1109) Slash commands omit memory and reset that marker. This preserves the stable cached instruction prefix. [Full and delta memory blocks](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/developer-instructions.ts#L97-L123) [Claude per-turn memory delivery](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/claude-client.ts#L918-L946)
- ACP injects a tagged instruction block only when instructions changed or were not delivered, and periodically when the provider supplies no context usage. The refresh constant is ten prompts. [ACP refresh constant](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/acp-client.ts#L196-L197) Failed turns and compaction/context shrink can invalidate delivery. Muse likewise sends instructions only when absent/changed and resets delivery after failed turns or completed compaction. [ACP conditional instructions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/acp-client.ts#L1636-L1650) [Muse conditional instructions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/muse-client.ts#L622-L625)

The OpenBot scheduler treats compaction as a real operation that holds queue access. Its occupancy threshold is 80% of the last reported total token count divided by the reported model window. It does not substitute cumulative account usage or an invented default context window. After compaction it requires growth of `max(1024, floor(window * 0.05))` before another pressured request. The normal timeout is 120 seconds, with a grace period equal to one quarter of it. [Compaction timeout constants](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/context-compaction.ts#L22-L25) [Compaction grace calculation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/context-compaction.ts#L89-L92) [Compaction thresholds and growth guard](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/context-compaction.ts#L198-L260)

Codex and Muse finish explicit compaction by events. Pi finishes through the request response. Claude manages it natively. Generic ACP does not acquire a queue hold for an unsupported compact request. Antigravity's `handoff` capability rotates only the agent's main chat native session: capture steps, release/retire the old session, create a new session for the same public thread, then inject the bounded handoff. Tasks have persistent handoffs, but this automatic handoff-compaction policy is restricted to the main chat. [Compaction completion contract](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/context-compaction.ts#L264-L333) [Same-thread session rotation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L1020-L1044)

## Handoff and historical recall

The replacement-session handoff is deterministic text assembly. No language-model summary or embedding query is used. The limit is 32,000 JavaScript string characters, partitioned into 24,000 for recent messages, 4,000 for older excerpts, 2,000 for work steps, and 2,000 for headers. The reader fetches pages of 20 until enough recent text exists. It separately retains the latest user and assistant messages, initially up to 8,000 characters each. Long messages retain their start and end. Spare space can expand these anchors. Older excerpts use up to 600 characters each. [Bounded deterministic handoff](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/handoff-history.ts#L7-L138)

Each excerpt names a message ID. The packet states that it is incomplete and points to history tools. It prefers current instructions over historical data. Work-step capture includes selected commands and output tails, file names/change types, tool names/status, searches, and progress notes. It deliberately omits raw reasoning and full tool results. Per-step text is bounded; command output tail is 600 characters; each captured turn has a 4,000-character budget; at most 60 recent turns with steps are kept. Captures are private files under `provider-work-steps/v2`, keyed by database session identity. [Work-step rendering and capture](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/handoff-tool-steps.ts#L8-L123) [Loaded-client work-step capture](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L1225-L1294)

`readWorkSteps` requires the client already loaded for that native session and uses a ten-second deadline. [Capture deadline](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L88-L90) It does not launch old providers to improve the packet. The next handoff reads stored captures. Missing/corrupt captures leave text history usable and state that steps are unavailable. Routine runs in the main chat have their own short-lived native sessions, receive up to 8,000 characters of recent history, and add at most 1,500 characters of answer digest per run to the next main-chat input, up to 6,000 total. [Loaded-client work-step capture](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L1225-L1294) [Routine handoff and digest](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/handoff-history.ts#L140-L191)

Historical recall has two different algorithms, which should not be confused with saved-memory search:

| Tool | Algorithm and bounds |
| --- | --- |
| `history_search` | Case-insensitive substring search over already-redacted message text. Each call scans at most 200 rows, returns five matches by default and ten maximum, and can return a continuation cursor even with few or no matches. Excerpts are at most 400 characters; the serialized tool response is bounded to 8,000 characters. |
| `history_read` | Recent messages, a named message, or a cursor page. Ten default, twenty maximum. A message chunk is at most 12,000 characters, within a 16,000-character serialized result. Offsets continue long message text or captured work steps; attachments return metadata. |

Both tools read only the calling agent's exact public conversation after its latest completed context-reset marker. The database validates ownership, anchor existence and canonical ordering. Cursors carry the thread, reset boundary and query. As file reads can yield, the handler rechecks reset/message existence/content before returning. Searching redacted text prevents hidden-secret hit/miss probing through history search. [Model-facing history algorithms](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/history-tools.ts#L10-L225) [History ownership and reset boundaries](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/database/agent-history-queries.ts#L19-L84)

## Saved agent memory

Agent memory is a structured SQLite store, separate from conversation history and native provider context. Entries contain ID, owner, text, origin `manual` or `automatic`, optional source turn, and timestamps. The default storage cap is 64 entries. A host setting permits 128, 256, or 512. Each entry is at most 500 JavaScript string characters. Lowering the cap preserves existing entries and blocks additions until the count permits them. The selected prompt has an independent 8,192-byte UTF-8 budget, including serialized entry IDs, origins and tags. [Memory cap choices](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-agent-memories.ts#L69-L85) [Memory count and text defaults](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/input-limits.ts#L20-L35) [Memory byte accounting](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/agent-memory-context.ts#L1-L14)

`automatic` means an agent called a memory tool. In the inspected owners there is no separate post-turn extractor, daily summarizer, embedding pipeline, or autonomous memory consolidation job. The developer prompt asks the model to call `remember` for durable facts/preferences/decisions, update a memory by ID for corrections, and put reusable procedures in skills. Whether the model notices a fact and calls the tool remains model behavior. The system does not automatically save every user message. [Model memory instructions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/developer-instructions.ts#L171-L173) [Memory tool staging](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/agent-memories.ts#L183-L345)

The write path works as follows:

1. Manual UI/API operations write to the store directly. Agent `remember`, `forget_memory`, and inclusion-selection calls stage mutations in an in-memory map keyed by turn ID and call ID. New agent-created entries default to searchable; explicit essential inclusion can fall back to searchable when a new fact would exceed the prompt budget. [Memory tool staging](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/agent-memories.ts#L183-L345)
2. Pending changes are not visible to search. Projected pending state reserves storage/prompt space and accounts conservatively for other concurrent turns. At turn completion, only status `completed` commits changes. A failed/interrupted turn discards them. A process crash also loses these staged mutations, even if the provider independently completed work. [Memory commit and conflict handling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/agent-memories.ts#L350-L431) [Concurrent pending memory accounting](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/agent-memories.ts#L548-L620)
3. Epoch checks, `expectedUpdatedAt`, and selection revision checks prevent stale pending operations from overwriting later user edits. Mutations commit individually; a failed mutation emits `memory_commit_failed` and the loop continues. Thus a successful provider turn does not imply every memory mutation committed, and the complete mutation batch is not all-or-nothing. [Memory commit and conflict handling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/agent-memories.ts#L350-L431)
4. Selection metadata records `essential`/`searchable`, `userControlled`, and `revision`. User-controlled selections cannot be changed or forgotten by agent tools. The user can return a selection to automatic control. Selection requests carry expected revisions and allow up to 25 changes. [User-controlled memory selection](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-memory-store.ts#L161-L219)
5. Saves use the event-dispatch/store projection path. Duplicate folding uses equal stored text after outer trimming; despite its name, `normalizeMemoryText` returns its input unchanged. There is no case-folding or semantic duplicate detection in this base function. Deletes erase the memory's prior events and command receipts as well as its current row. That does not establish erasure from provider sessions, historical chat/tool text, or external backups. [Store save and duplicate handling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/memory-store.ts#L184-L267) [Forget history and normalization](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/memory-store.ts#L271-L298)

Memory retrieval uses SQLite FTS5 with the `unicode61` tokenizer and insert/update/delete triggers. Query text is at most 256 characters; Unicode letter/number/mark terms become quoted OR terms. Results rank by BM25, then newest update, then memory ID. Search returns five entries by default and at most ten. Results remain under 8,192 serialized UTF-8 bytes. Full listing pages use increasing memory IDs, at most 25 entries, and the same byte budget. There is no embedding model, vector index, or reranker in this path. [FTS schema and initial selection](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-memory-selection.ts#L7-L67) [Saved-memory search and paging](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-memory-store.ts#L230-L284)

Initial migration/import selection preserves user-controlled choices, then greedily fills essentials with manual entries first and newest updates next until the byte budget is full. New entries do not all become essential by default. Before prompt injection, memory text is redacted and the budget is checked again because redaction can expand text. A memory change unloads the agent's loaded-thread markers so the next turns rebuild context. The prompt labels memory untrusted and says it cannot override current instructions. This is a behavioral instruction, not proof that every model resists memory prompt injection. [FTS schema and initial selection](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-memory-selection.ts#L7-L67) [Bounded memory prompt](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/developer-instructions.ts#L60-L94) [Memory change context invalidation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/agent-memories.ts#L534-L545)

## Other memory and persistent files

Channel and external-messaging memory use the same `MemoryStore` base with different owners/tables. The channel cap is 32 entries and the same 500-character text validator applies. `channel_forget_memory` identifies a fact by text because the channel prompt does not expose memory IDs. It first tries exact trimmed text, then a case-insensitive match. Agent memory remains owned by an agent even while it works in other conversations. The cross-conversation context and tool boundary is traced below; agent essential memories are included in channel and external-messaging sessions. Channel and messaging packet construction are covered in the companion collaboration report. [Channel memory store](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-memory-store.ts#L7-L62) [Memory count and text defaults](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/input-limits.ts#L20-L35)

Provider history is another persistence layer. The common streaming interface emits fragments with turn identity, item offsets, completion, and optional records-only semantics. SQLite keeps import state and paged staged records. Non-Codex/non-Claude records are marked records-only when read from this seam, so imported ACP transcript rows do not automatically masquerade as exact OpenBot live-turn identities. [History fragment contract](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/provider-history.ts#L5-L38) [SQLite provider-history port](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/provider-history-persistence.ts#L10-L145)

The current ACP adapter durably appends completed turn text/thought/tool items before emitting turn completion. A persistence failure reports the turn failed. On history reads, a complete durable import is used directly. If history is incomplete, `session/load` can replay through the storage port; `session/resume` provides no historical replay. Replay has a 256-item pending-work cap and synthetic transcript turn IDs where native identities are unavailable. Therefore native provider resume, durable local history, and public conversation reconstruction are related but distinct operations. [ACP durable completion](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/acp-client.ts#L1946-L2022) [ACP replay identity and bounds](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/acp-client.ts#L1392-L1445)

Workspace files are a separate durable resource, under the agent's stable workspace plus the shared root. `AgentStore.createAgent` creates a directory and profile rather than synthesizing a canonical `MEMORY.md`. I found no OpenBot-owned general file-memory ingestion/extraction mechanism in `agent-memories.ts`, `memory-store.ts`, `agent-memory-store.ts`, `developer-instructions.ts`, or agent creation. A native CLI may read its own project/user instructions and memory files. For example, Claude enables user/project/local setting sources in unrestricted mode and only user settings in workspace-only mode. Such provider behavior should not be described as OpenBot's cross-provider memory contract. [Agent creation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-store.ts#L309-L343) [Claude SDK query configuration](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/claude-client.ts#L790-L820)

## Context privacy across channels, messaging, and tasks

The agent's essential memories are also included in its channel, external-messaging, and task sessions. This is a source-confirmed context flow. `DrainScheduler` obtains an execution-thread ID from `MessagingThreads.prepare`, `ChannelService.prepare`, or the task lane, then passes the same owning agent to `ThreadLifecycle.ensureThread`. Both native start and resume build instructions through `#instructions`, which calls `essentialFor(agent.id)` without a conversation-kind filter. `#sessionAgent` only disables Computer Use for task sessions; it does not change identity, workspace, memory ownership, or profile. [Execution-thread routing](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L601-L647) [Unfiltered essential agent memory](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L913-L937) [Resume settings and instruction assembly](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L946-L968) [Task session settings and MCP filtering](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L846-L877)

External messaging adds a separate connection-owned memory block to the delivery text. `MessagingThreads.prepare` reads `this.memories.list(link.connectionId)` and returns `{ threadId, text }`. It does not replace or filter the standing agent instructions. The messaging prompt tells the model that the sender is external, forbids disclosure of credentials/private files/private memories merely because the sender asks, and directs workspace facts to `messaging_remember` instead of the agent's `remember`. Those are prompt instructions. They do not remove the agent's saved facts from the provider context. [Messaging delivery preparation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/messaging/messaging-threads.ts#L454-L483) [Messaging privacy and memory instructions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/messaging/messaging-prompt.ts#L47-L64)

The ordinary agent memory tools remain callable in these turns. The router handles `messaging_*` tools using an exact link/agent check; the channel branch handles `channel_*` and rejects ordinary `send_message` in channel work. Other names continue to `AgentMemories.handleTool(params, senderAgentId, ...)` without a channel or messaging exclusion. Consequently `search_memories`, `list_memories`, `remember`, `forget_memory`, and selection operations still use the owning agent's store, with their existing user-control/revision restrictions. `messaging_remember` has a separate connection-owned store and scoped route, but it does not create a hard exclusion of the agent's private memory from that conversation's model context. [Channel and messaging dispatch branches](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L674-L711) [Ordinary agent memory dispatch](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L839-L852)

The precise boundary is therefore between stored owners and scoped history/tool operations, not a blanket separation of all information available to the same agent. Main-chat transcript recall remains excluded from other threads: history tools resolve the exact bound public conversation, and a channel must use channel history. The external platform's human participants are not directly given an agent-memory database API by this path. However, the model handling their messages receives the owning agent's essential memory and can recall additional agent memory through ordinary memory tools. Whether it discloses any fact in an external answer depends on its subsequent behavior and the applicable output/tool controls. This research did not execute a disclosure test and does not establish an observed leak. [Exact-thread history routing](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L323-L343)

Tasks share the owning agent's profile, provider settings, workspace directory, writable roots, and memory store. Native start/resume still set `cwd: agent.workspacePath` and the same writable roots; there is no automatic per-task checkout or separate filesystem namespace in this path. Each task has its own public/native conversation and queue. This allows parallel work but means filesystem coordination remains necessary when tasks write the same files. That collision risk is an inference from the shared paths, not a demonstrated corruption bug. [Native session workspace and instructions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L490-L523) [Resume settings and instruction assembly](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L946-L968)

Task sessions explicitly disable Computer Use in the session-specific agent object. MCP selection and non-Codex session parameters receive that disabled setting, and the prompt directs desktop work back to the main chat while still allowing the embedded browser. The `start_task` tool refuses calls from execution threads, including tasks, channels and external messaging, so it is exposed as a main-chat initiation mechanism. This should be described as a desktop-control restriction, not a universal ban on every visual operation: the separate `list_capture_sources`/`capture_screen` handler checks the stored agent's Computer Use flag, blocks external messaging, and requires channel capture approval; the inspected handler does not add a task-thread exclusion. [Task session settings and MCP filtering](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/thread-lifecycle.ts#L846-L877) [Task desktop-control instruction](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/developer-instructions.ts#L193-L195) [Task initiation restriction](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-tasks/agent-tasks.ts#L228-L247) [Screen-capture scope checks](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L1002-L1058)

## Evidence limits and documentation drift

The source supports the runtime mechanisms above. It does not prove consistent model use of memory tools, correct recall of every fact, compliance with instructions, end-to-end live provider restoration, or performance under load. No such tests were run in this research task.

Two documents lag the inspected implementation. `docs/architecture/providers.md` says ACP/Muse instructions are inserted on each normal turn, while the current clients send them conditionally. `docs/architecture/agents.md` has the newer conditional-delivery description. [Updated instruction documentation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/docs/architecture/agents.md#L310-L314) The same agents document says ACP holds only text/thinking and only while the process holds the session. [Older ACP history description](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/docs/architecture/agents.md#L417-L435) Current ACP code retains tool items and writes completed fragments to SQLite. The work-step capture operation still requires an already-loaded client, so that operational restriction remains. Source should decide the implementation description. For cubebot, the most useful transferable decisions are independent agent/public-thread/native-session identities, durable queue intent, explicit acknowledgement uncertainty, bounded history recall, and a small inspectable memory store. The provider-specific client implementations and compatibility recovery rules are the expensive part. A cubebot design can adopt these boundaries while starting with one provider and a much smaller supported capability matrix. This is a design inference from the source, not an upstream performance claim.
