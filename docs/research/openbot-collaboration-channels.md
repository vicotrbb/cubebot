# OpenBot collaboration and channels: source audit

Research date: 2026-10-22. Source: `nightly-labs/openbot`, commit `cfee2971f29cdb7c16272e60ae912de7fbb30693`, inspected from `/tmp/openbot-analysis-20261022`. All source links below pin this commit. This is a source audit, not a runtime qualification. No upstream code was changed, dependencies installed, or model turns run. A web fetch of the pinned GitHub tree was restricted; the checkout supplied the primary evidence.

## Finding

OpenBot implements two distinct forms of agent collaboration. Direct agent exchanges use a durable asynchronous mailbox between persistent local agents. Shared channels add a canonical transcript, a routing step, a task dependency graph, and explicit assignments. A channel looks like a room, but its members do not all receive a model turn for every message. Only an assigned owner or an owner whose awaited work has finished runs. This keeps ordinary conversation from becoming a broadcast loop. [Direct tool contract](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/openbot-tools.ts#L599-L615), [channel context instructions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-history.ts#L158-L177), [completion transition](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1783-L1837).

The important reusable design is the separation of four records: an agent is a persistent identity; a thread is an execution context; a task is durable requested work; an assignment is an attempt by an agent on a particular task revision. A provider turn belongs to an assignment, not to the channel itself. [Task contract](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L37-L65), [assignment record](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-store.ts#L32-L65), [channel thread creation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-store.ts#L447-L488).

## Terms and boundaries

| Object | Actual meaning | Important limit |
| --- | --- | --- |
| Persistent agent | A local teammate with a profile, provider/model, tools, memory and continuing identity | `send_message` resolves local agent IDs; it is not a cross-host agent federation API |
| Sidebar section | UI grouping of agents | Grouping is not a shared transcript or execution queue |
| Shared channel | Host-owned chat with members, lead, title and instructions | Membership selects eligible agents; it is not a human privacy ACL |
| Channel task | Requested work with owner, sources, expected result, dependencies, resources and revision | A task has one owner at a time |
| Channel assignment | One dispatch attempt with delivery, provider turn, context cursor and resource reservation | Only one active assignment may serve a task |
| Execution thread | Provider-independent conversation identity for one agent/channel pair | Separate from the agent's normal chat |
| Team API | Human clients accessing a host's data and actions | It does not turn remote humans into agent members |
| External messaging | Slack/Discord/Telegram conversation linked to an answering agent | Separate from OpenBot channel chats; it can use direct teammate delegation |

Evidence: [local tool declarations](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/openbot-tools.ts#L340-L371), [channel fields](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L18-L65), [single-owner scheduling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L551-L569), [Team routes](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/main/team-api/route-channels.ts#L50-L97), [messaging return propagation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L1467-L1484).

There is no channel subscription or passive participation field in `ChannelMember`: it contains only `agentId`. The public command union supports save, restore, archive, send, routine request, stop/resume/reassign and read; it has no subscribe/unsubscribe or automatic-response policy. The prompt explicitly leaves unassigned members idle. UI event subscriptions refresh views, not model participation. This is a scoped absence finding from the channel contracts, service, store and tools, not a claim about every future extension. [Member/command definitions](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L18-L28), [command union](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L108-L155), [idle-member instruction](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-history.ts#L158-L163).

## Direct agent-to-agent exchange

An agent discovers peers with `list_agents`, which exposes name, title, description and progress. It can inspect one with `read_agent`. `create_agent` creates a persistent teammate when requested; this is distinct from a provider's transient subagent mechanism. `interrupt_agent` is constrained to work that the caller requested. Its declared contract excludes user, routine, channel and other-agent work. [Discovery and control tools](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/openbot-tools.ts#L345-L372).

`send_message` accepts 1–32 recipients, up to 100,000 characters, up to 10 local file paths, an optional original-message ID and `expectsReply`. The router rejects duplicate recipients, self-send, unknown agents and hidden agents. It derives the sender from the call, writes to the mailbox with a tool-call idempotency key, publishes queue changes, and schedules the recipients. It returns a receipt without waiting for their answers. [Schema](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/openbot-tools.ts#L599-L615), [router](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L1424-L1496).

The mailbox has one message and a separate delivery per recipient. Each delivery starts queued and gets its own ID and queue order. A repeated idempotency key returns the existing receipt. Files are copied into a message transfer before the stored message and delivery records are constructed. This gives the request a durable payload rather than a shared pointer to the sender's current draft. [Enqueue idempotency](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/mailbox-store.ts#L446-L454), [payload and delivery construction](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/mailbox-store.ts#L502-L558).

The recipient sees a collaborator envelope with sender and message IDs. Requests tell it to send a concise `Status`, `Result`, `Evidence`, and, for blocked work, `Unblock` answer. A result uses `replyToMessageId` and `expectsReply:false`. Informational messages also use false and explicitly forbid acknowledgements. This is instruction-level loop control, reinforced by the runtime's auto-result guard. [Delivery envelope](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/delivery-content.ts#L198-L226), [runtime guard](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L1104-L1144).

For a completed turn in the agent's ordinary conversation, a fallback relays the recipient's final text to the immediate sender if the request expects an answer and no explicit reply or same-turn message to that sender exists. The completion call site excludes separate execution threads and failed/interrupted turns. [Relay call site](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L847-L864). The relay uses `auto-result:<turn>:<message>` and sets `expectsReply:false`. Its chain-origin check stops a return to the origin from being relayed again. This is not an arbitrary recursive conversation engine. [Fallback relay](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L1104-L1144), [chain traversal](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/mailbox-store.ts#L1419-L1442).

If A sends one request to B and C, B's answer waits while C's copy remains queued, starting or running. Once those copies end, the answers can enter one requester turn. A new human message can take the available answers early. Failed/interrupted/cancelled copies without an answer can be identified in the prompt. This is batching for one fan-out request, not a global barrier across all of A's work. A slow or indefinitely queued recipient can hold the batch; no timeout is visible in this hold predicate. [Reply batching](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/mailbox-store.ts#L1157-L1196), [hold predicate](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/mailbox-store.ts#L1209-L1230).

OpenBot tells agents to end their current turn after delegation and to avoid provider `wait_agent` tools. Those tools belong to provider-native subagents and do not wait for OpenBot peers. `await_event` is another separate facility: persisted unfinished work awakened by an agent routine or script event, not a blocking peer-result wait. [Delegation guidance](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/tool-guidance.ts#L125-L129), [open-wait semantics](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-waits/agent-waits.ts#L60-L98).

## Channel routing and execution walkthrough

1. A human sends a channel command with an operation ID, text, optional target, optional reply ID and attachment drafts. The host commits attachments before accepting the request, so restart cannot erase unsent draft references. The command receipt prevents repeat operations. [Command handling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L250-L270), [attachment commit](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L345-L370).
2. The service chooses an owner without a model when the user targets an agent, replies to a task, replies to an agent message without a task, sends a recognized continuation to the sole open task, or only one member is eligible. Corrections increment the task revision, supersede earlier agent output and pause affected children. The continuation heuristic is an English regex (`also`, `instead`, `actually`, `please change`, `change that`, `correction`, `continue`, `yes`, `no`, `use that`, `make it`). Other languages do not get that specific shortcut. [Deterministic selection/correction](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L375-L458), [single-member shortcut](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L772-L781).
3. Ambiguous requests use the lead's provider, model and reasoning setting in a separate text-generation client with no work tools. The allowed result is exactly one agent ID, existing task ID, question, or idle result. The prompt includes membership/profiles, task, saved summary, bounded recent excerpts and open tasks. It instructs the model never to select everyone. A state fingerprint discards stale routing results. Invalid routing pauses and asks for correction rather than broadcasting. [Router schema/budgets](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L83-L101), [router execution](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L783-L981), [tool-less client](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-service.ts#L885-L920).
4. The scheduler checks agent availability, dependencies, active assignments, channel parallelism and resources. It persists a starting assignment before enqueuing a mailbox delivery keyed by assignment ID. The assignment snapshots the current resources and task revision. [Assignment scheduling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L990-L1068).
5. The ordinary agent drain prepares the channel-specific thread and bounded context. Preparation validates task revision and state before and after context generation. Provider acceptance persists context sequence/summary version and associates the assignment with the turn. [Prepare/accept](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1571-L1630).
6. The owner may work directly, assign children, or transfer the whole task. A child adds a dependency to the parent; a transfer changes the existing task owner and revision. At turn completion, a parent with newly created children waits, then returns to queued once its children complete. The new owner must wait for the old assignment to terminate. [Handoff mutation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1988-L2043), [parent continuation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1783-L1837), [single assignment guard](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L560-L569).

The selected lead is a router and summary model. It need not own every request. The selected owner performs the orchestration of that task. There is no separate all-powerful channel agent. Direct `send_message` is rejected inside a channel thread, so the model cannot use that API to evade the channel graph. [Lead routing](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L783-L848), [tool boundary](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L687-L708).

## Channel tool contract

| Tool | Behavior |
| --- | --- |
| `channel_history` | Reads an earlier transcript page or resolves a channel attachment; it does not start agents |
| `channel_assign` | Creates one child task; caller remains responsible for integration |
| `channel_transfer` | Changes ownership of the whole current task; caller must end its turn |
| `channel_result` | Publishes an idempotent result message; provider turn completion settles task state |
| `channel_remember` | Saves a durable channel fact immediately |
| `channel_forget_memory` | Deletes a fact by text, preferring an exact match |

Handoffs require another available member, task text, expected result and at least one valid source message. Optional resources declare `browser` and absolute `workspace:<path>` reservations. Optional dependencies must exist and cannot create a dependency on the current task through an existing path. Calls require a live assignment for the caller's current turn and task revision. [Declarations](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-tools.ts#L4-L57), [active assignment/result validation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1841-L1912), [handoff validation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1930-L1990).

## Context, history and memory

A channel has one canonical sequence of messages with stable IDs and authors (`member`, `agent`, `coordinator`). Each member gets a separate persistent execution thread. Context state records its last accepted provider session, delivered sequence and summary version. This prevents a channel from replacing or mixing with the agent's ordinary chat thread. [Message contract](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L58-L65), [context storage](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-store.ts#L447-L488), [acceptance cursor](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-store.ts#L591-L638).

Every assignment receives a self-contained packet, even if its provider session still exists. It includes channel title/instructions/members, current task, dependency task records, channel memories, summary, referenced messages including reply ancestry, recent messages, and the current expected result. Its ceiling is the lesser of 120,000 characters and a provider-dependent budget. It is not a token limit. If the complete packet still exceeds that budget, preparation fails rather than silently removing the current assignment. [Packet construction](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-history.ts#L84-L194), [provider budget hook](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent-service.ts#L923-L926).

When unsummarized history occupies more than half that budget, the lead summarizes older non-streaming messages. A single oversized message is split into model-sized pieces. The summary must be nonempty and at most 12,000 characters. It has a version and coverage sequence; concurrent summary work uses a version check. Requested source messages remain available in full and the transcript stays retrievable. This provides bounded continuity, but summary accuracy still depends on the model. [Summary algorithm](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-history.ts#L95-L158).

The prompt filters routing receipts and model reasoning rows from other models' input. It retains ordinary commentary because it can contain a useful answer. `channel_history` also removes member thinking from returned pages. Human-facing stored history and model input therefore differ. [Context filter](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-history.ts#L36-L54), [history tool filter](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1875-L1886).

Channel memory is distinct from a summary and from each agent's own memory. Channel facts are injected as untrusted data on every assignment. Writes are immediate, so no provider-thread invalidation is needed for the next packet. The declared limits are 32 facts and 500 characters per fact. Repeated normalized text is unique in storage. Deletion prefers an exact case-sensitive text match and falls back to a case-insensitive match if none exists. [Memory delete behavior](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-memory-store.ts#L49-L61). [Memory prompt](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-history.ts#L178-L186), [immediate writes](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1914-L1928), [limits](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/input-limits.ts#L28-L34), [schema uniqueness](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-schema.ts#L63-L74).

## Concurrency, deadlock controls and budgets

The limits are not a universal model-turn budget. A channel permits two active assignments and a root request permits eight automatic handoffs (`channel_assign` or `channel_transfer`). Initial routing, initial owner work and resumed owner turns are not all charged to that counter. The ninth handoff attempt pauses the unfinished root branch, increments revisions and interrupts its work. Human resume/reassign resets assignment counts for the affected branch. [Constants](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L15-L16), [handoff limit](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1953-L1972), [counter update](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L2013-L2023), [human action reset](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L493-L515).

An agent has one main lane, shared by normal chat, channel work and external messaging. Its separate task lanes can run beside channel work when the provider supports concurrent turns and task capacity permits it. A provider with one-turn-at-a-time semantics serializes those lanes. A channel assignment holds only its agent's main lane, not all agents on the host. [Drain lane model](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L80-L144), [drain guards](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L268-L303), [channel lane guard](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1240-L1249).

Resource checks span all channels. Two declarations conflict for the shared browser, identical workspace paths, or an ancestor/descendant pair. Paths are canonicalized. Empty resources, `none`, and legacy `host` reserve nothing. These are voluntary scheduling declarations, not filesystem or process isolation. The active assignment keeps its initial resource snapshot even if a transfer changes the task record. [Global scheduling/resource checks](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L542-L548), [reservation snapshots](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1008-L1043), [resource validation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1974-L1987), [conflict logic](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L2464-L2505).

Specific anti-stall measures exist: resource waiters get an age order; only an otherwise-ready older waiter can hold later work; a finished assignment reschedules the held agent; a channel delivery moves ahead of ordinary messages that arrived during attachment copying; dependencies reject cycles. Queue age is in memory and is rebuilt after restart. These mechanisms address known races. They do not prove arbitrary model workflows cannot deadlock. [Ready waiter/fairness](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L572-L650), [copy race reorder](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1075-L1089), [cycle guard](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1988-L1990), [in-memory queue order](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L118-L125).

No generic direct-message hop limit, global conversation turn allowance, or peer-wait cycle detector was found in the examined router/mailbox/turn-lifecycle code. Direct exchange loop control rests on the reply protocol, no-reply flag, self-send refusal and fallback relay guards. A cubebot requirement for a cost budget, TTL, maximum total turns, or direct-message graph cycle rejection would need its own implementation and tests. This is an absence finding limited to those inspected paths. [Direct dispatch](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L1424-L1500), [relay guards](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/turn-lifecycle.ts#L1104-L1144).

## Recovery, corrections and routines

Stop pauses the selected task and descendants and increments their revisions. Reassign moves the selected task and resumes stopped children. A new correction can steer current work or interrupt the old revision. Calls from obsolete assignments are rejected, and completion changes task state only when the assignment revision still matches. This protects the task's logical result from stale work; it cannot undo external effects already performed by that work. [Stop/resume/reassign](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L483-L517), [correction handling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L451-L458), [revision-sensitive completion](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1795-L1819).

Recovery reloads execution transcripts, finds deliveries by saved ID or assignment idempotency key, preserves confirmed live/queued work, and finalizes confirmed completed deliveries. An unconfirmed outcome becomes an interrupted assignment and paused task with an instruction to inspect prior work before resuming. The policy avoids blind retries of possibly executed side effects. The generic drain also waits for lifecycle events after an unconfirmed provider start. [Channel recovery](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1502-L1568), [uncertain start handling](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/drain-scheduler.ts#L827-L849).

Channel routines create durable runs and issue ordinary channel `request` commands. A request always starts a new root task, so a routine instruction beginning with “Continue” cannot accidentally correct a human's open task. Run state derives from stored tasks: paused dependencies become needs-attention, failed dependencies become failed, and all completed/cancelled tasks yield succeeded. Webhook reception and usage-limit skip behavior are present in the scheduler; the broader routine trigger engine is outside this note's detailed audit. [Routine command isolation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L463-L481), [run-state derivation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-routine-scheduler.ts#L37-L98), [webhook path](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-routine-scheduler.ts#L165-L192).

## Human Team clients and external chat

Channel reads/listing are available to authenticated Team members without per-channel membership checks. Administrative role checks guard archive, restore and permanent deletion. Adding an agent to a channel requires that member to have chat access to that agent. The channel membership list must therefore not be presented as a private-room security boundary. [Team access path](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/main/team-api/route-channels.ts#L50-L97), [agent-add authorization](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/main/team-api/route-channels.ts#L125-L141).

Channel capabilities are versioned. `channel-chats-v1` gates the surface, while deletion and attention metadata have distinct compatibility support. One-time channel routine schedules are filtered/refused on the released Team channel codec, although local IPC can support them. Remote access uses the host's records; it does not add a remote channel database. [Capability constants](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L7-L8), [remote schedule filter](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/main/team-api/route-channels.ts#L165-L184), [host database schema](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-schema.ts#L5-L52).

External Slack/Discord/Telegram orchestrators are normal persistent agents used as entry points for external human conversations. When they delegate, `messagingReturn` accompanies the request and routes the answer back into the original external conversation's execution thread. This is distinct from channel assignment ownership. The router discovers that origin from the active delivery; the model does not choose an arbitrary return connection. [Origin propagation](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/agent/openbot-tool-router.ts#L1467-L1484), [mailbox return storage](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/mailbox-store.ts#L532-L548).

## Documentation drift and qualification limits

- `tool-guidance.ts` says replies are never forwarded automatically. `TurnLifecycle.#relayAgentResult` supplies an automatic fallback under specific conditions. The fallback implementation controls current behavior; the categorical guidance is stale or misleading. - The messaging [“Order” paragraph](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/docs/architecture/channels-and-messaging.md#L372-L373) still describes channel work as holding the host. Current `mayDrain`, drain guards, and the concurrency E2E specify only the assigned agent's main lane. Do not use that paragraph as the concurrency contract. [Current guard](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/src/backend/channel-service.ts#L1240-L1249), [E2E intent](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/scripts/channel-concurrency-e2e.ts#L1-L11).
- Documentation uses “purpose” and “responsibilities” broadly. Current channel fields are `title` and `instructions`; a member has only an agent ID. Old `purpose` records are normalized for compatibility. There is no typed per-member role field in this contract. [Current fields](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L18-L28), [legacy normalization](https://github.com/nightly-labs/openbot/blob/cfee2971f29cdb7c16272e60ae912de7fbb30693/packages/contracts/src/ipc-chat-channels.ts#L162-L174).
- Eight assignments is an anti-runaway handoff count, not a total turn, dollar, elapsed-time or token budget. Declared resource serialization is not a sandbox. A source audit cannot prove summary fidelity, model compliance, fairness under all loads, exact-once external effects or restart correctness on every provider. The contracts and guards above are implemented mechanisms; live acceptance remains unverified.

## Design implications for cubebot

These are recommendations inferred from the inspected mechanisms, not claims that cubebot already implements them.

1. Keep persistent identity, provider sessions, task state and dispatch attempts separate. Put revisions and idempotency keys at their boundaries.
2. Treat room participation as a product decision. Explicit assignment is quieter and cheaper than waking every member. If subscriptions are wanted, add precise event filters, reply rules, cost limits and human visibility.
3. Use one authoritative transcript with bounded, replayable context packets. Keep saved facts separate from lossy summaries and original evidence.
4. Make uncertain execution a first-class state. Do not retry an external side effect just because a provider response was lost.
5. Keep human room authorization separate from agent membership. OpenBot's server-wide channel visibility is a real product choice, not a default privacy model to inherit accidentally.
6. Add an explicit total-work budget if required. OpenBot's handoff ceiling and no-reply protocol do not cover every runaway cost or logical waiting cycle.
7. Define task completion independently from text publication. OpenBot's `channel_result` publishes a row; the assignment's provider outcome settles task state.
8. Test the races at the scheduler/mailbox/provider boundary. UI smoke tests alone cannot establish recovery and duplicate-effect guarantees.
