# Calendar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A console Calendar (Month / Week / Day) merging the user's own calendar events with their agents' scheduled routine runs, with click-anchored details and create / edit / delete for both.

**Architecture:** Connectors gain the missing calendar write tools and, for CalDAV, local recurrence expansion. Routines gain a per-routine IANA time zone. A new orchestrator `calendar` module reads a range by calling connector tools with the connection's credential (as `check`/`poll` already do) and by expanding routine crons, and routes event writes to the right tool. The web app adds `features/calendar` with a pure date/layout model and the views.

**Tech Stack:** Rust (axum, sqlx, utoipa), new crates `chrono-tz` 0.10 and `rrule` 0.14 (time zones and RFC 5545 rules cannot be done correctly without the IANA database); TanStack Start, React 19, TypeScript, Bun, `Intl.DateTimeFormat` for display.

**Spec:** `docs/superpowers/specs/2026-11-09-calendar-design.md`

## Global Constraints

- Follow `AGENTS.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`. Cyclomatic complexity ≤ 15 per function in `src/`. `just check` passes at the end of every task that touches code.
- Ponytail rules for all code: smallest complete change, reuse existing helpers and patterns, no speculative options; match surrounding naming and comment density.
- All UI work goes through the `impeccable` skill; verify visuals in the live browser (not headless reduced-motion captures).
- Only calendar connections with `created_by` = viewer; only routines of agents with `created_by` = viewer.
- Webhook-only and connection-event-triggered routines never appear. Routines with a schedule and a trigger appear by their schedule.
- A routine with more than 24 runs in a local day appears that day as one digest item.
- Every time shown in the profile `time_zone`; browser zone when the profile's is empty.
- Recurring event edit / delete asks "This event" or "All events".
- Connection `level` governs writes: an event from a connection whose level does not offer the write tool is read-only.
- Connector brand marks from `modules/brand/logos.ts`.
- Range limit for `GET /api/calendar`: at most 62 days.
- New migrations continue at `0070_`.
- Lockfiles current (`Cargo.lock`, `bun.lock`).

## Review Focus

1. DST transitions: a 09:00 `America/New_York` routine stays at 09:00 local across 2026-03-08 and 2026-11-01; a 02:30 run on the spring-forward day runs once at 03:00; on the fall-back day it runs once. (Task 1 tests.)
2. A CalDAV server that ignores `<c:expand>` and returns a master with RRULE, EXDATE and a RECURRENCE-ID override: every occurrence in range appears exactly once, the moved one at its new time. (Task 2 tests.)
3. One failing connection (expired token, server down) must not blank the calendar: other sources still render and the failed one shows its problem. (Task 6 test.)
4. Events that cross midnight or span days, and all-day events, in a zone west of UTC (`America/Sao_Paulo`) land on the right local days in Month and Week. (Task 7 tests.)
5. A user who is not the connection's creator cannot read or write its events through `/api/calendar` even by sending its id. (Task 6 test.)

```rust
pub struct CalendarRange { pub sources: Vec<Source>, pub items: Vec<Item> }
pub struct Source { pub id: String, pub kind: &'static str /* "calendar" | "agent" */, pub name: String,
    pub connector: Option<String>, pub connection: Option<Uuid>, pub color: Option<String>,
    pub writable: bool, pub problem: Option<String> }
pub struct Item { pub kind: &'static str /* "event" | "routine" | "run" | "digest" */, pub id: String,
    pub source: String, pub title: String, pub start: String, pub end: Option<String>, pub all_day: bool,
    pub editable: bool, pub event: Option<EventDetail>, pub routine: Option<RoutineDetail> }
pub struct EventDetail { pub connection: Uuid, pub calendar: String, pub event: String,

    pub location: Option<String>, pub description: Option<String>, pub link: Option<String> }
pub struct RoutineDetail { pub agent: Uuid, pub routine: Uuid, pub schedule: String, pub time_zone: String,
    pub runs: Option<u32> /* digest */, pub outcome: Option<String> /* run */, pub turn: Option<Uuid> /* run */ }
```

`start`/`end`: RFC 3339 UTC for timed items, `YYYY-MM-DD` (end exclusive) for all-day. Source ids: `calendar:<connection>:<calendar>` and `agent:<agent>`.

Endpoints:
- `GET /api/calendar?from=<rfc3339>&to=<rfc3339>` → `CalendarRange`. `to - from` ≤ 62 days, else 400.
- `POST /api/calendar/events` `{connection, calendar, title, start, end, all_day, time_zone, location?, description?}` → `Item`.
- `PUT /api/calendar/events` `{connection, calendar, event, etag?, occurrence?, scope: "one" | "all", series?, title?, start?, end?, all_day?, time_zone?, location?, description?}` → `Item`.
- `DELETE /api/calendar/events` with body `{connection, calendar, event, etag?, occurrence?, scope, series?}` → 204.
- Routines are written through the existing `/api/agents/{agent}/routines` endpoints; no new routine API.
