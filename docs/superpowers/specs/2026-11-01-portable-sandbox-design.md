# Portable sandbox: one agent image, declared runtimes

Date: 2026-11-01. Status: implemented 2026-11-02, PRs #49 to #53. Amends ADRs 0084 and 0085; restores ADR 0076 as written.

## Intent

Cubebot must install with agents on, with full feature parity, on every target: any Kubernetes cluster, a Linux computer or VM, and every Mac. Today every agent is a KVM guest of Cubebot's own VMM, which is x86_64 only and needs `/dev/kvm`. That excludes Macs, arm64 hosts, EKS managed node groups, AKS without a Kata pool and most VPSes. The function an agent needs (a Linux userland, a persistent workspace, a desktop with a browser and terminal, screenshots and input the model's code cannot forge, outbound-only network) does not need a VM. Only one property does: containing a kernel exploit from software the agent installed. This design separates the two: the agent image runs everywhere, and the strength of the boundary is a declared property of the installation's runtime.

## Goals, non-goals, anti-goals

Goals: one agent image that runs as a plain container or as the root disk of a KVM guest; the same desktop, browser, vault, login handoff, rooms, files, routines and skills on both; the KVM VMM kept as the strong runtime wherever `/dev/kvm` exists; the full `docker-*` system suites runnable on plain CI runners in container mode; fewer lines than today.

Non-goals: an aarch64 VMM port, a macOS Hypervisor.framework backend, a userspace guest network, system-wide package installs by agents, gVisor or Kata qualification. Each is a later, independent step.

Anti-goals: an installation that reports a stronger boundary than it has; agent-run code able to inject input as a person or to replace the frames a person sees; frames stored in the orchestrator.

## Decisions

1. **The desktop lives inside the agent's sandbox.** Two X servers run as root-owned processes started by the agent's init: an outer Xvfb that only the arbiter can connect to, and Xephyr, a nested X server on the outer display, started with the XTEST extension disabled, as the tool user's desktop (`DISPLAY=:1`). openbox, xwallpaper, Chromium and every tool-user process connect to Xephyr. The arbiter injects input with XTEST on the outer display, which Xephyr receives as real device events, and reads frames with GetImage on the outer display. Tool code cannot inject (no XTEST on its display) and cannot reach the outer display (no cookie, socket owned by root). The guest kernel loses DRM, virtio-gpu and virtio-input; it needs no uinput. Settled by the spike (`docs/research/2026-11-01-xephyr-desktop-spike.md`, all four checks passed, median key latency 0.29 ms): the outer server starts with `-nolisten local -nolisten tcp` so no abstract or TCP socket exists, its Unix socket is chmod 0700 right after start and before any tool-user process exists, and its cookie is root-only; the arbiter sets input focus to Xephyr's window at startup, since the outer display has no window manager; Xephyr is placed at (0,0) at 1280x800 so both displays share coordinates. Tool code on `:1` can still send XSendEvent synthetic events, which carry the synthetic flag and which Chromium ignores for keys, and can move the pointer; today's single-server desktop allows the same, and the ADR 0085 amendment says so.
2. **The arbiter moves unchanged in logic.** `apps/sandbox/src/kvm/desktop.rs` (modes, attribution, login-handoff refusals, tile frames) and `apps/sandbox/src/png.rs` move to `apps/agent/src/desktop/`. Its two device edges become traits, `Screen` (frame source) and `Input` (event sink), with an X11 implementation through the `x11rb` crate and in-memory fakes for tests. The wire protocol in `modules/protocol/src/desktop.rs` is unchanged. The agent's computer tool and browser tools connect over a Unix socket in `/run` instead of vsock port 1025. The orchestrator's host channel runs `cubebot-agent desktop` through the platform's exec, with the same stdin/stdout relay `cubebot-sandbox desktop` has today.
3. **The VMM keeps four devices and a relay.** Block, net, vsock and serial. virtio-gpu, virtio-input, the desktop module and the PNG encoder are deleted from `apps/sandbox`. The VMM's vsock accepts only guest-initiated streams, so in `kvm` mode the arbiter dials host port 1026 at startup and the sandbox bridges that stream to the Unix socket at `CUBEBOT_GUEST_DESKTOP_SOCKET`; `cubebot-sandbox desktop` stays as the host channel command, a relay of a few dozen lines. In `container` mode the host channel command is `cubebot-agent desktop`, which connects to the arbiter's Unix socket directly. The orchestrator's exec channel picks the command by runtime.
4. **The agent image gains a `container` entry.** `cubebot-agent container` is PID 1 of a container: it reads its configuration from the environment (no vsock control channel), skips mounting disks and the kernel `ip=` route setup, creates the tool and browser users' directories on the mounted workspace, starts the desktop when `CUBEBOT_COMPUTER_ENABLED=1`, runs the agent, reaps children and exits with the agent's status. `*_FILE` variables are files mounted by the launcher. Guest init (`cubebot-agent guest`) and container init share one module for everything after the environment is known.
5. **The launcher chooses a runtime.** Both `ControllerConfig` and `DockerConfig` gain a required `runtime` field: `{"kind":"kvm"}` or `{"kind":"container","class":"<optional RuntimeClass or Docker runtime name>"}`. In `kvm` mode the pod and container shapes are exactly today's. In `container` mode the pod runs the agent image directly: no device plugin resources, no `NET_ADMIN`, `/dev/net/tun` or `/dev/kvm`, root with only `SETUID`, `SETGID` and `CHOWN`, baseline Pod Security, optional `runtimeClassName`; the workspace volume is mounted at `/var/lib/cubebot`, so `workspace/`, `runtime/` (the journal) and `browser/` have the same paths as inside the guest and crash recovery from the journal is unchanged; the bootstrap token is the projected token file as today. The runtime is installation-wide and set at install. A launcher refuses to start an agent whose volume carries the other runtime's layout (`workspace.ext4` present for `kvm`, a directory tree for `container`) with a clear agent status; there is no conversion in this design. The Docker backend does the same with `docker run` flags and an optional `--runtime`. The sandbox image for `kvm` stays `cubebot-sandbox`; the image for `container` is the agent image, so the config field `sandbox_image`/`image` names whichever the runtime needs.
6. **The runtime is declared.** The installation API reports the runtime kind and class; the console shows it on the installation view. The console never calls a container runtime a VM.
7. **Qualification moves to CI.** Every `docker-*` system test takes `CUBEBOT_SANDBOX_RUNTIME=kvm|container` (default: `kvm` where `/dev/kvm` exists, else `container`). On every push, CI runs a container-mode check with no provider key: one agent boots in container mode against the scripted stand-in provider (`CUBEBOT_TEST_PROVIDER_ORIGIN`, as `just integration` uses), runs one bash tool call, and the host channel shows the wallpaper, refuses a person's key until they take control and then delivers it. The real-model `docker-*` suites run nightly in container mode on GitHub runners with the provider secret, and in `kvm` mode on the homelab host as today.
8. **ADR amendments.** ADR 0085: the arbiter is a root process inside the sandbox with two X servers; integrity holds against the model's code and against the tool user, not against a root or kernel compromise inside the sandbox, which the `kvm` runtime still contains. ADR 0084: "one backend, no unisolated mode" becomes "one agent image, declared runtimes, no undeclared or misreported one"; the VMM remains the strong runtime. ADR 0076: accepted as written again (standard containers, optional RuntimeClass). STATUS and the reference document the runtime field.

## Constraints

- Rust everywhere in backend, agent and sandbox; `unsafe` only in `apps/sandbox/src/kvm`. `x11rb` is the one new dependency, pure Rust, locked.
- Cyclomatic complexity <= 15 per `src/` function; `just check` green at every step; lockfiles current.
- Nothing in the orchestrator stores frames. The host channel relays bytes unparsed as today.
- Tools and the browser run as uids 10001 and 10002; the arbiter and both X servers run as root in the sandbox. The outer display's socket is mode 0700 root; Xephyr's socket is readable by the tool user.
- Read-only root in the KVM guest stays; the container runtime's root is writable but agents still install into the workspace (ADR 0034).

## Order of work

1. Spike (throwaway): Xvfb + Xephyr (`-extension XTEST`) + openbox + xwallpaper + Chromium in a Debian container; prove XTEST on the outer display reaches inner clients, GetImage shows the desktop, and measure typing latency. Record the result in `docs/research/`.
2. Desktop into the image; KVM remains the only runtime; delete the VMM devices; run the desktop suites on the KVM host.
3. Container runtime in the agent and both launchers; installation API and console badge; system suites gain the runtime switch; CI runs them in container mode.
4. Release pipeline: GHCR images (agent image for amd64 and arm64; orchestrator and web multi-arch; sandbox amd64), digests written to the chart.
5. Helm chart in `deploy/chart`, translated from `tests/system/cluster_chat_setup.py`, with `sandbox.runtime`; the fixture installs the chart.
6. Installer: `deploy/install.sh` and a `cubebot` wrapper over Compose for Linux and Mac; README and site.
7. Later, independent: gVisor and Kata as pass-through classes; Apple's `container` behind the Docker CLI seam; userspace NAT for KVM pods; aarch64 KVM.

## Left to the builder

Exact socket paths under `/run`; how the arbiter learns the Xephyr geometry; `x11rb` feature set; whether Xephyr is started with `-screen 1280x800` or follows the outer display; the shape of the `Screen`/`Input` traits; test fixtures for the X11 edges (a headless Xvfb in `cargo test` is acceptable if present, otherwise the fakes only); Helm value names; installer wording.
