# Sandbox application

`cubebot-sandbox run` runs one agent in a KVM guest (ADR 0084); there is no other backend. The orchestrator starts it as the only container of an agent's pod, or as a Docker container without a cluster. On a Linux host without either, run the same command with the same `CUBEBOT_*` environment, as root with `/dev/kvm`, `/dev/net/tun`, `ip` and `tc`, inside a network namespace of its own (`ip netns exec <namespace> cubebot-sandbox run`) whose default route reaches the orchestrator. In the host's own namespace the sandbox refuses to start, since its redirect would hand the host's interface to the guest. Keep `CUBEBOT_BOOTSTRAP_TOKEN_FILE` on a tmpfs such as `/run`: the sandbox sends its contents to the guest over vsock, and nothing passes credentials on the command line.

The sandbox (x86_64 Linux only; elsewhere `run` fails) drives KVM through `nix` ioctls with no VMM crates; `src/kvm` is the only module in the workspace allowed `unsafe`, for KVM, guest memory and the tap ioctl. It boots the bzImage in `CUBEBOT_GUEST_KERNEL` in one memory region with one thread per vCPU, which the guest finds through an MP table, and relays a 16550 serial console to stdout. `CUBEBOT_GUEST_VCPUS` (1 to 32, default 2) and `CUBEBOT_GUEST_MEMORY_MIB` (256 to 3072, default 2048, below the device windows) size the guest; the orchestrator's pods use the defaults with a 3 GiB memory limit. Its virtio-mmio devices share one split-virtqueue module (`src/kvm/virtio`):

- **Disks.** virtio-blk serves the read-only root image in `CUBEBOT_GUEST_ROOT` as `vda` and the workspace disk in `CUBEBOT_GUEST_WORKSPACE` as `vdb`. A missing workspace disk is created as an 8 GiB sparse file and formatted with `mkfs.ext4`; an existing one is never reformatted. Guest flushes reach the file with `fdatasync`.
- **Network.** virtio-net sits on `tap0`, which the sandbox creates in its own network namespace (the pod's), and tc mirred redirects join `tap0` and the default-route interface in both directions. The guest takes that interface's MAC, MTU, IPv4 address and gateway, and the first two IPv4 resolvers, through the kernel's `ip=` parameter, so pod NetworkPolicy applies to exactly the guest's traffic; when the gateway is outside the subnet, as with Calico's /32 addresses, guest init adds the default route on-link. This needs `CAP_NET_ADMIN`, `/dev/net/tun`, and `ip` and `tc` from iproute2.
- **Control.** virtio-vsock carries one stream from the guest to host port 1024 ([`cubebot_protocol::guest`](../../modules/protocol/src/guest.rs)). The sandbox sends the agent's `CUBEBOT_*` environment over it, with each `*_FILE` variable's file contents in place of its path, and every minute resends any such file that changed, such as the rotated projected token. The guest reports liveness back, which the sandbox logs, and then the agent's exit status, which becomes the sandbox's own; a guest that ends without one exits 1. The first SIGTERM or SIGINT ends the host's side of the stream, and the guest stops the agent, unmounts its workspace and reboots, which ends the VM; a second signal ends the VM at once.

The kernel's init is `cubebot-agent guest` (see the [agent](../agent/README.md)). `tooling/guest` builds the kernel and the root image. `just guest-boot` runs both in a network namespace standing in for a Calico-style pod (a /32 address behind a link-local gateway): the agent must reach a stand-in orchestrator over TLS from the pod address with the forwarded token, report liveness over vsock, exit 0 and cleanly on SIGTERM, and reopen its journal on a second boot of the same workspace. A stand-in orchestrator is not agent, isolation or NetworkPolicy qualification.

The image is built from [`Dockerfile`](Dockerfile) with the repository root as context and `--build-context guest=target/guest` after `tooling/guest`; without that context the build fails. It contains `cubebot-sandbox`, `cubebot-agent` and the guest kernel and root image under `/usr/share/cubebot/guest`, the defaults of `CUBEBOT_GUEST_KERNEL` and `CUBEBOT_GUEST_ROOT`. The orchestrator runs the sandbox as root with only `CAP_NET_ADMIN`, with `/dev/kvm` and `/dev/net/tun` (KubeVirt's device plugin on Kubernetes) and its workspace disk at `/var/lib/cubebot/workspace.ext4`. On Kubernetes that requires a namespace whose Pod Security level is privileged; a Docker sandbox needs an HTTPS, non-loopback orchestrator origin, since host networking would hand the host's interface to the guest.
