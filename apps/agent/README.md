# Agent application

One Rust package, one executable: `cubebot-agent` (`src/main.rs`). It runs inside `apps/sandbox`'s `cubebot-sandbox` (ADR 0084), as the init of its KVM guest. The agent runs its own tools in that sandbox; there is no separate tool runner.

Normal runtime execution runs authenticated control and bounded text inference, synchronizes typed recovery evidence and acknowledges drain after work settles. It accepts scoped grants for the selected OpenAI or Anthropic model, streams provider output, compacts its context at 80% of the model window, and retries explicit transient provider responses with bounded backoff on the same model. It never resumes inference from a recovered local intent. See [text-chat setup and results](../../docs/development/text-chat-mvp.md). Tools, including MCP server tools, are gated off by default; see [tool execution](../../docs/development/bounded-terminal.md). With computer use on, browser tools drive the desktop's Chromium; see [browser tools](../../docs/development/bounded-terminal.md#browser-tools).

In the `kvm` guest, the kernel runs `cubebot-agent guest` as init (`src/guest.rs`). It mounts the workspace disk on `/var/lib/cubebot`, adds the default route itself when the pod's gateway is outside its subnet, receives the agent's environment from the sandbox over vsock, writes received files under `/run/cubebot` and rewrites them when the sandbox refreshes them, runs the agent as its child while reaping orphaned tool processes, and reports liveness and then the agent's exit status; then it unmounts the workspace and reboots, which ends the VM. With `CUBEBOT_COMPUTER_ENABLED=1` it also starts the desktop as the tool user (Xorg, openbox, the wallpaper, xterm and Chromium; see [computer use](../../docs/development/bounded-terminal.md#computer-use)). [`Dockerfile`](Dockerfile) builds the guest's root filesystem.

It requires `CUBEBOT_ORCHESTRATOR_ORIGIN`, a bootstrap token (`CUBEBOT_BOOTSTRAP_TOKEN_FILE` on Kubernetes, `CUBEBOT_BOOTSTRAP_TOKEN` in Docker sandboxes) and a private `CUBEBOT_JOURNAL_DIRECTORY` (the sandbox creates it with mode 0700). Tools also need `CUBEBOT_WORKSPACE_DIRECTORY` and `CUBEBOT_TOOL_USER`; MCP servers are read from `CUBEBOT_MCP_SERVERS`.

The internal modules own agent-specific behavior. Durable records, shared skill-library revisions, connection refresh, and installation permissions remain orchestrator responsibilities. Shared provider adapters and communication types belong under `modules/`.
